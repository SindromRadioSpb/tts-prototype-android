# Общие правила работы агентов

Единый источник постоянных правил для AGENTS.md и CLAUDE.md.

## Контекст и область задачи

- Читай документы и память по текущей задаче. Повторно используй уже прочитанный актуальный контекст; перечитывай при изменении файла, потере контекста или конкретном противоречии.
- Для границ модулей используй `docs/architecture/AGENT_DOMAIN_GUIDE.md`; для видимого UI — `docs/architecture/AGENT_UI_GUIDE.md`; для команд и релиза — `docs/architecture/AGENT_OPERATIONS_GUIDE.md`.
- Для продуктовых и кодовых решений применяй релевантные критерии R1–R17 из `docs/PROJECT_ROLES.md`. Роли не требуют отдельных агентов или формального отчёта по каждой линзе.
- Тематический канон ищи в `docs/planning/` по задаче. Живой код устанавливает фактическое поведение; он не отменяет утверждённые требования, права и ограничения владельца. При расхождении явно различай требуемое и реализованное.
- Историю восстанавливай, когда она влияет на решение: `.remember/recent.md`, `.remember/archive.md`, нужный `.remember/today-*.md`; индекс Claude memory — `C:/Users/lletp/.claude/projects/E--projects-tts-prototype-android/memory/MEMORY.md`. Поиск по теме предпочтительнее чтения всех журналов.
- Если локальная память недоступна и нужна задаче, сообщи об этом и используй релевантный раздел `docs/planning/AGENT_MEMORY_EXPORT_2026_07_15.md`. Это датированный снимок, не текущий статус.
- Пересказ состояния программы на 5–10 строк нужен при её возобновлении после потери контекста. Для узкой задачи достаточно относящихся к ней фактов.

## Выполнение и завершение

- Запрос на результат разрешает необходимые обратимые локальные этапы, диагностику и исправления в его рамках. Не запрашивай разрешение на каждый технический этап; учитывай ранее выданные разрешения.
- Существенную продуктовую развилку, отсутствующее право, новый платный расход за пределами бюджета или внешнее действие вне разрешённого объёма согласуй до зависимой операции. Подготовь доступный конкретный результат и продолжай независимую работу.
- Локальную ошибку исправь и повтори затронутую проверку. При нехватке исходных данных останови зависимый элемент, сохрани причину и продолжи остальные. Красный release gate блокирует публикацию, но не диагностику и разрешённый ремонт.
- Завершение означает получение и проверку заказанного результата. Первый рабочий вариант не является обязательной остановкой для согласования. Нерешённые ограничения указывай явно.
- Сохраняй чужие dirty-файлы. Перед записью проверь затронутые файлы, коммить только собственный allowlist. Не требуй очистки всего дерева для независимой работы.
- Для созданных по задаче репозиторных research/planning-артефактов делай целевой commit и push, если пользователь не запретил публикацию. Устная консультация не требует создания файла или коммита. Существующее разрешение на commit/push проверенного исправления сохраняется; push в main запускает production-деплой, учитывай фактическую ветку и согласованный объём. Не переходи в main ради отчёта.

## Проверки

- Проверяй затронутое поведение релевантными наборами; API smoke нужен для изменений API и затронутых интеграций. Для документации/инструкций проверяй diff, ссылки, структуру и согласованность правил; UI smoke не нужен.
- Повторяй успешные проверки после значимого изменения, сбоя или при наличии нерешённого риска. Не запускай весь набор только потому, что он существует.
- Для локальных тестов используй изолированные fixtures; проверь побочные эффекты неизвестного runner перед запуском. Paid/live/owner-data проверки требуют соответствующего уже выданного разрешения.
- Для релиза сохраняй требуемые доменные gates и согласованность shell/module URLs, SW, локалей и integrity-контракта. Проверяй фактически опубликованный результат.

## Журнал наблюдений

- Замеченное по ходу работы и не исправленное в этой же сессии (дефект, риск, UX-шероховатость, долг) записывай в `docs/planning/OBSERVATIONS_LOG.md` по правилам в его начале. Устное «заметил, не исправлял» в отчёте без записи в журнал не считается.
- В начале работы над областью смотри открытые записи журнала по ней; закрыв запись, укажи коммит.

## Инварианты качества и данных

- Бескомпромиссное качество, без заглушек: не выдавай отсутствие данных, непроверенный результат или частичную поставку за успех.
- Сохраняй исходники, raw provider evidence и provenance. Производные данные не становятся конкурирующей истиной. Проверяющий источник должен быть независим от проверяемого утверждения.
- Learner state и review_log меняются только каноническим путём в разрешённой задаче; диагностические проверки owner-профиля — read-only с доказательством неизменности review_log.
- БД: схема через миграции; перед рискованной операцией — резервная копия. Права публикации, consent и лимиты платных провайдеров сохраняются.
- Не смешивай automated, production, owner-live, physical-device и assistive-technology evidence.
- Секреты — в окружении, не в коде/артефактах/логах. `.claude/PROD_OPS_PRIVATE.md` открывай только для необходимой production-операции; его содержимое не передавай внешним API и не публикуй.
- Пользовательские артефакты размещай в `docs/research/<topic>/<date>/` или `docs/planning/`, fixtures — в принятом каталоге проекта. `.tmp/` — только промежуточные файлы. Для воспроизводимого артефакта добавь краткий заголовок или README с назначением, источником/командой, исходным commit и статусом evidence. Не создавай отдельный README, если заголовка достаточно.
- Не коммить секреты, кэши, raw transient logs, большие модели и тела Ben-Yehuda works (volume-only).
