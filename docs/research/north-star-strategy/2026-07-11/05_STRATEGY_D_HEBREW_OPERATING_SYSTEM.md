# 05 — Strategy D: Hebrew Operating System

**Status:** PROPOSAL · **Source commit:** `b426b1b7a91abcb4afb8fde7f0e34c042a9bc0d6` · **Date:** 2026-07-11

## Canvas

- **Target/problem:** committed learner whose translation, reading, memory, audio and tutoring are fragmented across tools.
- **Promise:** every meaningful encounter with Hebrew contributes to one coherent learning history and next step.
- **First value:** weak if presented abstractly; must be delivered through Studio or Reading Room.
- **Repeat loop:** any surface creates canonical evidence → shared projections → coordinated next action across surfaces.
- **Long-term value/moat:** longitudinal learner evidence, portable channel architecture and cumulative reduction in tool glue.
- **Dependency:** requires A to create high-quality evidence and B to convert it into continuity; also identity, consent, lifecycle, isolation, cost governance.
- **Competitive archetype:** integrated learning platform/ecosystem, not a single app feature.
- **Cost/risk:** highest; architecture and governance cost precede visible value; scope explosion is likely.
- **Success:** cross-surface continuity improves outcomes while navigation remains simple and each surface retains a clear job.
- **Kill criterion:** users cannot explain the product without a feature tour, or integrated workflows do not outperform focused surfaces.

## Correct role

“Hebrew Operating System” is an **umbrella vision and internal product/platform architecture**. It is not the near-term product name, first-use promise, or a license to add every modality. Users need not understand the term. Internally it means one event canon, explicit projections, shared artifacts, portable channel adapters and governed lifecycle.

## Flywheel and boundaries

`encounter anywhere → canonical evidence → safer learner projection → best next action → action in the right surface → richer evidence`

Moat data is longitudinal and relational, not indiscriminate volume. No dual writes, agent memory as truth, unconsented personal content, cross-tenant aggregates that leak identity, or collection without an outcome decision.

## Failure modes

Feature supermarket; overloaded dashboard; architectural metaphor without value; “for everyone”; impossible message. Anti-goals: no equal-weight navigation for every capability, no speaking/writing claims before safe evidence, no teacher platform now, no forced cloud, no generic chat, no irreversible local→cloud transition.

## Fact / inference / proposal

**FACT:** the code increasingly embodies a platform: common log/projections, adapters and cross-channel continuity. **INFERENCE:** D is already an architectural trajectory but not a validated market category. **PROPOSAL:** use it to govern roadmap and interfaces; market the concrete reading-to-mastery outcome.

## Sources / assumptions / unresolved

Current baseline; CLG architecture; retention canon; Studio/Room compatibility; privacy/security/cost rules. Unresolved: whether customers value suite replacement, which integrations are essential, and whether “OS” improves or harms acquisition comprehension.
