# Product direction — «Hebrew learning atelier»

> This is a product/design direction, not implementation authorization. Values and geometries are
> provisional design tokens to prototype and verify, not a request to replace the current theme in
> one monolithic commit.

## 1. Product thesis

The Reading Room should feel like the primary place where a learner returns to **continue one
meaningful encounter with Hebrew**. The corpus is deep and always reachable, but the first screen
is a composed learning desk: current text, a defensible next choice, and a quiet route to browse.

Working metaphor: **Hebrew learning atelier** — part scholar's desk, part language laboratory.

- “Scholar's desk” contributes calm, typographic dignity, context, memory, and curated paths.
- “Language laboratory” contributes familiar-word fit, audio, morphology, trainer continuity, and
  evidence about progress.
- Neither metaphor contributes ornament for its own sake. No leather-book textures, fake shelves,
  neon AI glow, or decorative cover wall.

Signature interaction: the **Learning Compass** on a featured text explains fit in one sentence:

```text
Подходит сейчас · ≈84% знакомых слов · средне · около 8 минут
```

On an empty profile, it changes honestly:

```text
Хороший первый текст · короткий · частотная лексика
```

On a teacher-assigned song:

```text
Назначено вашей группе · аудио полностью · уровень ב
```

The same region, different evidence. This becomes more distinctive and useful than a generic
colored card border.

## 2. Target information architecture

### L0: Learning Home

```text
┌──────────────── Читальный зал ─────────────── [RU] [theme] ┐
│ Добрый вечер / neutral return line                           │
│                                                            │
│ ┌ Continue / Start feature ───────────────────────────────┐ │
│ │ Hebrew title                           Продолжить · 38% │ │
│ │ Why it fits · level/familiarity/time                    │ │
│ │ last context / optional excerpt              [button]  │ │
│ └─────────────────────────────────────────────────────────┘ │
│                                                            │
│ Сегодня: [слова к повторению] [короткий текст] [песня]      │
│                                                            │
│ Готово для вас                                  Все →       │
│ compact row / compact row / compact row                     │
│                                                            │
│ Библиотека                                      Обзор →     │
│ [Бен-Иегуда 796] [Мои тексты 115] [Песни 12 · закрыто]       │
└────────────────────────────────────────────────────────────┘
```

Priority rules:

1. Due review CTA remains important but joins “Сегодня” rather than permanently owning a full
   banner above all reading choices.
2. Continue wins when a text has meaningful progress.
3. With no Continue, a recommendation must state a reason; otherwise show cold-start choices.
4. Corpus cards become compact browse entries; unavailable roadmap content does not mimic a corpus.
5. The user can always reach exhaustive browsing in one action.

### Corpus home

```text
[← Учиться]  [Библиотека Бен-Иегуды ▾]       [info/settings]

One featured next action / honest cold-start

[Search all texts…]  [Filters · 2]  [Recommended ▾]
active filter chips only: [Поэзия ×] [С аудио ×] [Clear]

Continue / Ready / Saved — short shelves when relevant

All texts — compact list, paged/windowed
title — creator/context — readiness — progress — action
```

### Reader return

Closing or finishing a text returns to the same corpus/home context and shows one result-oriented
choice:

- continue next section;
- review saved words;
- choose a related/easier/harder text;
- mark finished and return to Learning Home.

This is a continuity contract, not a new recommendation engine in the first slice.

## 3. Visual direction

### 3.1 Tone

Calm, editorial, warm-neutral, precise. The interface should feel authored, not generated by a
component template. Hebrew text carries the character. Controls recede until needed.

Provisional palette for prototypes:

| Token | Light direction | Dark direction | Purpose |
|---|---|---|---|
| page | warm paper `#F5F3EE` | ink navy `#0F1722` | reduces sterile dashboard feel |
| surface | near-white `#FFFEFB` | slate `#182230` | reading/content plane |
| raised | white `#FFFFFF` | `#202C3B` | featured/action plane only |
| text | ink `#182033` | `#F2F5F8` | primary copy |
| secondary | `#556070` | `#C2CBD5` | must pass AA at actual size |
| border | `#D9D8D2` | `#374558` | quiet but visible grouping |
| action | lapis `#2459A9` | sky-lapis `#73A8F5` | primary action/focus |
| progress | teal `#2F7D70` | mint `#6FC6B3` | reading/fit positive signal |
| attention | ochre `#A66C18` | amber `#E0AA57` | caveat/partial media |

These exact colors must not ship until automated and manual light/dark contrast checks pass. The
current `--text-faint` pattern must be eliminated for meaningful 11–12px text.

### 3.2 Typography

- UI: retain a high-quality system sans stack for performance and familiarity.
- Hebrew titles/excerpts: use the already shipped Frank Ruhl Libre where rendering quality is
  verified, with system Hebrew fallback. This is the editorial signature, not a global display
  font.
- Feature title: 22–26px desktop, 20–23px mobile; compact row title 16–18px depending on script.
- Support metadata: minimum 13px mobile; avoid 10–11px meaningful text.
- Line height: Hebrew `1.35–1.5` depending on niqqud; metadata `1.35`; no tight clipped niqqud.
- Use weight/spacing before color fading to create hierarchy.

### 3.3 Surface and separation

The user's instinct that cards need stronger separation is correct, but the treatment should vary
by role:

- **Featured next-action card:** 1px border, 2–3px lapis/teal leading edge, subtle two-layer shadow,
  gentle warm/blue tint. One per view.
- **Compact rows:** 1px separator or enclosed quiet surface; no resting shadow. Hover/focus raises
  by at most 1–2px and strengthens the border.
- **Current/reading row:** progress edge and explicit progress text. The edge is not the only cue.
- **Selected filter/control:** filled or strongly outlined state in the control layer.
- **Corpus browse entry:** small emblem/monogram and count, not a giant empty card.

Avoid:

- glowing outlines, because repeated glow creates noise and degrades dark-mode legibility;
- a different bright color for each corpus, because it fragments the shared Room identity;
- permanent shadows on every list row, because a 115-item stream becomes visually heavy;
- emoji as the only corpus identity; icons need a coherent vector/system-symbol treatment later.

### 3.4 Corpus identity without fragmentation

Use one common material and layout plus a restrained identity accent:

- Ben-Yehuda: lapis + archival/library glyph.
- My Texts: teal + manuscript/pencil glyph.
- Study Songs: muted plum/ochre + sound/lyrics glyph.

Accent appears in a 2–3px edge, icon, and small label—not the entire card background. Protected
corpora also show a lock/privacy label in text.

## 4. Component system

### 4.1 FeaturedLearningCard

Required fields:

- title and corpus context;
- primary Start/Continue action;
- fit/reason sentence;
- progress, when meaningful;
- optional excerpt/artwork/media state;
- secondary details/menu.

Empty-profile version uses intrinsic/editorial signals. It never shows `0% familiar`.

### 4.2 TextItemRow

Desktop target: 72–88px depending on second line. Mobile: 72–104px, with a readable two-line Hebrew
title. Content order follows locale while meaning remains stable.

```text
identity: title → creator/context
learning: difficulty/level → familiarity or media → time/length
state: progress line + finished/saved marker
actions: one primary text link/button + overflow
```

Do not make the whole container a `role=button`. Use an article/list item containing a proper title
link and sibling controls.

### 4.3 ShelfPreview

- 4–6 items desktop, 2–3 mobile in a vertical compact list or snap row.
- hard maximum 12 DOM items;
- explicit “Все N” destination;
- heading and one-sentence reason only when the reason adds information;
- no nested carousel inside a horizontal page region.

### 4.4 FilterDrawer / desktop filter bar

Mobile default:

- one search field;
- `Фильтры · N` button;
- sort menu;
- only active filters rendered as removable chips.

Drawer groups filters by purpose:

1. readiness/level;
2. state (new/reading/finished/saved);
3. content taxonomy;
4. media/provenance;
5. advanced personal signals.

Desktop can expose the first group plus sort inline; advanced groups remain in a popover/panel.
The eight smart chips remain available but cease occupying every first screen.

### 4.5 CorpusManagementDisclosure

- My Texts: Add, Manage in Studio, import/source explanation.
- Study Songs owner: participants/invitations, export, backup import.
- Ben-Yehuda: corpus/source/provenance information.

The learner sees a single `Управление` or `О корпусе` action near the corpus identity. Dangerous
import/restore retains explicit confirmation and authority checks in its secondary panel.

### 4.6 LearningTip

Contextual, dismissible, and local to the relevant feature:

- empty profile: “Отмечайте знакомые слова — подбор станет точнее”;
- first advanced search: “Можно искать `#тег` или внутри текста”;
- partial audio: “Аудио есть для 14 из 20 строк”;
- machine layer: “Машинный слой; исходный текст не изменён.”

One tip at a time. No forced onboarding tour.

## 5. Responsive behavior

### 380px contract

Within the first `844px` in a non-empty normal state, the user must see:

- current location/corpus;
- one primary next action;
- at least one complete text item or the beginning of the next meaningful shelf;
- search plus compact filter access;
- no owner backup/import button wall.

Suggested budget:

| Region | Target height |
|---|---:|
| app header + primary mode | ≤120px |
| corpus/learning context | ≤76px |
| featured next action | 180–240px |
| search/filter row | 52–64px |
| first compact item begins | preferably before 560–620px |

The exact numbers may shift after prototype testing; they create an objective antidote to the
current 600–820px of controls before content.

### Desktop contract

- Content max width roughly 1040–1180px; reading/browse columns should not stretch metadata across
  the full monitor.
- Learning Home may use a 7/5 composition: main current item plus a smaller Today/Review panel.
- Browse lists use one or two balanced columns only when each item remains easily scannable.
- A desktop row should not place position at the far left and Hebrew title at the far right across
  1000px; keep identity and signals in a bounded grid.
- Filters may live in a top bar or narrow side panel, but the list remains the visual protagonist.

### HE/RTL contract

- Use logical CSS properties (`padding-inline`, `border-inline-start`, `inset-inline-*`).
- Reverse spatial reading order, not semantic priority: title remains first in accessible/DOM order.
- Progress direction and media time remain semantically correct; numerals and percentages need
  bidi isolation.
- Corpus switcher, menus, chevrons, and back navigation must be explicitly verified, not assumed.
- Hebrew title with niqqud must not clip at compact row heights.
- RU/EN technical terms must not leak into the visible HE experience unless they are identifiers.

## 6. State design

### Loading

- Preserve layout with 3–5 skeleton rows, not dozens of blank cards.
- Announce loading state accessibly once.
- Search state remains stable while async results replace the skeleton.

### Empty profile

- Show editorial/intrinsic “Start here,” not empty personalized sections.
- Explain in one sentence how personal fit will improve.
- Offer one short, one audio-supported, and one culturally meaningful choice where data permits.

### Empty corpus/result

- State what filter/search produced zero.
- Provide `Сбросить фильтры` and one nearby alternative.
- For unsupported capabilities say why (“оценка знакомых слов появится после анализа”), not a dead
  “нет данных.”

### Offline/degraded

- Curated/local/offline-capable content remains available.
- Cloud-only or protected actions state what is unavailable and what remains usable.
- No generic retry after a canonical/local action already succeeded.

### Finished

- Give recognition, not confetti. Offer `К словам`, `Похожий текст`, or `На главную`.
- Finished items move out of prime Continue space but remain searchable/history-visible.

## 7. Motion and interaction

- 120–180ms state transitions for filter chip, row hover/focus, and drawer.
- 180–240ms shelf expansion/route continuity where it helps preserve place.
- No looping animation, card floating, shimmer after load, or automatic horizontal movement.
- `prefers-reduced-motion` removes translation/parallax and shortens fades.
- Focus is always visible with a high-contrast 2px outline plus offset; hover is never the only cue.
- Touch and keyboard reach identical actions. Overflow menus restore focus to their trigger.

## 8. Design option comparison

### A — Visual normalization only

- Restyle existing hub/cards, add stronger borders/shadows, align headers.
- Keep current zone order, all filters, all-card rendering, and group admin placement.

Pros: small implementation diff.

Cons: leaves performance, learning hierarchy, mobile fold, and semantic nesting unsolved. It would
make the same product model prettier but not mature. **Not recommended as destination.**

### B — Learning-first typified Room (recommended)

- Learning Home, common corpus zones, featured next action, compact rows, progressive filters,
  management disclosure, bounded shelves and paged/windowed browse.
- Preserve all current learning/data capabilities and deep routes.

Pros: directly improves learner decisions and density; uses current state; distinctive product
thesis.

Cons: touches shared Room presentation and needs staged adapter/gate work. **Recommended.**

### C — New multi-route learning platform shell

- Separate routes for Home, Browse, Saved, Paths, Review, Admin; new navigation rail; configurable
  dashboards and recommendation service.

Pros: maximal long-term flexibility.

Cons: high architecture, migration, routing, and state risk; can duplicate Studio/Room/Trainer
truths. **Reject for this maturity program; reconsider only through separate recon.**

## 9. Role critique

| Lens | Verdict on B | Required constraint |
|---|---|---|
| R2 SLA methodologist | Strong: next action, fit reason, context-to-review reduce dead ends | progressive disclosure; no metrics for their own sake; keep live context |
| R4 premium mobile/RTL | Strong if 380px and RTL are design inputs, not cleanup | screenshots + geometry + keyboard/a11y before each UI slice |
| R5 product/market | Differentiated by offline Hebrew readiness and one reading loop | do not imitate free retail libraries or add cloud dependency |
| R6 curator-librarian | Strong: curated preview versus exhaustive browse ends the “dump” feel | per-work attribution and native taxonomy remain reachable |
| R7 Hebrew literary editor | Strong if cold-start and recommendation respect period/register | do not label archaic/canonical difficulty as beginner-friendly without caveat |
| R8 graded-reading designer | Strong: readiness ladder, on-ramp, and “what next” are explicit | scaffolding must fade; no permanent translation dependence |
| R9 authority/provenance | Safe only with normalized confidence/provenance fields | derived/asserted/curated never collapse into one badge |
| R11 do-no-harm | Safe only as presentation over existing canonical states | no second progress/recommendation truth; cross-surface reader parity gates |

## 10. Immediate implementation sequence implied by design

1. **Foundation:** common view model/presenter contract, DOM bounds, semantic row, contrast/targets.
2. **Learning Home:** feature next action + compact corpus entries using existing state only.
3. **Corpus shell:** common switcher/zone order, filter disclosure, management disclosure.
4. **Corpus adapters:** Ben-Yehuda, My Texts, then Study Songs, preserving native capability.
5. **Continuity:** post-reader return/finish actions and visual-quality regression gates.

Personalized time estimates, cross-corpus bookmarks, paths, quizzes, and configurable shelves are
backlog. They should not delay the core premium hierarchy.

## 11. Visual self-critique before prototyping

- Is “warm paper” too nostalgic? Keep it nearly neutral; Hebrew typography, not texture, provides
  character.
- Is the Learning Compass too badge-heavy? Render it as one sentence with at most two compact
  supporting tokens, not four pills.
- Does a colored edge look like status severity? Pair it with an explicit label and keep corpus
  identity subtler than progress/attention.
- Are compact rows becoming spreadsheet-like? Use generous vertical rhythm, Hebrew hierarchy, and
  one carefully composed featured card to retain warmth.
- Does collapsing filters hide expert power? Show active-filter count, preserve query grammar, and
  keep desktop shortcuts; test expert tasks explicitly.
- Does Learning Home compete with Trainer? Treat due review as one Today action and reading as the
  Room's primary job; do not recreate Trainer content.
- Does group admin become undiscoverable? Keep a clearly labeled owner control beside corpus
  identity and test export/import/member tasks, just not before the first learning item.

The prototype should answer these with RU/HE 380px and desktop fixtures before implementation
scope is approved.
