# Медиатека: прерывание подготовки предпросмотра с HTTP_200

Основание: production 3.11.801 (`a5955da4`), сообщение владельца 2026-10-20.
Область: чтение сведений о корпусе в мастере публикации и Publication Center.

## Причина и изменение

`getPublisherCorpus` выбирал `SELECT *` из `publication_draft_items`, включая
полные `snapshot_json`. Для текущего канала KAN11 активный черновик содержал
25 материалов и 17 598 187 байт снимков. Заголовки JSON HTTP 200 приходили
примерно за 938 мс, но чтение тела прерывалось клиентским тайм-аутом
(зафиксированы 30 и 35 секунд, `net::ERR_ABORTED`). Обработчик скрывал ошибку
чтения через `.catch(() => ({}))` и показывал `HTTP_200` как ошибку полей.

Теперь запрос редактора выбирает только идентификаторы, порядок, заголовки,
хэши и сведения о правах. Снимки остаются в БД; проверка и публикация читают
канонические полные снимки прежним путём. Все найденные потребители редакторского
запроса используют только оставленные поля. Не меняются права, CAS, ключи
идемпотентности, исходные архивы и опубликованные редакции.

Тайм-аут/прерывание чтения ответа сохраняется как таковое. Некорректный JSON или
контракт ответа получает отдельное сообщение. На время отправки форма получает
`aria-busy`, кнопка — «Выполняется…»; повторная отправка заблокирована, после
ошибки исходная надпись восстанавливается. Переводы добавлены для RU/EN/HE.
R3: понятное ожидание и причина сбоя; R4: сохранение канонических данных.

Команда воспроизведения:

```powershell
node scripts/premium/mediatheque-preview-regression-smoke.cjs --archive '<полный путь к Hamam-3-clean.learning.zip>'
```

Без `--archive` используется синтетический переносимый пакет. Runner поднимает
одноразовый сервер без операторских секретов и не обращается к production.
Машинный результат: [browser-evidence.json](browser-evidence.json).
Скриншоты показывают синтетический профиль, архив в git не включён.

## Production-приёмка 2026-10-21 (местное время)

Выпущена 3.11.802, коммит `90013ec9f134ebb82a2e386564cfe2ff6a5c5530`.
Coolify завершил выпуск; совпали версия, health/DB/migrations и SHA-256 30
публикуемых файлов, включая новый модуль ответа. [Проверка файлов](production-assets.json).

В исходной открытой форме без перезагрузки и повторного ввода данных:

- GET корпуса: 76 203 байта вместо полных снимков, 261 мс; 25 материалов.
- Нажата только «Подготовить предпросмотр»: detail 137 мс, копирование архива
  308 мс, права 111 мс, проверка 1115 мс, финальный detail 141 мс. Все HTTP 200;
  показан шаг 3 с серией 3, без ошибки — около 1,8 с по запросам.
- Сразу после подготовки row count и SHA-256 `review_log`/`word_status` совпали
  с baseline. Сырые данные и отпечатки профиля не публикуются.
- Затем параллельно во вкладке завершены следующие шаги публикации. Агент их
  кнопки не нажимал. Серия 3 появилась в public API/каталоге; текущая редакция
  содержит 26 материалов. Read-only SQL сравнил новую редакцию с предыдущей:
  все 25 прежних материалов сохранили snapshot SHA-256 и три разрешения доступа.

Исторический `SELECT *` существует с `2e3e5f64` (2026-08-20), поэтому причинная
связь именно с предыдущим релизом 3.11.801 не установлена.
[Сводное evidence](production-evidence.json).

## Вместимость хоста

До выпуска 4,0 GiB / 89%, build cache 0 B. В пике сборки осталось 41 MiB (100%).
По ранее выданному разрешению выполнен только `sudo -n docker builder prune -af`:
2,69 GB по Docker. После rollout — 2,7 GiB / 93%, build cache 0 B; 16 images,
11 running containers, 4 volumes. Сохранены 3.11.802, rollback 3.11.801 и 3.11.800;
образы, БД и бэкапы вручную не удалялись. `disk_warn=true`, O-047 остаётся открытым.
Текущего запаса нельзя считать достаточным для следующей холодной сборки без
новой оценки вместимости.

Отчёт приёмки сохранён в ветке `docs/mediatheque-preview-acceptance-20261021`;
исправление и локальные доказательства уже в `main`.
