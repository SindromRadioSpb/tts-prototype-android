## `t1-baseline-vs-composed.json`

Coverage measurement for the serving-order change (spec §5.5, acceptance §12.1). Generated by:

```
npm run audit:train-queue -- --write
```

Deterministic: a fixed synthetic backlog of 208 due words shaped like the owner's recorded
profile (208 due / 290 scheduled, predecessor packet §9), a fixed start date, no randomness.
The harness carries its **own** reimplementation of the pre-T1 rule (`lapses DESC, due ASC` →
24-row prefix cut → weakness rank → 12), so the baseline is an independent oracle rather than
production code grading itself.

### The model matters

The simulation applies scheduling feedback **and failures**. A static backlog re-served every
day makes the old and new rules look identical at 100% coverage, and so does a success-only
model. The owner's loop closes through failure: a wrong answer sets `interval = 0`, which sets
`due = now`, which under `lapses DESC` pins the word to the head of the queue permanently.

### Results over 20 consecutive days

| Run | Unique served | Coverage | Starved | Backlog |
|---|---|---|---|---|
| baseline (pre-T1) | 36 | 17.3% | 172 (87%) | 208 → 188 |
| **T1 ordering, size-matched 12/session** | **137** | **65.9%** | **71 (38%)** | 208 → 112 |
| T1 with shipped defaults, 20/session | 184 | 88.5% | 24 (14%) | 208 → 66 |

The **size-matched** row is the honest headline: the session default also grew from 12 to 20,
so the third row mixes two changes. Holding throughput at the old 12 words a day, the ordering
change alone takes coverage from 17.3% to 65.9% and cuts starvation from 87% to 38%.

### Reading the numbers

- `uniqueServed` — distinct lemmas reached in 20 days.
- `starvedWords` — words that were **due on at least 5 days and served zero times**. This is the
  direct measure of the complaint that started this wave.
- `maxDayShare` is reported but is **not** a defect signal on its own: a word that fails every
  day is set to `due = now` by the scheduler itself, so serving it every day is honest. Spec
  §12.1's "unless FSRS genuinely schedules it there" is exactly this case, and starvation is the
  metric that separates the two.
- `loadAtOldSessionSize` — at 12 reviews a day this backlog needs ~37, which is why the old
  fixed session could never drain it.
