# Последовательная программа: исправления и контроль качества

Дата: 2026-10-03. Исходная production-база: `9d1d11e7` / 3.11.722.
Ветка реализации: `fix/material-reliability-performance`. Целевая версия: 3.11.723.
Статус: локальная реализация; production ещё не опубликован. Исследование до исправлений — [RESEARCH.md](RESEARCH.md).

## Реализовано

1. **Последний выбранный материал и позиция.** `studio-session.js` отделяет постоянный указатель сохранённой карточки от черновика каждой вкладки. Старый снимок мигрирует один раз на браузер; повторный вход не возвращает материал от 13 сентября. Старые данные сохранены. Открытие по ссылке приоритетнее восстановления. Позиция читается из `text_progress`; восстановление старой вкладки не перетирает более поздний явный выбор другой вкладки.
2. **Запоздавшие результаты.** `material-open.js` задаёт актуальность операции для Студии и Зала. Reader проверяет её до изменения DOM, включая ошибку загрузки. Исходник, заметки, привязка видео, подсказка перепривязки и восстановление строки проверяют актуальность после ожиданий. У каждого Reader mount также остаётся собственная защита.
3. **Повторный выбор во время импорта.** Три пути корпуса используют последовательную очередь: более поздний выбор отменяет устаревшее отображение и ещё не начавшуюся работу. Независимые импортные транзакции не выполняются одновременно. Запущенный импорт завершается безопасно; неподтверждённого прерывания записи нет.
4. **Защита сохранения.** Снимок строк, исходника, паспорта, TTS-профиля и базовой ревизии создаётся до асинхронных проверок. Несовпадающий ID отклоняется до обращения к БД; смена контекста до записи прекращает сохранение. Завершение уже записанного снимка A не возвращает редактор из B в A. Последующее обогащение строк также защищено.
5. **Classic ↔ расширенная Студия.** Один материал владеет исходником и таблицей; при переключении остаётся одна смонтированная таблица. Расширенный режим получает нормализованные поля для сохранения и сохраняет иврит. После сохранения используются новые ID строк, а не ID до замены.
6. **Быстродействие.** Публичная Медиатека отображается по готовности public API независимо от локального каталога, auth, tutor и owner draft. Баннер неопубликованных изменений сохраняется. Локальная ссылка Зала открывается до загрузки каталогов и групп. Транслитерация и заметки не задерживают восстановление позиции; дозаполнение обновляет ячейки без повторного создания всей таблицы. При наличии уже загруженного паспорта медиапанель не перечитывает карточку.
7. **Cross-tab.** Читающий `WITH ... SELECT` больше не создаёт уведомления о записи; `WITH ... UPDATE/DELETE/INSERT`, неизвестный SQL и смешанные statements сохраняют invalidation. Возврат фокуса на чистую Медиатеку не вызывает новый полный проход. Отдельная адресация уведомлений по таблицам пока не добавлена.
8. **QC.** Исполняемые гонки, сохранение, новая вкладка, позиция, независимость каталога от необязательных запросов и переключение режимов добавлены в `smoke:material-reliability` и CI. Согласованы URL модулей, локали, SW и integrity manifest. Старый диагностический `reproduce.cjs` теперь явно читает базу `9d1d11e7`, текущие acceptance-тесты проверяют исправленное поведение.

## Проверки и границы доказательств

- Полный `npm test`: **2371/2371**. Поздние узкие изменения дополнительно проверены профильными наборами и браузером.
- `test:api-smoke`: PASS, включая соответствие версии SW/client-config и проверки доступа без вызовов платных провайдеров.
- `smoke:memory-canon`: **91/91**. Исправлено устаревшее ожидание 53 миграций: фактически уже было 54; добавлена явная проверка последнего индекса. Учебная схема и review-log writers этим пакетом не изменены.
- Reader parity: 37 проверок функций + 6 вариантов таблицы; эталон не переписывался.
- SW A/D/E/G на неизменном наборе файлов: **8/8** (уведомление на всех поверхностях, возвращение, смешанная поставка, две вкладки). Обычный F5 при waiting worker остаётся известным O-015, эти сценарии не объявляются исправленными.
- Браузерные fixtures: A → B → поздний источник A; новая Студия восстанавливает B/строку 2; update → copy → update; Classic → IDE → Classic; один proTable и правильные Hebrew/row IDs; публичный каталог при зависших auth/tutor; локальная ссылка при зависшем запросе групп.
- Последний локальный замер fixtures: каталог 265 мс от навигации; локальный Reader 699 мс; прогретые открытия Студии до ready 289/333 мс. Это отдельные синтетические запуски, **не production p95 и не сравнительный benchmark устройства**.
- Несколько multitab-прогонов прошли (независимые черновики, отсутствие reload, перенос фокуса, видео, замороженная вкладка). Один повторный одновременный холодный запуск четырёх поверхностей дал `DB_LOCK_WAIT_TIMEOUT` при первой записи fixtures. Повтор отдельно прошёл; прогон исходной 3.11.722 также прошёл. Причина единичного отказа пока не доказана, отдельная диагностика продолжается; этот отказ не скрывается успешными повторами.
- Все изменяющие проверки используют одноразовые серверы и профили. Подключённый профиль владельца не использован для записи. Физический Android/iPhone и новое состояние владельца после публикации не проверены.

## Оценка крупной перестройки и начатый этап

Полная одномоментная перепись монолитов не имеет подтверждённой выгоды по latency и расширила бы область регрессий. Доказанная причина нескольких дефектов — асинхронные продолжения с общим изменяемым состоянием; поэтому выгодно сначала выделять владельцев состояния и операций.

Первый этап уже выполнен: независимый модуль сессии; общий модуль актуальности открытия, последовательного импорта и проверки идентичности сохранения; передаваемый контекст операции в Reader. Инварианты теперь исполняются отдельными тестами. Стек, канонические БД и авторизация сохранены.

Следующие границы: получение материала отдельно от показа, жизненный цикл media отдельно от таблицы, подготовка/фиксация save snapshot отдельно от UI. Выносить по одному после проверки эквивалентности. Виртуализацию 1000–5000 строк и серверную пагинацию личного каталога выбирать по отдельному профилю; текущие измерения не доказывают, что они выгоднее устранения блокирующих зависимостей. Прежде следующего крупного этапа — закончить расследование cold-start lock и проверить опубликованную поставку.

## Повторение

```powershell
npm test
npm run test:api-smoke
npm run smoke:memory-canon
npm run smoke:material-reliability
```

SW/parity запускались с изолированными DATA_DIR/DB_PATH через `smokeServerEnv`; браузерные binaries брались из существующего `PLAYWRIGHT_BROWSERS_PATH`. Для SW набор файлов должен оставаться неизменным весь прогон: server integrity вычисляется при старте. Изменение JS во время первого прогона сделало его результаты непригодными; стабильный прогон приведён выше.

Обнаруженный побочный эффект общего `npm test`: `physicsLearningDerivatives.test.js` пересобирает tracked research artifacts по месту. Их собственные тестовые изменения восстановлены; чужой основной checkout не тронут. Это отдельный долг изоляции тестов.
