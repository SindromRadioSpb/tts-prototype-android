# Актуализация быстродействия после 3.11.727

Дата: 2026-10-04 (локальная дата, raw timestamps — UTC). Запрос: повторно измерить результат работ по надёжности, открытию/lifecycle, сохранению и адресным обновлениям вкладок. Изменений production runtime в этой проверке нет.

## Вывод

На этом стенде подтверждается сокращение работы при межвкладочной записи прогресса и сохранение эффекта пакетного импорта. Открытие IDE также стало быстрее. Для Classic, Зала и сохранения существующей карточки разница значительно меньше, разброс перекрывается. Сохранение копии не ускорилось: медиана выросла на 9,7 мс / 4,1%, с перекрытием диапазонов; эта серия не доказывает устойчивую регрессию или эквивалентность. На production обнаружено отдельное ограничение: первое открытие двух публичных материалов занимает медианы 29,83 и 13,89 с. Его нельзя скрывать за быстрыми повторными открытиями локальной карточки.

Прежние значения 1,58 с для импорта и 443/347/193 мс для открытия остаются историческими. Для текущих решений использовать эту серию. Это не production p95, не статистический SLO, не Android/iPhone и не тест пользовательского профиля.

## Методика и воспроизводимость

- Windows 10.0.26200, Ryzen 5 5600G, 12 logical CPUs; Node 22.22.1, Chromium 148.0.7778.96, headless, 1280×850. Нагрузка прочих процессов ОС не фиксировалась; другие тестовые наборы одновременно не запускались.
- Одноразовые browser contexts и серверные DATA_DIR/DB_PATH; `.env` оператора не загружается. Service worker заблокирован; маршрутизация Playwright отключает HTTP cache. Внешние провайдеры заблокированы. Локальное browser-хранилище использует штатный выбор backend; это не сравнительный тест OPFS против IndexedDB.
- Основной сценарий: 3.11.724 (`54b7d803`, runtime побайтно совпадает с `d5e6c826`) → 3.11.727 (`6854c976`, runtime совпадает с production `e878b850`). Порядок блоков A–B–B–A, по два чистых профиля в блоке. Итого четыре профиля на версию; в каждом две разогревающие и десять измеряемых операций. 40 тёплых измерений на метрику сгруппированы по четырём профилям, а не являются 40 независимыми устройствами.
- Материалы: две карточки по 40 строк, исходник 100007 символов. Завершение открытия проверяется по правильному материалу и всем 40 строкам. Таймер тёплого открытия заканчивается после завершения настоящей функции открытия, не после дозагрузки всех необязательных источников/медиа и не после измеренного paint браузера.
- Сохранение через настоящие UI core-функции: копия, затем обновление её же карточки; после таймера сверяются ID и строки. Во время сохранения открыт Reader. Перед тестом межвкладочных обновлений в библиотеке 14 карточек. Каждая запись прогресса остаётся в статусе `in_progress`; замер от начала вызова записи до завершения обработчика/синхронного render Медиатеки. Ожидание готовности в harness не включается в browser timestamps обработчика.
- «Холодное» открытие здесь означает первую навигацию к поверхности в новом browser context с отключённым HTTP cache. Reader и личная Медиатека имеют заранее подготовленную локальную библиотеку; это не первый запуск пустого продукта с автоматическим импортом канона. Studio измеряется до готовности БД, Reader — до видимой строки, Медиатека — до готовности личного каталога. Значения включают навигацию и ожидание состояния через Playwright.
- Все числовые сводки воспроизводятся: `python docs/research/material-performance-refresh/2026-10-04/summarize.py`. [Машинная сводка](summary.json); raw samples сохранены рядом.

## Холодный импорт и соседняя запись

Одинаковый канон: 79 текстов, 6646 строк; SHA-256 исходного ZIP в обеих версиях `3a4319ad81cb9512e82b5c62a03d54d18128e4d489f4b08eeb5e2531d203069b`; независимый digest всех полей и default audio keys `24f98390a1d37b395444bebd6326c740077ba63c71e4383a3e7ec7f280b73308`. Корпус не копируется в evidence. Конкурирующая запись запускается после подтверждения BEGIN; схема, write path и 30-секундный lock deadline не изменяются.

Исходная версия — 3.11.722 / `9d1d11e7`; итоговая — 3.11.727. Два завершённых исходных прогона и четыре итоговых, последовательно A–B–B–A. Дополнительные исходные профили не добавлялись после повторения штатного lock timeout.

Транзакция быстрее в **5,70 раза** в этой серии. Время старой конкурирующей записи не представляется как успешное ожидание: она завершилась ошибкой примерно через 30,15 с, хотя импорт позднее завершился и содержимое совпало. Raw: [исходный A](import-before-a.json), [итоговый A](import-after-a.json), [итоговый B](import-after-b.json), [исходный B](import-before-b.json).

[Первый незавершённый замер и диагностический повтор](import-initial-failure.json) сохранены отдельно и исключены из числовой сводки. Первый runner останавливался при ошибке конкурирующей записи; диагностический повтор пытался читать через уже отказавший worker. Итоговый runner учитывает ошибку как отдельный outcome и проверяет данные через вкладку импорта. Причина отличия прежних 11,22/1,58 с от сегодняшних абсолютных значений отдельно не установлена; условия и момент измерения в старом и новом runner различаются, перенос коэффициента на любой ZIP или устройство не обоснован.

## Production

Результаты четырёх последовательных анонимных профилей приведены в [production.json](production.json). Service worker и HTTP cache отключены; состояние серверного/edge cache и реальная сеть не контролировались. Каталог измеряется до первой видимой публичной ссылки; два Reader — до первой видимой строки. Независимый public snapshot запрашивается после таймера; ID/заголовок/иврит/перевод проверяются отдельно. Это актуальная наблюдаемая скорость, не историческое сравнение deployment A/B.

### Отдельный диагностический прогон

[Диагностика](production-diagnostic.json) не включена в четыре основных замера: observer long tasks и наблюдение worker RPC добавляют собственную нагрузку. Для первого материала (`work-eeb47e95ad7e278cd95d1b6b`, 2477 строк) открытие заняло 28,61 с, суммарные long tasks — 16,39 с, одна непрерывная задача — **14,37 с**. Public snapshot загрузился за 0,67 с; две записывающие транзакции заняли 5,54 и 1,37 с. Для второго материала (`work-33e1abbcf255bda33c2e834b`, 1040 строк): открытие 14,13 с, long tasks суммарно 4,75 с, одна задача — **4,10 с**, транзакция 0,67 с.

Это подтверждает существенный вклад главного потока, а не объяснение всей задержки одной сетевой загрузкой. [reader-core.js](../../../../public/js/reader-core.js) в `presentMaterial` строит HTML для всех строк и присваивает его `mount.innerHTML` целиком. Большая таблица и её последующая обработка — обоснованный кандидат для следующей оптимизации; CPU-профиль с attribution по функциям не снимался, поэтому точная доля конкретного рендера не заявляется. RPC wall time включает очередь и задержку доставки callback заблокированным главным потоком: его нельзя выдавать за чистое время SQLite. Resource timings и long tasks перекрываются, их нельзя просто суммировать.

Приоритет следующей работы: профиль первого открытия на 1000–2500 строк и ограничение объёма синхронной отрисовки, сохраняя позицию/поиск/озвучку и идентичность материала. Отдельно оценить конкуренцию начального импорта канона с запрошенным публичным материалом. Наблюдение зарегистрировано как O-069; производственный код в этой задаче не менялся.

## Запуск

```powershell
node scripts/multitab/material-performance-benchmark.js --root=<runtime-worktree> --rounds=2 --out=<workflows.json>
node scripts/multitab/material-performance-benchmark.js --mode=import --root=<runtime-worktree> --rounds=2 --out=<import.json>
node scripts/premium/material-production-performance.js --version=3.11.727 --rounds=4 --out=<production.json>
node scripts/premium/material-production-performance.js --version=3.11.727 --rounds=1 --diagnostics --out=<diagnostic.json>
python docs/research/material-performance-refresh/2026-10-04/summarize.py
```

Скрипты запускаются из worktree, в котором установлены зависимости; `--root` меняет только тестируемый runtime. Измерять версии последовательно, одним и тем же runner. Этот отчёт и harness опубликованы в рабочей ветке; повторный production build ради измерений не нужен.
