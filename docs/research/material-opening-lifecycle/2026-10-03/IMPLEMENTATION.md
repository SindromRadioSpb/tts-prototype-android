## Границы реализации

1. **Общая модель чтения.** `MaterialOpen.load` параллельно получает лёгкую карточку и строки через переданный local DB или API adapter; проверяет актуальность и ID карточки/каждой строки, единообразно сортирует строки. Возвращает данные или типизированную причину неуспеха, не меняет DOM, сессию, прогресс или медиапаспорт. Classic, IDE и Зал используют этот путь. Само чтение БД не прерывает транзакции.
2. **Отображение отдельно от чтения.** В Reader выделен `presentMaterial`: готовая модель → UI rows → таблица; перед записью DOM остаются проверки актуальности операции и mount. Studio передаёт ту же проверенную модель существующим отображениям Classic/IDE. IDE теперь, как Classic, дозагружает большой исходник после показа; поздние source/rebind продолжения ограничены той же операцией. Табличный дизайн и правила отображения иврита сохранены.
3. **Общий владелец ресурсов медиа.** `MediaHost.createLifecycle` управляет отменой создаваемого YouTube-плеера, принятым адаптером, остановкой karaoke, освобождением local stage/object URL и очисткой blob resolver. У каждой попытки создания отдельный DOM-контейнер: поздний ответ может удалить только свой контейнер. Повторное обращение к тому же плееру сохраняет адаптер/слушатели; другой материал с тем же video ID получает новый lifecycle. При пересчёте источника устаревшая попытка освобождается и не блокирует повторное создание. Запоздавшее OPFS-чтение не заполняет очищенный кэш.
4. **Актуальность закрытия.** Исполняемая гонка доказала, что `closeReader`, ожидающий сохранения позиции, мог затем скрыть уже открытый новый текст. Теперь закрытие тоже теряет право менять поверхность после нового открытия: проверка после progress flush, ожидания каталога и перед навигацией.
5. **Один поиск строки по ID.** `MaterialOpen.sentenceIndex` понимает DB и UI формы ID. Его используют Classic, IDE и Зал. Устранено расхождение IDE: старый поиск не учитывал обычное поле `id`; ссылка на конкретную строку не выделяла её. Переход к строке 7 подтверждён браузером.

Коммиты реализации: `602967d5` (общая модель чтения и Reader presentation), `66e0439a` (Studio, media lifecycle, гонки и проверки).

R4: материал, выбранная строка, отсутствие перезагрузок и сохранение плеера при смене колонок. R11: отдельные исполняемые гонки, независимые ожидаемые ID/строки и прежний parity-эталон. ## Скорость

Один и тот же `scripts/multitab/material-opening-lifecycle-smoke.js`, один ПК/Chromium, отдельные чистые профили и серверы, по две разогревающие и десять измеряемых операций на поверхность. Две карточки по 40 строк, исходник 100010 символов. Измеряется завершение настоящего открытия с проверкой содержимого таблицы. База запускалась в неизменённом предыдущем worktree; её runtime побайтно совпадает с main. Сравнительные прогоны не выполнялись одновременно с другими тестами.

## Повторение и пределы этапа

```powershell
npm test
npm run test:api-smoke
npm run smoke:material-reliability
npm run smoke:room-media
node scripts/multitab/material-opening-lifecycle-smoke.js --checks-only
# Сравнение тем же стендом с выбранным неизменённым checkout:
node scripts/multitab/material-opening-lifecycle-smoke.js --root=<baseline-worktree> --out=<result.json> --benchmark-only
```

Все изменяющие сценарии — в одноразовых профилях/БД; owner-profile не использован. Внешние provider запросы заблокированы в новых browser fixtures. Поздние YouTube-ответы моделируются на границе provider create/destroy при настоящих surface wrappers/lifecycle; реальное внешнее YouTube-воспроизведение, физические Android/iPhone и production acceptance не заявляются. Локальное воспроизведение проверено настоящими media fixtures.

Выделены владельцы основных чтений и media resources. Optional notes/transliteration, passport activation и surface-specific progress policy остаются в существующих оркестраторах; этот этап не является полной переписью монолитов. Виртуализация, адресная cross-tab invalidation и отдельный save coordinator — следующие самостоятельные задачи по профилю, не часть принятого результата.
