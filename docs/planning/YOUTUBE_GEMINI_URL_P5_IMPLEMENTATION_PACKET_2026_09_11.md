## 1. Задача владельца

Сегодня путь «ссылка → учебный материал» требует вручную: скачать медиа, выбрать файл, запустить ASR, добавить черновик,
обновить таблицу, сохранить в библиотеку, открыть метаданные и вставить ссылку в «Источник видео».
Требование: **вставил ссылку — получил сохранённую карточку с работающим режимом «YouTube-видео»**, без скачивания медиа.
Локальный файл остаётся возможным позже: пользователь подключает его в Импорт-центре и переключает воспроизведение.

## 2. Что уже измерено (не повторять)

Полные числа — в research-артефакте. Существенное для реализации:

- Ссылка принимается как `parts[].file_data.file_uri`; сервер Google сам достаёт ролик, наш сервер не участвует.
- Метки **честные**: против нашего детерминированного `ffmpeg`-среза медиана ошибки 0 с (73 якоря, 5 окон), между двумя
  независимыми прогонами медиана 0 с и P95 = 1 с (210 якорей). Полное покрытие 26-мин ролика без дыр >25 с.
- `video_metadata{start_offset,end_offset}` работает и для YouTube и режет **вход** (120 с = 10 921 видео-токен против
  141 962 на полном ролике), метки возвращаются **абсолютными**.
- `countTokens` для YouTube-ссылки **бесплатен**, и аудио-модальность ровно 32 ток/с (49 919 / 1560 = 32.00).
- `fps: 0.2` снижает стоимость окна на 55 % без ухудшения меток; `mediaResolution` на YouTube не влияет ни на что.
- Отказы: `watch?v=` и `youtu.be/` принимаются, **URL с `&t=`/`&list=` → 400**; битый id и не-YouTube → 400
  `INVALID_ARGUMENT` без различимой причины. За сессию 5 × HTTP 503 и 1 × HTTP 429 на `generateContent`.

## 3. Контракт

### 3.1 Новый модуль `public/js/youtube-asr.js`

Dual-export (browser `window.YoutubeAsr` + Node), pure-ядро отделено от сетевых вызовов, по образцу `asr-transcript.js`.

| Функция | Контракт |
|---|---|
| `canonicalize(url)` | Через существующий `PlaybackSource.parseVideoId` → `canonicalUrl`. Возвращает `{video_id, url}` либо `null`. Именно это снимает измеренный 400 на `&t=`/`&list=`. |
| `estimate(deps, url)` | `countTokens` (бесплатно) → `{durationSec, audioTokens, windows, inputTokens, estimatedUsd}`. `durationSec = audioTokens / 32`. |
| `planWindows(durationSec)` | Делегирует `AsrTranscript.asrWindows` — те же 15 мин и перекрытие 30 с, что у файлового пути. Одно окно ⇒ один вызов без клипа. |
| `buildRequest(url, win, opts)` | `file_data.file_uri` + `video_metadata{start_offset,end_offset,fps:0.2}` + канонический `AsrTranscript.ASR_PROMPT`. **Range-промт запрещён**: диапазон ограничивает вход на стороне API, метки абсолютны by construction. |
| `transcribe(deps, url, onPhase)` | Прогон окон, шов по тексту `stitchWindowSegments`, гейты честности, ретрай. Возвращает `{segments, warnings, coverage, blindRanges, usage}`. |
| `classifyFailure(status, body)` | 400 → `YT_URL_REJECTED` (честно: «ссылка не принята»; причину API не сообщает), 403/429 → `YT_QUOTA`, 503 → `YT_OVERLOADED`, иначе `YT_FAILED`. |

Ретрай: 503/429 → экспоненциальный backoff (3 попытки, 4/12/30 с, джиттер). 400 не ретраится никогда.

Честность переиспользует готовое из `asr-transcript.js` без форка: `stitchWindowSegments`, `runSpeechDensity`,
`classifyGap`, `classifyClockCompression`. Ненадёжное по часам окно помечается `blind` — караоке там молчит, строки живут.

### 3.2 Фаза `transcribing` в `learning-material-task.js`

`create()` принимает `youtube_source: {video_id, url}` как альтернативу непустому `source_text`.
Раннер получает ведущую фазу: если `job.input.youtube_source` задан и `!job.transcript` — транскрибируем и кладём
`job.transcript = {text, segments, coverage, blind_ranges, provider_meta}` в журнал.
**Resume после сбоя перевода или F5 не оплачивает ASR второй раз** — это отдельный красный тест.

### 3.3 Фаза `binding` после `saved`

`PlaybackSource` repository `append({url, offset_ms: 0})` для `saved_text_id`.

**Решение по `timing.status`: `unverified`.** Новый статус `source-asr` не заводим: `validate()` отвергает неизвестные
значения, поэтому старые клиенты падали бы fail-closed на импорте пакета, а выигрыш информативный. `unverified` —
буквальная правда: человек транскрипт не проверял. Провенанс («ASR по URL, модель, дата, окна, blind-диапазоны»)
пишется в `import_meta` карточки. Действующая политика 3.11.508 (`same-video-default`) даёт работающее караоке без
скрытого утверждения о проверке. R9: derived ≠ asserted.

### 3.4 UI Студии, вкладка «Видео»

Новый блок под полем ссылки: **«Учебный материал из ссылки»**.

1. **«Оценить»** — бесплатный `countTokens`: длительность, число окон, `≈USD 0.XX`. Ключ BYOK, как у всего ASR.
2. Если у ролика есть свои субтитры (существующий путь S5a их уже обнаруживает) — рядом вторая строка
   «Субтитры — бесплатно» и явный выбор. Автовыбор не делается: авто-субтитры на иврите часто хуже.
3. **«Поехали»** — создаётся задача `LearningMaterialTask`, дальше до карточки без вопросов, с resume и «Остановить».
4. Итог показывает: карточка сохранена, «Источник видео» подставлен, сколько строк без надёжной привязки (blind).

Ошибки честные и различимые: «ссылка не принята», «квота исчерпана», «провайдер перегружен — можно продолжить»,
«приватные и unlisted ролики недоступны».

## 3.6 Что изменилось против плана по ходу работы

Три вещи выяснились уже в коде и заслуживают отдельной записи.

**Зонд вместо молчания.** Отгруженный `classifyClockCompression` СОЗНАТЕЛЬНО отказывается судить, когда
окно одно: база из самого подсудимого дала бы отношение 1.0 по построению. Но одно окно — как раз
типичный случай ролика до 26 минут, то есть на самом частом пути гейта не было бы вовсе. У URL-маршрута
есть то, чего у файлового не было: короткое окно вырезается провайдером без скачивания, поэтому вторая
выборка физически независима от первой. `transcribe` по умолчанию докупает **один 90-секундный зонд**
(~4 % стоимости прогона) и сверяет его текст с таймлайном по абсолютному времени. Асимметрия порогов
намеренная: опровергнуть часы хватает 2 якорей, заверить — нужно 3 (R11 do-no-harm). Опровергнутые часы
забирают только метки, текст остаётся весь.

**`fps` работает и без офсетов.** Замер во время реализации: полный ролик 160 681 → 72 073 токена
(−55 %) при `fps: 0.2`, метки не портятся. Поэтому кадры срезаются и на одновызовном пути, а не только
в окнах. `fps: 0.1` дешевле ещё на 7 %, но на качестве меток не мерено и не берётся.

**Дефект, который поймал браузерный гейт (иначе уехал бы на прод).** Добавив `?v=509` к
`learning-material-task*.js` в precache и в `index.html`, я оставил те же файлы в
`SHELL_INTEGRITY_PATHS` сервера без запроса. Ключи перестали совпадать байт в байт, `cache.match(url)`
не находил запись — и **установка Service Worker падала целиком**. Юнит-набор этого не видел: гейт
«cache-busts changed assets exactly» проверяет свой список URL, а не согласованность двух списков.
Нашлось только живой проверкой страницы (`pageerror` при загрузке). Оба списка теперь выровнены, и
`youtube-material-browser-smoke.cjs` держит эту проверку постоянной.

## 3.8 Что вскрыл первый живой прогон владельца (3.11.510)

Первый настоящий прогон в профиле владельца встал на `ASR_BAD_JSON`. Разбор показал две вещи.

**HTTP 200 не значит «транскрипт есть».** Ответ бывает пустым, обрезанным по бюджету вывода
(`finishReason: MAX_TOKENS`) или заблокированным — три разные беды, которые прежний код сваливал в
«плохой JSON»: пользователю не называлась причина, а прогон терял возможность восстановиться.
Теперь `classifyResponse` различает `ASR_EMPTY` / `ASR_TRUNCATED` / `ASR_BLOCKED`.

**Восстановление — тем же приёмом, что у файлового пути.** Непригодный ответ лечится делением
ЗВУКА пополам через `videoMetadata` и швом по ТЕКСТУ, рекурсивно, пока кусок не станет короче
`SPLIT_MIN_SEC`. Отказ провайдера делением не лечится и не переспрашивается.

**Диалог перестал отвечать одной фразой на всё.** Исчерпанная квота, перегруженный провайдер,
отвергнутая ссылка, обрезанный ответ и отсутствующий ключ получили собственные строки в трёх локалях.

Отдельно: ключ владельца в момент прогона был **исчерпан по квоте** (HTTP 429, подтверждено
независимым запросом). Это не дефект маршрута; задача осталась `paused` и возобновляемой, повторной
оплаты распознавания при продолжении не будет.

## 3.9 UX-дефекты первого полного прогона (3.11.511)

Владелец довёл маршрут до конца на своей карточке: материал сохранён, ZIP скачан, **синхронизация
строк с YouTube подтверждена**. Три замечания — все об одном: экран переставал говорить правду
о происходящем.

**Прогресса не было.** Диалог показывал плоский список из четырёх строк, не менявшийся минутами.
Теперь этапы несут собственное состояние (сделано / идёт / ждёт / остановлено) и живую строку под
ними. Что в ней позволено писать — ограничено тем, что известно на самом деле: распознавание
сообщает номер окна и время работы (у одного вызова провайдер доли выполненного не даёт вовсе),
таблица — доказанное покрытие строк, и полоса появляется ТОЛЬКО у неё. Выдуманный процент — то же
враньё, что и подделанная метка, поэтому этап без знаменателя процента не получает.

**Поверх открытого материала оставался модал «Добавить материал».** Правило «один модал владеет
фокусом» в коде уже было — его просто не применили в точке передачи из задачи.

**Посреди прогона выскакивал `window.confirm` со сметой таблицы**, ломая единственное обещание
маршрута. Экран сметы теперь показывает обе цены сразу. Цена таблицы — **вилка**: сколько будет
реплик, до распознавания неизвестно, а отгруженная константа `SEGS_PER_MIN_ASR = 6` откалибрована
на монолог — интервью владельца дало 11.5/мин. Предохранитель сохранён: если счёт перерос
показанный потолок более чем в 1.5 раза, вопрос задаётся.

**Подписи этапов стали существительными:** «Распознаём речь» под галочкой читалось как неправда.

Гейт `youtube-material:e2e` показан **красным на отгруженной сборке** ровно по этим трём дефектам
и зелёным после починки. В него добавлена проверка, что сценарий с оставшимся модалом вообще
воспроизводится: прежний ассерт проходил по случайности — он читал атрибут `.hidden`, которым этот
модал не пользуется (прячется CSS-классом).

## 3.10 Премиальный прогресс и провайдер по умолчанию (3.11.512–513)

Владелец провёл второе тестирование и указал, что знаки без слов неполноценны. Наблюдение за
**пятью настоящими прогонами** (`scripts/premium/youtube-material-observe.cjs`, артефакты в
`docs/research/youtube-gemini-url-asr/2026-09-11/observation/`) дало больше, чем список правок.

**Провайдер по умолчанию.** Настроен ключ Gemini ⇒ таблица строится Gemini. Умолчание НЕ пишется в
хранилище — иначе оно выдало бы себя за явный выбор и не вернулось бы к бесплатному пути после
удаления ключа. Явный выбор владельца неприкосновенен. Решение перенесено в блок ключа: `initProviderSelect`
выполняется раньше, чем существует `geminiKeyGet`, и прежняя проверка молча уходила в ветку «без ключа».

**Дефекты, которые показал только живой прогон:**

1. Этапы рисовались **снимком задачи, взятым до старта** — четыре минуты работы выглядели как
   «остановлено» с пустой строкой. Лечение: перерисовка всегда из самого свежего состояния.
2. Строка повтора брала **терминальную** фразу ошибки и советовала нажать «Продолжить», пока прогон
   продолжался сам. Теперь короткая причина и обратный отсчёт.
3. **Последняя задержка лестницы ретраев была недостижима** — цикл сдавался на шаг раньше. Самая
   длинная пауза, самая полезная при перегрузке, не использовалась никогда; после починки именно
   четвёртая попытка довела ASR до конца.
4. Счётчик кусков называл **первый кусок вторым** (телеметрия уже 1-based).
5. Часы этапа терялись при `startedAt = 0` — falsy-проверка на законной метке.
6. **«Остановить» не работала внутри паузы** между попытками: отмена проверялась только между
   фазами. Теперь её слушают и ожидание, и каждый платный вызов, а остановка по просьбе человека —
   состояние `cancelled` без ошибки, а не провал.

**Что добавлено по существу:** знак **и слово** у каждого этапа; **часы каждого этапа** — живые по
ходу и сохранённые в итоге (из журнала задачи, поэтому переживают перезагрузку и возобновление, а
повтор этапа заводит свои часы); **шкала по законченным окнам** для длинных роликов (внутри окна
доли нет и она не выдумывается); **ожидаемое время** в смете и честное признание «дольше обычного»,
когда прогон его перерос; **перестановка диалога** — имя, цена, действие, и только потом пояснения.

## 3.11 Большой материал владельца: что показал разбор на проде (3.11.514–516)

Материал на 637 реплик (ролик 47:14, часы `verified`) не собирался. Разбор по сетевым телам и
сохранённым сырым ответам провайдера дал четыре разных причины — ни одна не была видна из кода.

**1. Согласованная цена терялась при возобновлении.** Она жила в переменной страницы, поэтому
возобновлённый прогон спрашивал заново, а закрытый вопрос оставлял пустую таблицу и безликое
`TASK_TABLE_INCOMPLETE`. Цена переехала в журнал задачи; гейт `youtube-material:e2e` возобновляет
прогон через стадию таблицы и падает, если что-то спрашивается повторно.

**2. ASCII-кавычка в реплике обрезала эхо модели.** Реплика `בגיל 23 טסתי לחו"ל…` вернулась с
полем `he`, оборванным ровно на кавычке, при полной и корректной огласовке (с ивритским гершаим).
Валидатор сравнил целую огласовку с обрезанным источником и обвинил огласовку. Глубинная причина:
в сегментном режиме текст строки брался **из эха модели**, то есть наш собственный текст был
надёжен ровно настолько, насколько модель умеет его повторить. Теперь сегменты запроса доходят до
подготовки строк, и если эхо оказалось **префиксом** нашего текста — берётся наш. Любое другое
расхождение не трогаем: оно может означать сбитое соответствие строк.

**3. Модель правит источник при огласовке — и это НЕ дефект валидатора.** В куске 2 шесть строк из
120: `מעשר` → `מעשרת` (добавлена буква), `30 ס"מ` → `30 סנטימטר` (развёрнута аббревиатура).
Сервер честно чинит такие строки дважды и останавливается с «нужен человек». Решение, что делать
дальше, — продуктовое, и вынесено владельцу: пропускать огласовку у таких строк с явной пометкой,
увеличить число попыток починки, либо править источник вручную.

**4. Chrome замораживает фоновую вкладку** — длинный прогон умирает вместе с висящим запросом
(опрос `/api/usage` встал, POST так и не получил статус). Пока идёт сборка таблицы, вкладка должна
быть активной; это ограничение браузера, и его следует написать в диалоге прямо.

Отдельно, инфраструктура: диск прода снова заполнился до нуля (темп релизов этой сессии), из-за
чего **Redis перешёл в MISCONF и запретил записи**, а очередь Coolify встала — это и есть источник
«500 Wait, this is not cool…». Освобождение диска само по себе очередь не лечит: зависший деплой
пришлось добить Force Start.

## 4. Границы

Не входит: изменение плеера и двусторонней синхронизации; смена провайдера таблицы по умолчанию; скачивание YouTube
на сервер; обход ограничений встраивания; массовая перепривязка существующих карточек; публикация; изменения SRS,
`review_log` и морфологии; расширенный пилот на 6 роликах (владелец принял включение на измеренном одном ролике —
отдельная задача при желании).

## 4.1 Открытый пункт: локальный файл к карточке, у которой его никогда не было

Владелец описал желаемый итог так: «если пользователь скачает полное медиа из этой ссылки, у него
есть возможность подключить его в Импорт-центре, чтобы выбирать воспроизведение локально или через
YouTube». **Сегодня такой возможности нет, и эта работа её не добавляет.**

Проверено по коду, а не по плану: `importCenterCore.mediaState` для карточки с YouTube-привязкой
возвращает `external`, поэтому маршрут никогда не доходит до `needs-media` → `relink-media`. Сам
`relink-media` чинит **точную** привязку — он требует уже известного `media_expected_sha256`, то
есть файла, который у карточки когда-то был. Материал, созданный из ссылки, локального медиа не
имел никогда, и подставить ему произвольный файл нечему.

Это не упущение, а следствие сознательного решения: свободную («ambient») привязку медиа к чужой
карточке из продукта убирали намеренно (провенанс-инцидент 2026-08-06), заменив её точной. Вернуть
её «по-быстрому» нельзя, а честная версия упирается в вопрос, который канон уже сформулировал:
**совпадение названия и длительности не доказывает, что это та же запись** (см.
`YOUTUBE_SYNC_EXISTING_AND_NEW_TABLES_2026_09_10.md`). Нужен явный дизайн: чем доказывается
тождество скачанного файла и ролика, что делать при другом монтаже, и как показать пользователю
разницу между «тот же ролик» и «похожий». Предлагается отдельной задачей; здесь она не начата.

До неё материал из ссылки играет через YouTube — то есть основной сценарий владельца закрыт, а
офлайн-вариант для таких карточек остаётся недоступным.

## 5. Разбор по ролям

| Роли | Проверка |
|---|---|
| R4 | Один экран сметы — единственная остановка; ошибки называют причину, тупиков нет |
| R5 | Мобильный путь без скачивания вообще; локальный файл остаётся опциональным офлайн-вариантом |

## 6. Риски

| Риск | Ответ |
|---|---|
| 503/429 провайдера (утопили прошлый пилот) | Backoff + resume; «перегружен» показывается как продолжаемое состояние, не как провал |
| Ролик запрещает встраивание (ошибка 150/153) | Транскрипт и таблица всё равно готовы; экран честно предлагает открыть YouTube отдельно |

| Часы «поехали» внутри окна | Существующий `classifyClockCompression` → переспрос → `blind`, караоке молчит честно |
| Права на расшифровку | Встраивание их не даёт; публикация остаётся отдельным явным действием владельца |

## 7. Долгая сборка: падение не должно стоить нового прогона (v3.11.518)

Владелец после первого 47-минутного материала: «сделай, чтобы падение в середине длинной сборки
не стоило нового прогона» и «вкладка должна быть на переднем плане — учти это требование».
Ниже — что измерено и что из этого следует.

### 7.1 Измерения на машине владельца (2026-09-11)

| Что измерено | Результат |
|---|---|
| `localStorage` вкладки | **10 239 КБ в 142 ключах**; пробная запись 120 КБ → `QuotaExceededError` |
| Кто занял место | `ttsDashboard_v3_library_cache_v1:*` — 8 верхних ключей ≈ 7,8 МБ (1897/1885/1516/814 КБ …) |
| Журнал кусков таблицы | **OPFS** `recovery/studio-table-job-v1.json`, 595 КБ, `state: done`, 6 из 6 — переполнение его НЕ трогало |
| Куски последнего прогона | `fromCache: true, true, false, false, false, false` — первые два спас СЕРВЕРНЫЙ кеш, а не журнал |

Отсюда две поправки к прежнему диагнозу. Кеш библиотеки ломает **не себя, а всех остальных
писателей** в `localStorage`, и молча (пустой `catch`). А журнал в тот раз **не подошёл** —
возобновление прошло куски заново, и на экране это было неотличимо от обычного старта.

### 7.2 Что сделано

- **`public/js/local-cache-budget.js`** — бюджет для кеша в `localStorage`: 6 записей / 1,5 M
  символов (≈30 % потолка Chrome), вытеснение «сначала неизвестного возраста, потом самые старые»,
  на `QuotaExceededError` освобождается ТОЛЬКО свой префикс, отказ возвращается именованным
  (`ENTRY_TOO_LARGE` / `QUOTA_EXCEEDED`), а не глотается. `prune()` на загрузке лечит браузер,
  выросший до появления бюджета.
- **`TableJob.diagnose(journal, input)`** — вердикт возобновления: `resumable` с номером куска либо
  причина (`NO_JOURNAL` / `SIGNATURE_MISMATCH` + ЧТО изменилось / `BROKEN_CHAIN`). Журнал теперь
  хранит отпечаток каждого поля (`fields`), старый журнал честно отвечает «неизвестно».
  Диалог задачи говорит «Продолжено с куска N из M» либо «журнал не подошёл (изменился текст)».
- **`public/js/chunk-retry.js`** — лестница повторов куска таблицы вместо двух попыток подряд:
  503/сеть — 4/12/30 с (полная лестница), обычная 500 — один повтор, но и он ждёт, 429/401/403 и
  `retryable:false` не повторяются вовсе, повреждённый JSON лечится дроблением, а не ожиданием.
  Каждая попытка — оплаченный вызов, поэтому бюджет у каждого класса свой.
- **Замороженная фоновая вкладка названа своим именем.** `createTabWatch` помнит, была ли вкладка
  скрыта во время запроса; такой обрыв классифицируется как `TAB_BACKGROUNDED`, и продолжение
  ждёт НЕ часов, а возвращения на передний план (`waitForForeground`). Экран говорит
  «вкладка была в фоне · вернитесь в неё, продолжу сам».
- **Требование среды объявляется до трат**: в смете длинной (многокусковой) сборки появляется
  строка «Держите эту вкладку на переднем плане… готовые куски сохраняются — переплаты не будет».

### 7.3 Чем это доказано

- `tests/chunkRetry.test.js` (9) — классы отказов, достижимость последней ступени, бюджет 500,

### 7.4 A и D (v3.11.519)

Два пункта из прежнего списка предложений, отложенные владельцем и теперь взятые в работу.

- **A — готовность видна, когда на вкладку не смотрят.** Терминальное состояние прогона
  объявляется в заголовке вкладки: «✅ Материал готов · <прежний заголовок>» либо
  «⚠️ Прогон остановлен · …». Заголовок — чужая собственность, поэтому правило жёсткое: трогаем
  его ТОЛЬКО пока вкладка скрыта, объявляем один раз и возвращаем прежний, как только человек
  вернулся (`titleNotice` / `applyTitleNotice`; слушатель `visibilitychange` снимает себя сам).
- **D — «Продолжить» больше не выглядит как «заплатить снова».** У возобновляемой задачи, где
  транскрипт уже есть, диалог говорит: «Распознавание уже оплачено и сохранено — при продолжении
  оно не повторяется». Готовый материал об этом молчит: там нечего возобновлять.

Доказано: `tests/learningMaterialTaskUi.test.js` (+5, включая три локали) и три проверки в
`smoke:youtube-material:e2e` (30/30) — строка об оплате видна в живом диалоге, скрытая вкладка
узнаёт о готовности, а вернувшийся человек получает свой заголовок нетронутым.
