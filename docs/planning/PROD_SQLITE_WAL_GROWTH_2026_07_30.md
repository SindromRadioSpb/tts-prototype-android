# Прод: SQLite WAL удерживал high-water mark 261 МБ — закрытый тикет

**Дата находки:** 2026-07-30 (сессия S12.5, попутно при разборе диска прода).
**Статус:** ЗАКРЫТ 2026-07-30. Прод remediation выполнен без рестарта: verified
`db:backup` → `wal_checkpoint(TRUNCATE)` → WAL 0 байт, health green. Постоянный фикс
v3.11.269: `PRAGMA journal_size_limit=16777216` на основном connection.
**Итоговый диагноз:** физический размер WAL был сохранённым high-water mark, а не
доказанным backlog в 64 000 активных frames. Авточекпоинт работал; отсутствовал лимит
усечения (`journal_size_limit=-1`).

## Диагностика и закрытие (2026-07-30 12:32–12:40 UTC)

⚠ До первой диагностической PRAGMA внешний docs-only push уже запустил новый контейнер
(revision `3c9ec0c2`, v3.11.268, start 12:32:04 UTC). Поэтому состояние прежнего
connection было утрачено не этой диагностикой, и утверждать, что ДО рестарта не было
долгого читателя, нельзя. Ниже — доказанное состояние после рестарта.

- `PRAGMA wal_checkpoint(PASSIVE)` → `(busy=0, log=291, checkpointed=291)`: все
  активные frames успешно перенесены, checkpoint не блокирован.
- `lsof app.db*` → один Node PID; повторяющиеся строки были threads того же PID,
  второго процесса/контейнера не было.
- Код-аудит не нашёл explicit read transaction (`BEGIN DEFERRED`/голый `BEGIN`):
  явные транзакции в `db/` — bounded `BEGIN IMMEDIATE` writer-секции с
  `COMMIT`/`ROLLBACK`. `keyingService` прямо не касается DB; его idle sweeper
  выгружает только in-memory resolver bundle.
- PRAGMA: `journal_mode=wal`, `wal_autocheckpoint=1000`, `page_size=4096`,
  `journal_size_limit=-1`. Основной app connection также задавал
  `busy_timeout=5000` в `db/sqlite.js`.
- При этом физический `app.db-wal` оставался ровно 261 574 712 байт. Это нормальная
  семантика reuse WAL: PASSIVE checkpoint переносит frames, но не обязан уменьшать
  уже выделенный файл; следующий цикл пишет с начала.
- Перед записью создан `/app/data/backups/app.2026-07-30T12-39-11.pre-wal-truncate-20260730.db`
  вместе с sidecars; независимое открытие копии дало `PRAGMA integrity_check=ok`.
- `PRAGMA wal_checkpoint(TRUNCATE)` → `(0,0,0)`; live WAL стал 0 байт. DB/migrations
  остались green, restart не выполнялся.
- Диск после операции 90%, а не ниже исходных 89%: verified backup добавил около
  626 МБ, truncation освободил около 261 МБ. Backup намеренно сохранён.

### Постоянное исправление

`db/sqlite.js` теперь задаёт `journal_size_limit=16 MiB` при открытии connection.
Штатный `wal_autocheckpoint=1000` не меняется. Лимит в четыре раза больше обычной
checkpoint-порции, поэтому не создаёт постоянный resize churn, но не позволяет
одному большому burst навсегда закрепить сотни мегабайт в каждом volume backup.
Периодический `TRUNCATE` не добавлен: он может ждать readers/writers и не нужен при
работающем autocheckpoint + bounded high-water mark.

Тест: `tests/sqliteWalPolicy.test.js` проверяет WAL mode, autocheckpoint=1000 и
лимит 16 MiB на реально открытой временной SQLite.

### Отдельный хвост: формат ежедневного бэкапа

`/opt/backup-linguistpro.sh` всё ещё делает `tar` горячего volume целиком. На
2026-07-30 есть 15 свежих архивов общей массой 9.3 ГБ; последний — 661 МБ.
Скрипт в этой сессии НЕ менялся. Переход на SQLite Online Backup API (`.backup`)
или `VACUUM INTO` следует делать отдельным bounded ops-слайсом: записать скрипт →
`bash -n` → реальный прогон → `integrity_check` восстановленной копии → freshness
следующего cron-артефакта. До такого доказательства hot-tar нельзя молча заменить.

## Исходная находка и гипотеза (формулировка владельца, 2026-07-30)

Ниже сохранена исходная формулировка как audit trail. Вывод «размер файла = число
активных frames» позднее опровергнут прямой PRAGMA-диагностикой выше.

> Внутри каждого архива лежит `app.db-wal` на 261 МБ при самой базе в 354 МБ. На живом томе
> он такой же и продолжает расти. WAL нормально не превышает нескольких мегабайт — SQLite
> чекпоинтит его автоматически; 261 МБ означает, что чекпоинт не проходит (обычно из-за
> долгоживущего читателя, который держит снимок). Практические следствия: этот баласт тащится
> в каждый из двадцати бэкапов, а на томе он лежит третьим по величине файлом. Если чекпоинт
> не восстановится, WAL будет расти дальше и однажды сам добьёт диск — тогда 100% вернётся
> независимо от образов и бэкапов. Разбираться с этим лучше не сейчас, а когда закончите
> приёмку: нужно посмотреть, кто держит соединение, и прогнать `wal_checkpoint(TRUNCATE)`
> в спокойный момент.

```
app.db-wal   261 574 712  (261 МБ)  2026-07-29 22:25   ← растёт
app.db-shm        32 768              2026-07-29 22:25
```

- В бэкапе `app-data-20260729-0300.tar.gz` тот же WAL 261 574 712 — то есть балласт лежит
  в КАЖДОМ из ежедневных архивов (сейчас их 15).
- Норма для авточекпоинта SQLite — ~1000 страниц (≈4 МБ). Арифметически файл 261 МБ
  вмещает ≈64 000 frames, но его физический размер не доказывает, что столько frames
  сейчас активно: полностью checkpointed WAL может сохранять прежний allocation для reuse.
- Наблюдение по датам: `app.db` в архиве от 29-го имел mtime 2026-07-28 20:36 — сам файл базы
  почти сутки не переписывался. Это было совместимо с гипотезой блокировки, но без
  одновременной тройки PASSIVE не являлось достаточным доказательством.

## Почему это важнее разовой чистки диска

Диск прода в тот день был 100% (деплой S12.5 не собирался). Разобрали на три части:
build-кэш ~3.2 ГБ (вычищен), старая сборка ~3 ГБ (освободилась при деплое), внеплановые
бэкапы 3.3 ГБ (удалены) → 75%, `disk_warn:false`. WAL оказался не доказанным бесконечным
backlog, а неограниченным high-water mark. Практический ущерб всё равно был реальным:
каждый ежедневный hot-tar тащил лишние 261 МБ, пока файл не был усечён и bounded policy
не была закреплена.

## Исходные гипотезы причины (проверены в указанном порядке)

1. **Долгоживущий читатель держит snapshot** — не доказано: pre-restart улика утрачена;
   после рестарта PASSIVE был полностью успешен. Открытая read-транзакция не
   даёт чекпоинту перезаписать WAL с начала. Кандидаты в проекте: keyingService
   (`KEYING_IDLE_UNLOAD_MS`), фоновые задачи CLG/агента, healthz/миграционные соединения,
   долгий стрим-запрос.
2. **`wal_autocheckpoint` отключён/переопределён** — опровергнуто (`1000`); часть про
   **`journal_size_limit` не задан** — подтверждена (`-1`) и исправлена.
3. **Постоянный busy** — опровергнуто для доступного post-restart состояния:
   PASSIVE вернул `busy=0` и перенёс все активные frames.

## План диагностики (когда будет спокойное окно)

1. Не рестартить приложение до снятия улик — рестарт «вылечит» симптом и уничтожит причину.
2. На проде: `PRAGMA wal_checkpoint(PASSIVE)` и посмотреть возвращаемую тройку
   `(busy, log, checkpointed)` — она прямо скажет, блокирован ли чекпоинт и сколько страниц
   не перенесено.
3. Посмотреть, кто держит соединения: список процессов/хэндлов на `app.db*`
   (`sudo lsof | grep app.db`), длительность живых соединений приложения.
4. Проверить в коде: где открывается БД, какие PRAGMA ставятся (`journal_mode`,
   `wal_autocheckpoint`, `journal_size_limit`, `busy_timeout`), нет ли соединения, которое
   открывает читающую транзакцию и не закрывает её.
5. Только после этого — `PRAGMA wal_checkpoint(TRUNCATE)` в момент низкой нагрузки
   (усечёт файл до нуля). Сделать `db:backup` ДО.
6. Закрепить результат: явный `journal_size_limit` + периодический TRUNCATE-чекпоинт (или
   исправление долгоживущего читателя), чтобы файл не отрастал заново.

## Побочные улучшения, всплывшие рядом (по желанию владельца)

- **Бэкап копирует горячую БД** (`tar` по тому, включая `-wal`/`-shm`). Восстановление
  сработает (SQLite применит WAL), но снимок не гарантированно согласован. Правильнее —
  `sqlite3 app.db ".backup"` или `VACUUM INTO` в бэкап-скрипте: получится один файл, без WAL,
  меньше по размеру и консистентный по построению.
- Ротация 14 дней исправна (`find -mtime +14 -delete`), трогать не нужно.
