# Локальное выравнивание строк по звуку (forced alignment)

Дата: 2026-09-18. Основание: решение владельца после волны 3.11.589–596, где выяснилось,
что метки языковой модели дрейфуют и проверяемы только постфактум. Предшественники:
`YOUTUBE_TIMING_PROBE_VETO_FIX_2026_09_18.md`, `YOUTUBE_TIMING_PER_WINDOW_VERDICT_2026_09_18.md`.
Статус: **PROPOSAL, ничего не реализовано.** Пакет написан, чтобы начать в новой сессии.

## Зачем

Сейчас время строк берётся из меток, которые модель **сочиняет как текст**. Измерено на
материале владельца: внутри одного окна распознавания отставание нарастает 9 с → 15 с → 27 с.
Это свойство генерации, а не промпта. Вся машинерия зондов, кворума, пооконных вердиктов и
смет существует только потому, что такие метки нельзя принять без проверки.

Forced alignment меняет природу величины: текст ИЗВЕСТЕН (мы за него уже заплатили), а время
ищется в самом сигнале. Путь по кадрам идёт только вперёд, поэтому монотонность гарантирована
по построению; время строки — это номер кадра в буфере, поэтому терять внутренние часы нечему,
и ошибка ограничена длиной кадра (десятки мс), а не длительностью записи.

Чего оно НЕ делает: не исправляет ошибки расшифровки. Выравниватель размещает во времени тот
текст, который ему дали. «Правильно расслышать» и «правильно разместить» — разные работы, и
главный вывод волны 589–596 в том, что смешивать их в одной модели не следует.

## Решения владельца (2026-09-18)

1. **Модель — та же, что уже в компаньоне.** Никаких новых моделей ради эксперимента.
2. **Считаем на машине владельца.** Требуется подтвердить выигрыш по скорости и цене.
3. **Результат входит в карточку через отказоустойчивый путь.**
4. Субтитры YouTube как источник времени — **отклонены** (в этой ветке с ними не работаем).

## 1. Модель: что реально стоит

`ai-local/` — это и есть ASR-компаньон (сервис `linguistpro-media-acquisition` к ASR
отношения не имеет: его единственная зависимость — `yt-dlp`, он добывает медиа).

| что | значение |
|---|---|
| модель ASR | `ivrit-ai/whisper-large-v3-turbo-ct2`, пин по ревизии |
| лицензия | Apache-2.0, установка с явным принятием лицензии |
| рантайм | `faster-whisper==1.1.1`, `ctranslate2==4.5.0`, `torch==2.5.1` |
| сервис | FastAPI, эндпоинты `/v1/asr/...`, на машине владельца |
| режим | локальные открытые веса, НЕ хостинговый API ivrit.ai — бесплатно |

Владелец указал на ivrit.ai верно: это их модель, но используется как открытые веса локально.

### Два маршрута, и их надо различать

- **Маршрут A — пословные метки faster-whisper (`word_timestamps=True`).** Использует ровно
  то, что уже установлено и пролицензировано. Время выводится из аудио (DTW по cross-attention),
  но модель при этом ПЕРЕ-расшифровывает: это не forced alignment в строгом смысле, и известная
  слабость — границы у пауз, музыки и наложенной речи.
- **Маршрут B — настоящее CTC-выравнивание** (`torchaudio.functional.forced_align` + ивритская
  акустическая CTC-модель). Текст зафиксирован, модель выбирает только «когда». Даёт покадровую
  точность и честную уверенность на слово. Цена: новая модель, новая лицензия, `torchaudio`
  в зависимостях, requalification рантайма (в `ai-local` идентичность рантайма закреплена).

**Рекомендация: начать с A и ИЗМЕРИТЬ.** Маршрут B держать как запасной, если точность A не
устроит. Не начинать с B из эстетических соображений: он дороже во всём, а разница может
оказаться несущественной для построчной подсветки.

## 2. Где считать: машина владельца против сервера

| | машина владельца | production-сервер |
|---|---|---|
| CPU | Ryzen 5 5600G, 6 ядер / 12 потоков | 2 vCPU Xeon Skylake |
| RAM | 32 ГБ | 3 ГБ всего, ~2 ГБ доступно |
| GPU | **RTX 3070, 8 ГБ VRAM**, драйвер 595.79 | нет |
| нагрузка | простаивает | несёт сайт, Postgres, Coolify, Traefik |
| диск | свободен | 2026-09-18 был забит на 100%, сейчас 75% |

**Вывод: считать на машине владельца, и это не близкий выбор.**

- На RTX 3070 с CT2/float16 large-v3-turbo идёт ориентировочно 30–60× реального времени: час
  записи ≈ 1–2 минуты.
- На сервере: 2 ядра Skylake без GPU, int8 — ориентировочно 0.5–1.5× реального времени, то есть
  час записи ≈ 40–120 минут, при этом модель требует ~1.5–2 ГБ RAM из ~2 доступных и будет
  конкурировать с сайтом. Практически это означает деградацию продакшена ради фоновой задачи.
- **Дешевле** тоже локально: GPU уже куплен и простаивает, а GPU-хостинг — это новая
  ежемесячная статья расходов. Плата провайдеру за тайминг исчезает полностью.

⚠️ Числа пропускной способности выше — типовые, **не замеры на этом железе**. Первая же задача
пакета обязана их измерить, а не унаследовать.

## 3. Как результат входит в карточку

Новых поверхностей не заводим: требование владельца — низкий порог входа, обучение по карточке,
а не обслуживание карточки. Точка входа — уже существующий диалог «Восстановить синхронизацию»,
новый способ рядом с прочими.

### Канал записи

Переиспользуем весь построенный путь, ничего не изобретая:

- `commitTimingRepair` — атомарная ревизия ТОЛЬКО тайминга + привязка + паспорт.
- Гард `TIMING_REPAIR_TEXT_CHANGED` остаётся: выравнивание не вправе тронуть ни одну строку текста.
- `authority.timing` получает новое значение — `aligned-local`. Это честное авторство: время
  измерено локальным выравнивателем, а не заявлено провайдером и не введено человеком.
- Построчная честность как везде: строка с низкой уверенностью остаётся БЕЗ кнопки. Молчащая
  строка честнее подсветки, которая врёт.
- `mergeRecovered` не стирает уже работающие интервалы.

### Отказоустойчивость

Уроки этой волны переносятся сюда целиком:

1. **Журнал по ключу ИСТОЧНИКА**, не ревизии: `text_id + ':align:' + media_sha256`. Ключ с
   `revision_id` уже приводил к храповику, который умеет только терять
   (см. `feedback-paid-evidence-outlives-artifact`).
2. **Паспорт обязан пронести доказательства** через фиксацию: сырой выход выравнивателя
   сохраняется, повтор не пересчитывает уже посчитанное.
3. **Чанки с журналом до работы, а не после.** Каждый кусок записывается в журнал перед
   вычислением; падение/закрытие ноутбука продолжается с места, а не с нуля.
4. **Компаньон офлайн, модель не установлена, GPU занят** — это НАЗВАННЫЕ состояния с честным
   текстом. Никакого молчаливого отката на метки языковой модели: подмена измерения оценкой —
   ровно тот дефект, который мы всю ночь чинили.
5. **Медиа отсутствует локально** — состояние, а не ошибка. Добыча идёт через существующий
   `media-acquisition` (yt-dlp), это уже поддержанный путь.
6. Идемпотентность: повторный запуск на неизменившихся (медиа, текст) не тратит вычислений и
   не создаёт новой ревизии, если результат тот же.

## План работ

**T1. Замер точности на ГОТОВОЙ карточке с эталоном.** У нас есть редкая вещь — карточка
`V2hPVipyWN0`, где часы заверены сквозной проверкой при расхождении 0 с и 983/990 строк играют.
Это эталон. Выровнять тот же ролик локально и сравнить пословные границы с сохранёнными
интервалами: распределение ошибки, доля строк вне допуска, поведение на паузах и музыке.
Замерить заодно реальную пропускную способность на RTX 3070 и на CPU этой же машины.
**Это единственная задача, которая отвечает на вопрос «стоит ли вообще» — и она дешёвая.**

**T2. Решение по маршруту.** По числам T1: хватает ли A, или нужен B. Если B — отдельный
пакет на модель, лицензию и requalification рантайма `ai-local`.

**T3. Контракт эндпоинта.** `/v1/align` в компаньоне: вход — медиа + известные строки, выход —
на строку: начало, конец, уверенность. Чанкование и возобновление внутри.

**T4. Клиентский путь.** Новый способ в диалоге ремонта, состояния из раздела «отказоустойчивость»,
запись через `commitTimingRepair` с `authority.timing = 'aligned-local'`.

**T5. Гейты.** Расширить `scripts/youtube-timing-repair-smoke.cjs` режимом `--align`: медиа есть,
медиа нет, компаньон офлайн, прерывание на середине с продолжением, уверенность ниже порога.
Плюс проверка, что текст не изменился ни в одном сценарии.

## Что НЕ входит

- Замена существующего пути YouTube-ASR. Он остаётся для материалов без локального медиа.
- Субтитры YouTube (отклонено владельцем).
- Точечное выравнивание одного сбойного окна через `youtube-full-timing` — отдельная тема,
  всплывшая в этой же волне и не закрытая.

## Открытые вопросы к началу работ

1. Совпадает ли пословный выход faster-whisper со строками таблицы по тексту достаточно, чтобы
   маппить без повторного сегментирования? В проекте уже есть `alignRowsToSegments` по тексту —
   вероятно, переиспользуется.
2. Порог уверенности, ниже которого строка остаётся без кнопки. Назначается по данным T1,
   не «на глаз».
3. Нужен ли отдельный контроль дрейфа после выравнивания. Вероятно нет: монотонность даётся
   по построению. Проверить на данных T1, а не предполагать.
