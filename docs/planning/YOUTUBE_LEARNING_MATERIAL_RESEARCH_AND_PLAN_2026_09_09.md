## 1. Рекомендация

Сделать **учебный материал с выбором источника воспроизведения**: YouTube онлайн, локальный файл офлайн или оба варианта. Таблица, субтитры и их редакции принадлежат материалу; видео может воспроизводиться непосредственно с YouTube, не занимая диск сервера LinguistPro.

Стандартный встроенный YouTube-плеер подходит для этого без подписки YouTube Premium и без отдельной платной интеграции с YouTube. Это штатный механизм embedding. Для его подключения по известному video ID не нужен YouTube Data API key или OAuth. Подписка на специальные образовательные продукты YouTube для предложенного решения не нужна. [Официальная справка по embedding](https://support.google.com/youtube/answer/171780?hl=en), [Developer Policies: IFrame API без авторизации](https://developers.google.com/youtube/terms/developer-policies).

Рекомендуемая последовательность:

1. Сохранить и переносить YouTube-привязку у готовых карточек; переиспользовать уже существующее караоке.
2. Проверить и реализовать полноценный экран «видео + таблица» на iPhone.
3. Объединить импорт, обработку, сохранение и экспорт в одну возобновляемую задачу.
4. Добавить прямое получение черновика через Gemini по YouTube URL как дополнительный проверяемый маршрут.
5. После личного сценария добавить публикацию лёгких материалов и корпусов без оригинальных медиабайтов.

**Основной выигрыш доступен даже без нового ASR:** однажды полученные текст и таймкоды можно использовать с YouTube при дальнейшем обучении и распространении. Скачанное медиа нужно только там, где требуется локальная обработка, офлайн-видео или независимый архив.

## 3. Возможности и ограничения внешних платформ

### 3.1 Встроенное видео и синхронизация

IFrame Player API предоставляет часы, события состояния, паузу и переход ко времени. Это позволяет подсвечивать строку по времени ролика и переводить ролик к строке. Переход асинхронный и может начинаться с ближайшего ключевого кадра; покадровую точность обещать нельзя. Минимальная область плеера — 200 × 200 px, включая мобильный дизайн. [IFrame API](https://developers.google.com/youtube/iframe_api_reference).

Для реализации: видимый штатный плеер, начало по действию пользователя, сохранённые YouTube controls и branding. Не проектировать извлечение аудиопотока, скрытый аудиоплеер или подавление рекламы. [Developer Policies](https://developers.google.com/youtube/terms/developer-policies), [Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality).

Встраивание может быть запрещено автором; существуют возрастные ограничения. Отсутствие HTTP Referer вызывает ошибку 153. `youtube-nocookie.com` даёт privacy-enhanced режим, но не гарантию отсутствия внешних запросов или рекламы. [Справка YouTube](https://support.google.com/youtube/answer/171780?hl=en).

Практический вывод: ZIP с YouTube-ссылкой сохраняет учебный материал, но не гарантирует вечную доступность видео. Для библиотеки важны два отдельных признака: целостность таблицы и текущая доступность внешнего ролика. Удаление ролика не должно ломать открытие текста.

### 3.2 Откуда получить субтитры

Официальный `captions.list` возвращает описание дорожек, а не их текст. `captions.download` требует авторизации и разрешения редактировать видео. Поэтому универсальная кнопка «скачать субтитры любого чужого ролика через официальный бесплатный API» на этом механизме не строится. [Captions list](https://developers.google.com/youtube/v3/docs/captions/list), [Captions download](https://developers.google.com/youtube/v3/docs/captions/download).

В IFrame API документированы настройки отображения captions, а не публичный экспорт транскрипта. Используемый сейчас `getOption('captions','tracklist')` не считать надёжным контрактом наличия текста: пустой ответ означает «не удалось определить», а не «субтитров нет». [IFrame API](https://developers.google.com/youtube/iframe_api_reference).

Разделять четыре происхождения: авторские субтитры, автоматические субтитры YouTube, собственный ASR, ручная правка. И авторские субтитры могут иметь ошибки или иной монтаж; монотонность меток не доказывает точность речи.

### 3.3 Gemini непосредственно по YouTube URL

Официальная документация описывает передачу публичного YouTube URL как видео-входа. На дату проверки функция обозначена preview без отдельной платы; указано ограничение free tier — 8 часов YouTube в день, private/unlisted не поддерживаются. Условия могут меняться. [Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding).

Это **кандидат на устранение скачивания и повторной загрузки файла**, но не доказательство качества транскрипта или синхронизации. Встраивание бесплатно независимо от того, каким способом создавалась таблица; расходы модели, переводчика и TTS нужно считать отдельно по выбранному тарифу. [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing).

Перед реализацией проверить именно используемый endpoint/модель и структурированный video input; простая текстовая вставка URL в ASR-промпт не эквивалентна обработке видео. Документация также описывает clipping через параметры обработки, но это не доказательство работы комбинации clipping + YouTube URL на текущем провайдере. Старый range-промпт не возвращать. [Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding).

### 3.4 Почему отдельная задача для iPhone

COEP применяется рекурсивно к вложенным документам; iframe credentialless позволяет исключение, но имеет ограниченную совместимость. Промежуточный обычный iframe под изолированной страницей сам по себе проблему не решает. [MDN: iframe credentialless](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/IFrame_credentialless).

В репозитории изоляция нужна SQLite/OPFS. Нельзя глобально снять COEP ради ролика. Требуется проверяемая архитектура разделения хранения и воспроизведения, описанная в разделе 6.

Браузерное расширение для переноса доступной расшифровки — возможный более поздний вариант для ПК. Оно требует отдельной установки, разрешений и сопровождения интерфейса YouTube, не решает iPhone целиком. Не ставить его раньше объединения уже существующих шагов.

## 5. Целевой пользовательский процесс

### 5.1 Новый материал

1. «Добавить материал → Видео»: вставить ссылку. Приложение сохраняет нормализованный video ID и предлагает «С субтитрами», «Распознать по ссылке» после квалификации B, «Использовать файл».
2. Выбрать профиль один раз: язык, провайдер таблицы, получение транскрипта, бюджет/лимит, «показывать проверку текста» или «продолжать после успешных проверок». Перед запуском понятно, что отправляется провайдеру.
3. «Подготовить материал»: получить/принять текст → проверить покрытие и тайминг → сформировать таблицу → сохранить новую карточку. При явной ошибке или неоднозначной привязке остановиться на конкретном действии, сохранив результат предыдущих этапов.
4. Экран готового материала: «Учиться», «Проверить текст», «Сохранить/отправить пакет». Системный выбор места или получателя остаётся действием пользователя.

Цель — убрать технические переходы через поле Студии, ручное «Обновить таблицу», отдельное сохранение и повторный поиск в Импорт-Центре. Редактор остаётся доступным по необходимости. Целевое число основных решений — 3–4 вместо семи раздельных этапов; это целевой UX, пока не измеренный результат.

### 5.2 Уже готовая карточка

«Источник видео → Подключить YouTube» → вставить ссылку → предпросмотр привязки → сохранить новую редакцию привязки.

- Имеется точная исходная YouTube-ссылка и надёжные метки: переиспользовать их, проверить начало/середину/конец.
- Имеется локальный файл, исходная ссылка потеряна: пользователь указывает ролик; совпадение имени/длительности лишь подсказка. Не связывать автоматически по названию.
- Файл обрезан или отличается вступлением: отдельная привязка часов; постоянный offset применять только после подтверждения и нескольких контрольных точек. Формула: `youtube_ms = source_ms + offset_ms`. При разных монтажах одного offset недостаточно.
- Есть только таблица без тайминга: видео можно прикрепить сразу; синхронизация получает статус «нет проверенных меток». Для караоке нужны субтитры/выравнивание, а не распределение строк равномерно по длительности.

Существующую таблицу, правки и учебный прогресс не перегенерировать при смене способа воспроизведения. Локальное медиа не удалять автоматически. Групповая обработка старых материалов — только preview со списком однозначных и спорных кандидатов, затем выбранный владельцем набор.

### 5.3 ПК и iPhone с локальным медиа

На ПК объединить выбор файла, проверку совместимости и запуск выбранного ASR в одну задачу. Совместимый файл не перекодировать; результат проверки кешировать по SHA + версии профиля совместимости. Один раз сохранить blob и переиспользовать в распознавании и просмотре.

Для iPhone сохранить существующий helper: его отчёт об успехе ещё не означает, что браузер получил File. Возврат должен вести прямо к ожидающей задаче и выбору сохранённого файла, а затем продолжать настроенную цепочку. Автоматическую передачу байтов из a-Shell в браузер не обещать без отдельной проверки системных возможностей. YouTube-воспроизведение позволит не переносить этот файл далее вместе с карточкой.

## 6. Предлагаемая архитектура

### 6.1 Один материал, отдельные источники и часы

Минимальная логическая модель, имена полей до реализации уточняются по схемам:

```text
material → выбранная редакция таблицы → стабильные строки
        → выбранная редакция субтитров → cue IDs и интервалы
        → playback source binding
             YouTube: video ID, canonical URL, source revision, offset, verification
             local: SHA-256, MIME, duration, compatibility, local availability
```

Нужен один канонический источник привязки; `audio.video` для старых потребителей строить как проекцию. Не вести две независимые редактируемые ссылки в паспорте и `external_ref_json`. Конкретный владелец записи выбирается после проверки всех import/save/export/publication consumers.

YouTube ID — идентичность внешнего ресурса, не хеш неизменных медиабайтов. Локальный SHA сохраняет своё назначение. Нельзя «успешно relink по SHA» подменять введённой YouTube-ссылкой. После изменения монтажа с тем же ID нужна повторная проверка привязки.

### 6.2 Экран воспроизведения для всех устройств

Рекомендуемый первый технический эксперимент: отдельная **верхнеуровневая** страница, условно `/study-video.html`, без COEP, с обычным YouTube iframe и общей таблицей. Это экран того же материала с явной кнопкой возврата в Студию.

Хранение и редактирование остаются в действующем приложении. Перед навигацией формируется минимальный проверенный снимок выбранной редакции для чтения; возможный транспорт на том же origin — ограниченный IndexedDB handoff с непрозрачным ID и сроком жизни. Страница не открывает SQLite и не записывает SRS. При недоступности/истечении снимка возвращает пользователя к материалу. Публичный материал получает разрешённый immutable snapshot через существующий слой публикации.

Это **гипотеза архитектуры**, требующая проверки, включая возврат, reload, SW-кеш, приватные данные и смену аккаунта. Не передавать текст, ключи или токены в query string. Снимок — производная для чтения, не второй канон; ограничить размер/TTL и очищать по политике. Не полагаться на `window.opener`: COOP может разрывать связь окон.

Альтернативы: оставить существующий Chromium-плеер и внешнюю ссылку на iPhone — быстрый промежуточный выпуск, но не закрытие требования синхронизации на iPhone; переделать storage-движок для всей Студии — значительно более широкий риск, не рекомендован для этой задачи.

### 6.3 Синхронное изучение

- Время YouTube — единственный источник текущего положения при YouTube-воспроизведении. Не запускать параллельно скрытый MP3 как «точные часы».
- Общий контроллер связывает проверенные интервалы со stable row/cue IDs; не доверяет порядковому номеру предложения провайдера.
- Отдельное управление переходом к строке не мешает морфологии и TTS. Для нового интерфейса использовать явную кнопку таймкода/оригинала; поведение существующего tap-seek согласовать отдельно.
- Полная остановка старого плеера при смене материала; защита от двойного запуска и устаревшего async-ответа.
- Для YouTube-повтора строки нужна своя конечная машина: запрос перехода → подтверждённое положение → воспроизведение → достижение конца → пауза. Нельзя проверять конец сразу по старому `currentTime`. При timeout честно отменить повтор.
- Буферизация, ручная перемотка, смена скорости и возврат из фона не должны давать ложную подсветку. Недоступность ролика и неизвестное состояние показывать явно.
- Не пытаться определять/обходить рекламу недокументированными методами. Проверить фактические часы и UI при рекламе; не обещать непрерывного упражнения без прерываний.
- Синхронизация таблицы с оригинальным ивритским видео не означает синхронное звучание русского TTS. TTS и оригинал взаимоисключаются; режим последовательного прослушивания можно добавить позднее.

### 6.4 ZIP и корпус

Лёгкий пакет должен включать текст, выбранные редакции таблицы и субтитров, точное соответствие строк, сведения о происхождении, YouTube-привязку и README. Медиабайты не обязательны. Различать «пакет учебных данных полный» и «видео доступно только онлайн».

Выбрать версионированное расширение формата после round-trip эксперимента. Старые ZIP продолжают импортироваться. Старый клиент не должен молча потерять новый обязательный источник: требуется понятное сообщение о версии или поддерживаемая деградация. Dry-run, hashes, идемпотентность и rollback сохраняются.

Для публичного корпуса издатель сохраняет immutable snapshot учебных данных и внешнюю привязку. YouTube не входит в счётчик отсутствующих локальных audio assets. Показать отдельно внешнее видео, локальный оригинал и сгенерированный TTS. Проверить sanitizeSnapshot, экспорт публикации и reader adapter; наличие общего JSON ещё не доказывает их сквозную совместимость.

Встраивание само по себе не подтверждает права на отдельную публикацию расшифровки, перевода и ZIP. В публикационном процессе сохранить отдельные сведения о правах на учебный текст/производные и разрешённый способ представления видео. Не переносить на новые ролики разрешения из ранее опубликованных корпусов. Политики YouTube регулируют встроенный плеер; конкретные права на учебные производные требуют отдельного основания. [Developer Policies](https://developers.google.com/youtube/terms/developer-policies).

## 7. Оптимизации процесса и экономика

| Изменение | Что сокращает | Условие качества |
|---|---|---|
| Сначала использовать пригодные субтитры | ASR, загрузку больших файлов, ожидание | Проверить язык, полноту, принадлежность ролику |
| Одна возобновляемая задача | Переходы через редактор и Импорт-Центр | Явные состояния и сохранённые результаты этапов |
| Кеш raw transcript | Повторный ASR при сбое перевода | Ключ включает источник/редакцию, модель и параметры |
| Кеш и продолжение таблицы по кускам | Повторную оплату уже готовых строк | Исправленные сегменты инвалидируют только затронутые результаты |
| Идемпотентное создание карточки | Дубли при повторном нажатии/возврате | Ключ задачи и проверка выбранной редакции |
| Сохранение проверенного результата автоматически в рамках выбранного режима | Отдельную кнопку «в Библиотеку» | Незавершённое обозначается черновиком; ошибка не превращается в «готово» |
| Экспорт из экрана результата | Повторный поиск материала | Сохранять receipt: подготовлено ≠ фактически сохранено системным диалогом |
| Текстовый/YouTube пакет по умолчанию для передачи | Копирование и хостинг оригинального видео | Явная пометка онлайн-зависимости |
| Пакетная очередь | Повторение одинаковой настройки | Ограниченная параллельность, бюджет, отмена, состояние каждого элемента |

Бюджет задачи: ASR/модель + перевод/огласовки + необязательный TTS + хранение/трафик LinguistPro. YouTube embedding не добавляет платёж за просмотр в этой модели, но не обнуляет остальные составляющие. При исчерпании квоты — пауза и понятное продолжение, без скрытого переключения на платного провайдера.

Экономия хранения: если учебные данные занимают `T`, а локальное видео `V`, переход от `T + V` к `T` убирает долю `V / (T + V)`. Иллюстрация, не замер: 2 МБ таблицы/меток + 300 МБ видео → около 99,3% меньше исходных данных на сервере. Реальные backup/replication, TTS и служебные расходы считать отдельно. Трафик просмотра видео переносится на YouTube; на устройстве зрителя он остаётся.

Не объединять ASR и всю билингвальную таблицу в один огромный непрозрачный вызов ради меньшего количества кнопок. Автоматизировать оркестрацию уже разделённых этапов: это сохраняет исправление текста, кеш и повтор только неудавшегося шага.

## 8. Поэтапный план внедрения

| Этап | Результат | Ключевая проверка / выход |
|---|---|---|
| P0. Техническая квалификация | Одно реальное видео с таблицей: ПК, iPhone; пробный export/import YouTube-привязки на fixture; отдельная проба Gemini URL | Матрица PASS/FAIL по браузеру и маршруту. Не расходовать ключи без отдельного запуска владельцем; автоматизация Б не блокирует A/C |

| P2. Переносимый пакет | Ссылка + редакции + mapping проходят export → чистый профиль → import | Полное сравнение выбранной редакции и источника; нет обязательного MP4 для онлайн-материала; старые пакеты работают |

| P4. Единая задача подготовки | Субтитры/файл → таблица → карточка → экспорт; resume/cancel | Сбой и reload на каждом шаге не теряют текст, не дублируют карточку, не повторяют законченные provider calls |

| P6. Публикация | Отдельный материал и корпус с онлайн-видео, лёгкий ZIP | Чистый пользователь открывает опубликованный снимок; оригинал не загружен на сервер; недоступное видео не блокирует таблицу |

P0 проводится до выбора окончательного браузерного решения. P1–P2 дают раннюю ценность существующим материалам. P3 обязателен для полного требования iPhone. P4 не зависит от успеха Gemini URL. P6 использует уже проверенные P1–P3 и существующий публикационный процесс.

Предварительный allowlist по этапам (не разрешение на изменения в этой исследовательской сессии):

- P1/P3: `public/js/studio-yt-player.js`, `studio-media-karaoke.js`, `media-host.js`, `media-package-{core,repository}.js`, `public/index.html`, `public/js/library-ui.js`; новый экран и его минимальные JS/CSS; узкое правило headers в `server.js`.
- P2: `public/js/portable-learning-package-{core,repository}.js`, `studio-portable-learning-package.js`, код формирования пакета и проверки формата, найденный consumer sweep.
- P4/P5: `public/js/studio-import.js`, существующий контроллер задач/ASR и провайдерные адаптеры после актуальной разведки. Новое API создавать только при доказанной необходимости.
- P6: `db/publicationRepo.js`, `public/js/publication-center.js`, `public/js/public-corpus-adapter.js`, необходимые reader consumers.

Не включать: смену ASR/переводчика по умолчанию, массовую перепривязку библиотеки, удаление локального медиа, перестройку SRS, E2EE/cloud sync, новые серверы/платные transcript-сервисы, cookies/login bypass, перемещение незакрытого downloader-кандидата в main.

## 9. Проверки и критерии приёмки

### 9.1 Данные и регрессии

Сначала красные тесты: YouTube-привязка теряется при portable round-trip; импорт онлайн-материала ошибочно требует локальное медиа; смена ролика оставляет старый адаптер; async seek завершает строку по старым часам. Не писать тест, повторяющий тот же serializer как единственный оракул: сравнить исходный fixture и восстановленный материал независимо.

Прогнать релевантные существующие `smoke:captions-parse`, `smoke:media-karaoke`, `smoke:studio-karaoke`, `smoke:room-media`, `smoke:media-package`, `smoke:portable-learning-package`, `smoke:import-center`, `smoke:text-card`, `smoke:reader-parity`, `smoke:i18n`, API smoke. При изменении ASR/таблицы — `smoke:studio-chunks` и соответствующие живые гейты. Имена и актуальные требования повторно проверить по `package.json` целевой ветки.

Известный предшествующий риск: документ серверного downloader сообщает незелёный `smoke:studio-chunks`; это не новый измеренный сбой данной сессии. Перед релизом проверить baseline, причину и границы влияния, не переписывать постороннюю логику ради зелёного результата.

### 9.2 Независимая оценка текста и тайминга

Предлагаемый пилот: минимум 6 роликов — короткая речь, интервью с несколькими говорящими, ручные/автоматические субтитры, музыка/длинные паузы, часовая запись, длинная лекция ближе к поддерживаемому пределу. Restricted/deleted/embed-disabled случаи проверять отдельно как отрицательные сценарии. Контент для прогона предоставляет/выбирает владелец с допустимым доступом.

Для каждого: ручной контроль начала/середины/конца и равномерно распределённых реплик, отдельно чисел/имён; минимум 30 временных якорей на ролик. Отчёт: ошибки текста, пропуски, ложные вставки, медиана/P95 ошибки старта, максимальный дрейф, проблемные интервалы. Оценщик сверяет с фактическим видео, а не с метками той же модели.

Предлагаемые начальные пороги для обсуждения после baseline: P95 ошибки старта ≤1 с; ни одного неотмеченного проверенного участка с дрейфом >2 с; ноль неверных row↔cue привязок в независимых fixture; ноль скрытых пропусков в проверенной выборке. Выборка не доказывает отсутствие всех ошибок во всём ролике. Увеличивать её при обнаруженном дрейфе. При провале отмечать непригодные интервалы, не интерполировать их молча.

### 9.3 Браузер и владелец

Desktop Chrome/Edge; Firefox с фактическим поведением capability; реальные Safari/Chrome на iPhone и PWA. Проверить 380 px RU, 380 px HE RTL, desktop, landscape, keyboard focus; выполнить и посмотреть скриншоты до UI-коммита. Мобильная эмуляция не заменяет iPhone.

Обязательные сценарии: play → pause → seek 25%/75% → выбор строки → возврат из фона → reload → другая карточка → TTS → оригинал; ошибка 153; запрет embedding; сеть пропала; ролик удалён; две быстрые команды; playback rate; остановка/конец; возвращение из экрана видео в Студию. Проверять фактическое изменение времени и активных строк, а не только появление iframe.

Экспорт: новая среда открывает ZIP и таблицу без MP4; видео запускается онлайн; offline ясно показывает отсутствие видео при доступном тексте. Публикация: права и snapshot hash, без включения профиля/ключей, реальные просмотры в новой сессии. `review_log` не меняется от пассивного проигрывания или миграции источника.

Фиксировать отдельно: unit/browser technical pass, живой provider pass, production verification и physical-device owner acceptance. Не переносить статусы старых программ на новый экран.

## 10. Разбор решения по ролям и решения владельца

| Роли | Проверка рекомендации |
|---|---|
| R1/R10 | Подключение YouTube не меняет огласовки/морфологию; ASR не сертифицирует собственный текст |
| R2/R8 | Видео и строки рядом, повтор и ясное управление; редактор не обязательная остановка каждого успешного импорта |
| R3/R9 | Stable IDs, provenance, явная связь тайминга с конкретным источником; video ID не равен content hash |
| R4/R5 | iPhone — обязательная часть результата; бесплатное embedding и честная онлайн-зависимость |
| R6/R7 | Название/автор/источник и редакционный контекст сохраняются; корпус не становится списком голых ссылок |
| R11 | Существующие строки/правки не перезаписываются; проверка часов независима; нет массового relink |
| R12/R13 | Один канон, версионированная привязка, снимки для чтения, обратимый импорт |
| R14/R15 | Узкий headers exception, минимальный handoff, lifecycle/права; личный пакет не публикуется сам |
| R16 | Кеш, resume, лимиты и отдельный подсчёт затрат; YouTube-ссылка не обещает бесплатный перевод |
| R17 | Просмотр не пишет оценки SRS; генерируемая таблица не служит оракулом качества ASR |

Предлагаемый пакет решений для следующей реализации:

1. Онлайн-YouTube сделать стандартным вариантом распространения подходящих материалов; локальный оригинал сохранить как дополнительный офлайн/архивный вариант.
2. Одобрить P0 → P1 → P2 → P3 → P4; P5 допускать только по результатам качества, P6 выпускать отдельным этапом.
3. Для iPhone принять проверку отдельного экрана того же материала; если требуется исключительно текущий экран Студии, сначала расширенная архитектурная разведка.
4. Автоматически сохранять успешно подготовленный материал только в явно выбранном режиме задачи; публичная публикация и фактическая отправка остаются отдельными действиями.
5. Для provider-пилота отдельно задать набор роликов, модель и допустимый бюджет. В этой сессии никаких платных вызовов не делалось.

**Ожидаемый результат программы:** готовая карточка переносится одним лёгким ZIP или открывается из корпуса, показывает YouTube-видео и синхронные учебные строки на ПК и iPhone; путь создания использует субтитры или выбранный ASR, сохраняет промежуточные результаты и не требует вручную повторять технические этапы после каждого успеха.
