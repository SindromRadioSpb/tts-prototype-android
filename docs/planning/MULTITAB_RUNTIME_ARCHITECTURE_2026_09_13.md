# Многовкладочная Студия, Зал и Медиатека

Дата: 2026-09-13. Исходный production commit: `ff41fae5` (3.11.527).
Реализация: ветка `fix/multitab-runtime-2026-09-13`, кандидат 3.11.528.
Статус: локальная реализация и автоматические проверки; production и физический iPhone ещё не приняты.

## Запрос и подтверждённые причины

Пользователь должен одновременно работать в нескольких Студиях, Залах и Медиатеках одного браузерного профиля. Закрытие или уход в фон одной вкладки не должны перезагружать остальные, менять активный материал другой Студии или показывать чужое пустое хранилище как личную библиотеку.

В предоставленной записи `8.MP4` (11.23 секунды) Медиатека показывает личные видео, переход открывает таблицу «Моше Шарон-3», затем Зал показывает сообщение о другой вкладке. Скриншот `9.jpg` показывает недоступность исходного хранилища. Запись подтверждает пользовательский сбой, но не содержит WebKit/OPFS-трассы; точная причина именно на устройстве не установлена.

В исходном коде обнаружены отдельные дефекты общего фундамента:

1. `local-db.js` держал Web Lock всю жизнь вкладки-владельца. Другие вкладки зависели от её `BroadcastChannel` и выполнения её JavaScript.
2. Failover и позднее подключение вызывали `location.reload()`. Для Студии это прерывает текущую работу.
3. Обработчик ухода со страницы освобождал логическую блокировку до гарантированного закрытия физических OPFS handles.
4. `db-worker.js` использовал `async onmessage` без последовательной очереди; асинхронные SQL-запросы могли перекрываться. Проксирование отдельных SQL также не изолировало транзакции разных вкладок.
5. `AccessHandlePoolVFS` открывал handles через `Promise.all`. При ранней ошибке очистка могла закончиться раньше запоздавшего успешного открытия. Тест с ранней ошибкой и поздним handle воспроизводит утечку.
6. Активный текст, введённый текст, таблица и выделенная строка Студии использовали общие ключи `localStorage`.
7. Legacy-замена таблицы состояла из отдельных операций, без общей транзакции и проверки версии открытого материала.

Итого: симптомы относятся к общему слою, однако это несколько дефектов, а не доказанная единственная причина всех случаев на iPhone.

## Выбор архитектуры

| Вариант | Оценка |
|---|---|
| Усилить владельца heartbeat, повторными подключениями и перезагрузками | Сохраняет зависимость от фоновой страницы; недостаточно для нескольких Студий. |
| SharedWorker как единственный владелец | Полезный вариант для отдельного прототипа, но синхронный OPFS API предназначен для dedicated worker; перенос требует дополнительного слоя и самостоятельной проверки жизненного цикла на iOS. Не считать поддержку SharedWorker доказательством работоспособности всей цепочки. |
| Короткое владение в dedicated worker на SQL-операцию / целую транзакцию | Выбрано. Использует текущие SQLite, OPFS и IndexedDB без миграции личной библиотеки в другое хранилище. Простаивающая вкладка не владеет физическими файлами. |

Основания: [Web Locks specification](https://www.w3.org/TR/web-locks/), [FileSystemSyncAccessHandle](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemSyncAccessHandle), [SharedWorker](https://developer.mozilla.org/en-US/docs/Web/API/SharedWorker).

Ролевые критерии: R4 — обычная многовкладочность без предупреждения и принудительной перезагрузки; R9 — единая физическая идентичность библиотеки; R11 — реальные транзакционные и аварийные тесты, сохранность learner state; R1/R2 — сохраняется таблица и учебный контекст материала.

## Реализованный контракт

- Каждая вкладка имеет dedicated worker и собственную последовательную очередь. Все workers используют один origin-scoped Web Lock `linguistpro-opfs-db-owner-v1`.
- Порядок: lock → физическое открытие → SQL → закрытие SQLite/VFS → отпускание lock → ответ. Вне транзакции ответ не оставляет библиотеку занятой.
- `sqlite3_get_autocommit` определяет границу транзакции, включая SAVEPOINT. Между BEGIN и COMMIT/ROLLBACK владеет один worker. SQL чужой вкладки не может попасть в эту транзакцию.
- WASM/VFS-регистрация переиспользуются; при следующем владении переоткрываются файлы. Миграции проверяются при первом открытии worker. Структура и исходный backend пользовательской БД не меняются.
- Небольшая отдельная запись IndexedDB `linguistpro-storage-identity-v1` согласует первый выбор backend между одновременно стартующими вкладками. Существующий `opfsVfsPreference_v1` сохраняется; конфликт идентичности или неизвестный backend останавливают открытие. Переключения в другую, пустую библиотеку нет.
- Таймаут ожидания lock — 30 секунд. Отменяется ещё не начавшийся запрос lock, а не уже исполненная запись. Автоматического повторения записей нет.
- Транзакция без SQL-активности 30 секунд откатывается. После этого её запоздавшие команды запрещены до явного recovery. При возобновлении проверяется и настенное время: замороженный таймер не позволяет исполнить остаток транзакции как отдельные записи.
- Ошибка физического закрытия сохраняет exclusion и блокирует продолжение записи; recovery повторяет cleanup. Lock никогда не отбирается у неизвестного живого worker.
- После commit соседние вкладки получают сигнал инвалидировать каталоги. Открытый reader/плеер и редактор не заменяются. Пропущенный фоновый сигнал восполняется обновлением видимой Медиатеки и pageshow.
- Retry Медиатеки работает на месте. BFCache Медиатеки не требует reload. Нормальная многовкладочность не показывает баннер владельца.
- Активная Студия использует `sessionStorage`: input, table cache, active material, selected row. Один раз копируется предыдущий legacy draft, исходные общие ключи не удаляются. Вкладки имеют независимое состояние, reload своей вкладки его сохраняет. Это не новая долговечная система восстановления всех несохранённых черновиков после закрытия браузера: сохранять материал в библиотеку по-прежнему необходимо.
- Legacy-замена текста использует `replaceStudioText`: BEGIN IMMEDIATE, сравнение `updated_at`, замена строк, COMMIT. Устаревший редактор получает конфликт, без потери своего текущего черновика. Ошибка вставки откатывает всю замену. Версионные медиаматериалы остаются на каноническом пути ревизий.

## Совместимость обновления

Новый транспорт запускает `/db/db-worker-runtime.js?v=528`. Исторический `/db/db-worker.js` сохранён для уже открытых старых оболочек: новый и старый протоколы не смешиваются. Старый владелец блокирует новые короткие операции тем же Web Lock, пока его вкладка не закроется/обновится. При переходе с 3.11.527 может потребоваться однократное обновление старых вкладок с предварительным сохранением работы. Это ограничение перехода, не штатная модель новой версии.

Согласованы APP_VERSION, SW, module URLs, локали `v=223`, locale hash lock, integrity manifest; добавлены runtime dependencies в precache и integrity contract.

## Проверки и границы доказательства

Команды и результаты: [evidence](../research/multitab-runtime/2026-09-13/EVIDENCE.md).

Локально доказаны: четыре и восемь клиентов Chromium на реальных OPFS и IndexedDB; четыре клиента WebKit на IndexedDB; две полные Студии + Зал + Медиатека; разные черновики; сохранение при reload; отсутствие reload при закрытии соседа; живое обновление Медиатеки; реальный локальный MP4 и таблица; заморозка простаивающей Студии; CAS-конфликт; rollback ошибочного сохранения; закрытие вкладки внутри транзакции; непустые `review_log`/`word_status` без изменений; `integrity_check=ok`.

Не доказаны: физический iPhone, его конкретный WebKit/Chrome, возврат после нескольких минут фона на iOS, YouTube-воспроизведение в условиях конкретного устройства, VoiceOver, production 3.11.528.

Windows WebKit 26.4 в Playwright не предоставляет `navigator.storage.getDirectory`: его OPFS-прогон завершился ошибкой, а не был засчитан как успех. IDB-прогон прошёл. Системно замороженный worker внутри незавершённой транзакции нельзя безопасно «отобрать» таймером другой страницы; ожидание ограничено, при возобновлении транзакция проверяется/откатывается. Это нужно проверить на физическом iOS; обещания неограниченной фоновой работы нет.

## Выпуск и приёмка

1. Проверенная отдельная ветка и reviewable PR; без слияния с main и production-записи.
2. Согласованный выпуск кандидата; повторные no-cache проверки shell/module/locale/integrity версии на production.
3. Физический iPhone: сохранить работу в старых вкладках, обновить до одной версии; открыть две Студии с разными материалами и Медиатеку; повторить исходный переход к видео; свернуть на несколько минут; вернуться; закрыть одну Студию; убедиться, что другая не перезагрузилась и не сменила материал.
4. Отдельно проверить конфликт сохранения одного материала в двух Студиях, реальные браузер/PWA, Safari/Chrome и AT. До этого не отмечать iPhone-проблему как окончательно закрытую.

Rollback выпуска — возврат предыдущего shell/runtime. Материалы и review_log не мигрировались и не требуют отката данных; запись identity остаётся неразрушающим метаданным. Нельзя удалять пользовательскую БД или менять backend ради устранения сообщения.
