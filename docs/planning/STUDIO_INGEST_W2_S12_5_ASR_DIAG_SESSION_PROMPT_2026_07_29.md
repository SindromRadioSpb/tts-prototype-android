## Гипотезы (ранжированы) и как их РАЗЛИЧИТЬ до кода

**H1 (главная): прогон шёл на несвежей вкладке.** Вкладка владельца жила с прошлых прогонов
(предупреждение «Библиотека открыта в 2 вкладках» наблюдалось); SW обновляется
(auto-skipWaiting), но УЖЕ ЗАГРУЖЕННЫЕ модули страницы — нет. Если его вкладка держала
JS ≤v3.11.261 — дубли на границах ожидаемы (клип слеп), а обрыв мог быть старой семантикой.
**Проверка — попросить владельца выполнить в консоли ЕГО РАБОЧЕЙ вкладки** (той, где делал
транскрибацию; DevTools → Console):
```js
copy(JSON.stringify({
  stitch: typeof AsrTranscript !== 'undefined' && !!AsrTranscript.stitchWindowSegments,
  overlap: typeof AsrTranscript !== 'undefined' ? AsrTranscript.ASR_WINDOW_OVERLAP_SEC : null,
  coverTol: typeof AsrTranscript !== 'undefined' ? AsrTranscript.STITCH_COVER_TOL_SEC : null,
  asr: window.v3LastImportMeta && v3LastImportMeta.audio && v3LastImportMeta.audio.asr
}, null, 1))
```
и прислать вставку. `stitch:false` или `overlap:null` = H1 подтверждена. `asr.windows/seams/
coverageGaps/warnings` — полный провенанс прогона: сколько окон реально выполнено, были ли
якоря (`anchored`), пропуски (`skippedRanges`), доборы. Это решает H1/H2/H3 одним махом.

**H2: код свежий, но шов не работает на реальных данных** (якорь не находится → noAnchor-путь;
или находится, но модель на швах отдаёт слишком разные формулировки). Провенанс `seams`
покажет. Тогда чинить алгоритм по фактическим швам.

**H3: обрыв = деградация модели в пиковые часы** (503/обрывы вывода; замер 2026-07-29:
окно уходило >180с, 503 повторные). Провенанс `windows` покажет, выполнились ли окна 6-8.
ВАЖНО: если прогон завершился «успехом» при 3 невыполненных окнах — это отдельный R11-баг
(результат с потерей 44% таймлайна не имеет права выглядеть успехом).

**Контрольный эксперимент (после диагноза по провенансу):** свой прогон текущим кодом на
том же файле — скрипт-образец: `.../scratchpad/m4-dup-probe.js` прошлой сессии (окна через
РЕАЛЬНЫЙ runWindowedAsr + шингл-анализ дублей; печатает только статистику, не контент).
Ключ `GEMINI_API_KEY` в `.env` проекта; квота дневная — могла восстановиться; расход ~$0.35.
Файл 117-мин у владельца в Downloads (см. выше). НЕ гонять вслепую до чтения провенанса.

## Кандидаты-фиксы (решить ПО ДИАГНОЗУ, не до)

1. **R9-штамп версии в паспорт прогона**: писать версию загруженного кода (константа сборки)
   в `asr`-мету — «каким кодом сделан прогон». Дёшево, закрывает слепоту навсегда. Делать
   почти при любом диагнозе.
2. **Stale-tab guard**: перед стартом дорогой операции сравнивать версию загруженной страницы
   с версией активного SW/сервера (`/api/client-config` теперь честный) → «Страница устарела,
   обновите вкладку» вместо прогона старым кодом. Прямо закрывает H1-класс.
3. **Честный итог прогона в превью** (R11): «окон 8: успешно N, пропущено M (мм:сс–мм:сс)»
   + при большой потере — явное предупреждение и подтверждение перед «Использовать».
   Обрыв на 66-й минуте не должен выглядеть успехом.
4. Разбор шва по фактическим `seams` (если H2): подстройка якоря (длина/нормализация/зона),
   или запасная стратегия шва.
5. Если H3 — стратегия деградации: пере-прогон упавших окон позже / явный частичный результат.

## Инварианты (не нарушать)

- R11: никакой интерполяции; потеря/пропуск ВСЕГДА виден пользователю; лучше видимая копия,
  чем тихая потеря — но и копия должна быть исключением, а не 22% текста.
- R9: провенанс полный (окна/швы/пропуски/версия кода).
- browser-first BYOK; сервер — только по явной развилке владельцу.
- Личный материал владельца НЕ коммитить (интервью — семейный архив); в репо только числа/методика.
- Локали ru/en/he + бамп `?v=` И `CACHE_VERSION` одним изменением + `--write-lock` (`smoke:i18n`).
- `renderTable`/reader-core не трогать (`smoke:reader-parity`); стейджить явными путями;
  пуш только в релиз-задаче; скриншот 380×844 для UI-правок.
- Гейты: `node --test` (базлайн: 9 pre-existing падений GCP/classic), `smoke:i18n`,
  `smoke:studio-chunks`, `smoke:ingest`, `test:api-smoke` (включая пин версии client-config).

## Порядок работы

1. Диагноз по провенансу (сниппет владельцу) + анализ артефактов (пере-извлечь при нужде).
2. Контрольный прогон текущим кодом (m4-паттерн) — только после п.1, если нужен.
3. Развилки/дизайн-решение владельцу с рекомендацией (какие из кандидатов-фиксов делать).
4. Имплементация паттерном проекта: свежий имплементер + ревью (мутационное, живыми пробами —
   планка задана S12.4-ревью), whole-branch до пуша, один пуш, прод-верификация.
5. **Живая валидация на реальном длинном аудио ДО объявления успеха** — новое правило слайса:
   без чистого прогона (дубль-шинглы <3%, покрытие таймлайна без нулевых корзин, окна все)
   слайс не закрыт. Метрика-скрипт — по образцу анализа 2026-07-29 (шинглы + корзины покрытия).
6. Owner-приёмка: его файл, его вкладка (свежая!), сборка таблицы «Собрать таблицу» +
   сохранение 💾 — то, что он отложил до починки.

## Уроки (оплачены)

- **Юнит-зелёное ≠ живое-рабочее**: три мутационно-выверенных фикса подряд не дожили до
  живого прогона. Живой длинный прогон — обязательный гейт этого класса правок.
- **Штамп версии в артефакте** — без него каждый брак порождает гипотезу «а тем ли кодом?».
- Модель врёт метками, если промт требует «метки внутри диапазона»; половина дублей пришла
  из этого требования (S12.3→S12.4).
- Пиковые часы: 503 + >180с на окно — реальность; таймауты и ретраи должны это переживать.
- Дифф-ревью с мутациями живыми прогонами (планка S12.4) ловит то, что не ловит чтение.

Начни с диагноза (сниппет владельцу — первым сообщением), НЕ с кода.
