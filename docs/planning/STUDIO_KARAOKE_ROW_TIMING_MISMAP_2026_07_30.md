# BUG: караоке-тайминг сопоставлен строкам один-к-одному с сегментами (рассинхрон до 36 мин)

**Дата:** 2026-07-30. **Источник:** owner-приёмка S12.5 — «кнопка воспроизведения в колонке
Перевод не соответствует по таймингу тексту в колонке Иврит».
**Статус:** ИСПРАВЛЕНО в рабочем дереве (K1 отключение + K2 возврат), гейты зелёные,
НЕ закоммичено, owner-приёмка не проводилась — см. §«Что сделано» внизу.
**Приоритет: ВЫСОКИЙ** — ломает моат-функцию
(сегмент-караоке) на длинных материалах и делает её хуже, чем бесполезной: подсветка
уверенно показывает НЕ ТУ строку.

## Симптом в числах (карточка «Шломо Крук. Интервью. Холокост.», 117 мин)

Сверка `audio.timing.entries` с реальным временем каждой строки по тайм-меченым
YouTube-субтитрам (внешний оракул):

```
строк в таблице:            1651
записей тайминга:           1070   (o от 0 до 1072)
строк БЕЗ тайминга:          581   (35% таблицы — конец не подсвечивается вообще)
медиана |ошибки|:            558 с (9.3 мин)
строк с ошибкой <= 5 с:      0.0%
строк с ошибкой > 60 с:     94.3%
максимум |ошибки|:          3368 с (56 мин)
```

Ошибка НАКАПЛИВАЕТСЯ по ходу таблицы (медиана по децилям строк):

```
строки    0- 165:  +111 с  (1.9 мин)
строки  165- 330:  +602 с  (10.0 мин)
строки  495- 660:  +551 с  (9.2 мин)
строки  660- 825:  +949 с  (15.8 мин)
строки  825- 990: +2145 с  (35.8 мин)
строки  990-1155: +2158 с  (36.0 мин)
строки 1155-1651:  тайминга нет вовсе
```

## Механика

`buildRowTiming(segments, rowSegIdx)` (asr-transcript.js) строит `firstRow: сегмент → ПЕРВАЯ
строка этого сегмента` и возвращает `{o: индекс СТРОКИ, t: start сегмента}`. Замысел верный.

Факт: в сохранённом паспорте `entries` идут `o = 0,1,2,…,1072` подряд (пропуски лишь 259,
260, 800) — то есть `firstRow.get(k) === k` для всех сегментов. Это возможно ТОЛЬКО если
`segment_index` строки равен её собственному порядковому номеру, а не индексу исходного
сегмента. При 1074 сегментах и 1651 строке (модель дробит длинную реплику на несколько
строк — нормальное поведение) соответствие ломается с первого же раздробленного сегмента и
дальше расходится линейно; хвост таблицы за пределами 1073 остаётся вообще без меток.

Где именно вырождается индекс — определить при фиксе; кандидаты по коду:
- ответ сервера seg-режима (`ingest/segTable.js` / `tableRows.js`): чем заполняется
  `segment_index` — индексом входного сегмента или порядком строки в ответе;
- `TableChunks.offsetRows(rows, base)` (table-chunks.js) сам по себе корректен
  (`segment_index + base`), но он лишь сдвигает то, что пришло;
- сборка чанков в `v3TranslateTableChunked` (index.html ~33458) и `v3AttachAudioTiming`
  (~23480): гейт `anyIdx` проверяет ЛИШЬ наличие целых чисел, а не их осмысленность.

## Почему не поймали раньше

- Приёмка W2-S4 (19-мин mp3, 153 сегмента) прошла успешно: там модель почти не дробила
  реплики, число строк было близко к числу сегментов, и тождественный маппинг случайно
  совпадал с правильным. Дефект проявляется тем сильнее, чем больше строк на сегмент.
- Ни один гейт не сравнивает тайминг с внешним оракулом. `buildRowTiming` покрыт юнитами на
  синтетике, где индексы заданы правильно by construction; `SEG_MAPPING_LOST` ловит
  ОТСУТСТВИЕ индексов, а не их бессмысленность.
- Тот же класс, что и корневая причина S12.5: **структура доверяет самоотчёту вместо
  проверки**. Здесь — «раз индексы целые, значит осмысленные».

## Направление фикса

1. **Валидировать `segment_index` перед построением тайминга** (не «есть целые», а
   «согласованы»): максимум `segment_index` не может превышать `segments.length - 1`;
   число уникальных индексов не может равняться числу строк, когда строк заметно больше
   сегментов; строки одного сегмента обязаны идти подряд. Не сошлось → честный
   `SEG_MAPPING_LOST` и НЕТ караоке (лучше отсутствие, чем уверенно неверная подсветка, R11).
2. **Починить источник индекса** — чтобы `segment_index` строки указывал на исходный сегмент.
3. **Гейт с внешним оракулом**: смоук, где сегменты с известными метками дробятся на строки
   1:N, и проверяется, что `entries[o]` попадает в свой сегмент (а не в соседний).
4. Рассмотреть монотонную проверку: `t` по возрастанию `o` и покрытие всей таблицы, иначе —
   деградация.

## Проверка на существующих карточках

Дефект затрагивает уже сохранённые тексты из аудио, где строк заметно больше сегментов.
Диагностика без пересборки: `entries.length ≈ segments.length` и `max(o) ≈ segments.length-1`
при `rows.length` заметно большем — верный признак вырожденного маппинга.

Связано: `docs/planning/STUDIO_INGEST_S12_6_FALSE_GAP_COMPRESSED_MARKS_2026_07_30.md`
(там — отдельная, более мягкая неточность тайминга внутри одного окна из-за сжатых меток
модели; этот баг куда грубее и от него независим).

## Что сделано (2026-07-30)

### K1 — перестать врать

- Корень: премиум-ответ `/api/translate-table-v2` нёс `segment_index`-**однофамильца**
  (1-based номер предложения СВОЕГО сегментатора), а клиентский гейт проверял лишь «есть целые
  числа». Индексы принимались за индексы ASR-сегментов → вырожденный тайминг 1:1.
- `AsrTranscript.validateRowSegMapping()` — проверка ОСМЫСЛЕННОСТИ (диапазон / неубывание /
  непрерывность блока строк сегмента / невозможность 1:1 при строках > сегментов);
  `v3AttachAudioTiming(res, segMode)` доверяет `segment_index` ТОЛЬКО когда сам послал
  `segments`. Премиум → караоке честно отключено.
- `AsrTranscript.timingLooksDegenerate()` — карантин уже СОХРАНЁННЫХ паспортов при открытии
  текста (точный отпечаток, не порог): карточка владельца перестаёт подсвечивать не ту строку
  без пересборки таблицы.

### K2 — вернуть караоке честно (премиум-ветка = дефолт владельца google-free)

- `db/premium/segmenter.js`: сегменты получили **`line_index`** — 0-based номер ИСХОДНОЙ
  строки. Правило нарезки строк вынесено в `splitSourceLines()` и совпадает **по построению**
  с клиентским (`studio-import.js useText`, `index.html v3MediaLineIdentity`):
  `split("\n") + trim + filter(Boolean)`. Строки режутся ДО снятия BIDI-марок — иначе строка из
  одних марок сдвинула бы всю нумерацию. Границы предложений не изменились (byte-parity против
  прежнего алгоритма на корпусе).
- `db/premium/pipeline.js` → строка ответа несёт **`source_line_index`** (имя намеренно другое,
  чтобы коллизия имён — корень бага — не повторилась). `segment_index` премиума не тронут.
- `db/premium/versions.js`: `SEGMENTER_VERSION` `regex-v1` → `regex-v2-lineidx`. Он входит
  ТОЛЬКО в doc-ключ, поэтому старые doc-кэши (без нового поля) становятся недостижимы, а
  пересборка идёт из segment-кэша — без обращений к переводчику/никуду, то есть бесплатно.
- Клиент (`public/index.html`, `public/js/asr-transcript.js`): `premiumRowLineIdx(rows, lines)`
  принимает мост НЕ на слово — каждая строка ответа обязана быть **подстрокой той строки**,
  на которую ссылается (NFKC + снятие марок с обеих сторон). Не сошлось → `SEG_MAPPING_LOST`
  с деталью `LINE_TEXT_MISMATCH`, караоке нет. Индексы затем проходят ТУ ЖЕ
  `validateRowSegMapping`, что и seg-режим — правила K1 не ослаблены.
- Идентичность «строка = ASR-сегмент» проверяется ОДНОЙ функцией `v3MediaLineIdentity()`
  (её же использует seg-режим): число строк ≠ числу сегментов ⇒ маппинга нет.

### Адверсариальное ревью K2 (2026-07-30, независимый ревьюер)

Проверено ИСПОЛНЕНИЕМ, не чтением. Итог: **byte-parity сегментатора подтверждена, заявленные
свойства верны, найден и исправлен 1 дефект + 1 дыра в гейтах.**

- **Byte-parity на СОБСТВЕННОМ корпусе ревьюера** (не на корпусе автора): 8 985 документов ×
  2 режима (raw + `normalizeForDisplay`) = 17 970 прогонов, **854 648 сегментов**, сравнивалась

  Источники: 158 реальных `source_text` с авторской разбивкой строк (`Library/*.zip`) +

**Дефект 1 (IMPORTANT, ИСПРАВЛЕН).** `v3AttachAudioTiming`: K1/K2 подняли вызовы
`AsrTranscript.premiumRowLineIdx/validateRowSegMapping` ВЫШЕ развилки `if/else`. До фикса
отсутствие модуля было безопасно — тайминг обнуляла else-ветка, к `AsrTranscript` не
обращавшаяся. После — `TypeError` улетает во внешний `try/catch`, и на ОБЩЕМ объекте паспорта
остаётся тайминг ПРОШЛОГО ответа (воспроизведено в браузере: 8 записей пережили новый ответ,
`timingDropReason` пуст, медиа-бар показал бы «Караоке ✓»). Это запрещённый путь «молчаливо
неверная подсветка» (R11) — тот самый класс, ради которого делались K1/K2. Сценарий не
гипотетический: рядом в этом же файле стоит guard `window.TableChunks` с обоснованием «offline
right after a CACHE_VERSION bump before it's precached», а K2 CACHE_VERSION как раз бампит.
Фикс: guard доступности модуля ДО любого обращения → `timing = null` + честная причина + refresh
медиа-бара. Тест **сценарий 9** `smoke:studio-chunks` (красный до фикса).

**Дефект 2 (дыра в гейтах, ЗАКРЫТА).** Проверка `lines.length !== p.segments.length` в
`v3MediaLineIdentity()` — единственная защита идентичности «строка = ASR-сегмент», и у неё ДВА
потребителя. Премиум-ветку страхует повторная сверка в `v3AttachAudioTiming`, а **seg-режим
Gemini — не страхует ничто**: без этой строки клиент отправит ТЕКУЩИЕ строки как `segments`,
модель вернёт индексы в ИХ нумерации, а `buildRowTiming` положит их на сегменты ИМПОРТА.
Удаление строки оставляло ВЕСЬ набор гейтов зелёным. Замерено на мутанте: удалили первую строку
(9 строк на 10 сегментов) → ушёл seg-запрос с 9 сегментами → построено 9 записей караоке со
сдвигом на целый сегмент (`o=0` получил `t=0` вместо `t=7`), `timingDropReason=null` — молча.
Худший случай by construction: строк МЕНЬШЕ сегментов ⇒ все индексы в диапазоне, не убывают,
непрерывны ⇒ `validateRowSegMapping` такой сдвиг поймать не может. Тест **сценарий 8**
`smoke:studio-chunks` (красный на мутанте, зелёный на проде).

**MINOR (в отчёт, не чинилось).** (1) Комментарий в `splitSourceLines` утверждает, что марки —
«Cf, not White_Space»: для U+200E/200F/202A-202E верно, но в списке `BIDI_RE` есть ещё
**U+FEFF**, который `String.prototype.trim()` как раз удаляет (он в WhiteSpace по спецификации).
На поведение не влияет — строка из одного BOM отсекается `filter(Boolean)` одинаково на обеих
сторонах, — но формулировка неточна. (2) `timingDropDetail` (`LINE_TEXT_MISMATCH`,
`DEGENERATE_1_TO_1`, `OUT_OF_RANGE`, …) хранится в паспорте, но нигде не показывается: владелец
видит класс отказа, а не диагноз. Для отладки живой карточки его пришлось бы доставать из
`table_model_meta_json`.

### K3 — оживление УЖЕ СОХРАНЁННЫХ карточек офлайн (2026-07-30)

Закрывает раздел «Остаётся» ниже: караоке возвращается на уже оплаченном ASR, **без единого
сетевого запроса и без трат**, по факту открытия текста.

- **Ядро** `AsrTranscript.alignRowsToSegments(rowTexts, segments)` (`public/js/asr-transcript.js`):
  строки таблицы выравниваются на сегменты **по тексту**. Нормализация обеих сторон одна и та же
  (NFKC + существующий `stitchNormalizeWords`: слова любого письма, огласовки/теамим сняты внутри
  слова); указатель (сегмент, слово внутри него) идёт только вперёд; строка обязана **совпасть со
  словами сегмента начиная ровно с позиции указателя** — сравнение пословное, не `indexOf`, иначе
  «שלום» нашлось бы внутри «שלומי» и разрешило бы перескок непокрытого куска. Не сошлось → отказ
  (`ROW_NOT_IN_SEGMENT` / `SEGMENT_UNCOVERED` / `TRAILING_ROWS` / `EMPTY_INPUT`), караоке нет.
- **Оракул внутри ядра** (пересчёт из СЫРЫХ входов, без бухгалтерии указателя): (а) тот же
  `validateRowSegMapping`, что судит seg-режим и премиум; (б) **каждый сегмент, получивший строки,
  покрыт ими целиком** — конкатенация нормализованных слов его строк === слова сегмента. Одно
  сравнение ловит и «строка попала не в свой сегмент», и «часть сегмента без строк».
- **Подключение** — `v3RestoreMediaFromMeta` (`public/index.html`) на открытии текста + после
  восстановления строк в `v3RestoreSavedTableIfUnchanged`. R9: восстановленный тайминг помечается
  `timingSource="aligned-offline"` + `timingAlign{v,ok,reason,счётчики,codeVersion}`. В БД **не
  пишется**: пересчитывается за ~20 мс при каждом открытии, persisted-производное поле пришлось бы
  ещё и инвалидировать при правке строк.
- **Замер на ЖИВОЙ карточке владельца** (864f3aa2, kapture, 2026-07-30): 1074 сегмента ↔ 1651
  строка → `ok`, **1651/1651 строк размещено, 1074/1074 сегмента покрыты целиком**, 1071 запись
  тайминга (сегментов с числовой меткой ровно столько), **0 записей на чужой сегмент**, 23 мс.
  Хвост таблицы больше не мёртв: последняя запись `o=1649` против `o=1072` у сохранённого тайминга.

**Две предсуществующие мины, найденные замером живой карточки (обе исправлены здесь):**

1. **Паспорт не читался вовсе.** «Сохранить как новый» (`v3LibrarySaveCurrentCore`) пишет
   `tableModelMeta` в **`source_meta_json`**, а «Обновить карточку» — в `table_model_meta_json`;
   открытие текста читало ТОЛЬКО вторую. На карточке владельца `table_model_meta_json = NULL`, а
   `source_meta_json` = 130 КБ с полным паспортом ⇒ при открытии не было ни медиа-бара, ни
   караоке — независимо от K1/K2/K3. Добавлен узкий фолбэк `v3AdoptSavedTableMeta` (берём чужую
   `source_meta_json` только если в ней есть медиа-паспорт).
2. **Карантин K1 проходил мимо той самой карточки.** Отпечаток искал `o === индекс сегмента`, а в
   живом паспорте у **всех 1070 записей `o === индекс сегмента − 1`** (премиумный `segment_index`
   1-based): `timingLooksDegenerate` возвращала `false` на первой же записи. Правило переписано на
   **локстеп**: разность `o − segIdx` одинакова у всех сопоставленных записей и равна 0 или −1.
   Честная 1:N-таблица такой константы не даёт (на каждом раздробленном сегменте разность растёт).
   Сверх того, при успешном выравнивании доказанный маппинг **замещает** непроверяемый сохранённый
   тайминг — это и закрывает класс «карантин чего-то не поймал».

### Остаётся (важно, НЕ закрыто K2 — ЗАКРЫТО K3 выше)

- **Уже сохранённая карточка владельца караоке НЕ получит** — ни автоматически, ни по кнопке
  «Перевести». Две причины, обе предсуществующие (не внесены K1/K2):
  1. `v3RestoreSavedTableIfUnchanged()` при неизменённом тексте восстанавливает строки из
     Библиотеки и **не делает запроса вовсе** (а до неё ещё и localStorage-кэш таблицы);
     значит, новых строк с `source_line_index` не появится.
  2. Даже при принудительном перезапросе `v3MediaLineIdentity()` читает
     `window.v3LastImportMeta`, а он **обнуляется при открытии текста из Библиотеки** (R9:
     смена сущности). Паспорт самого текста при этом восстановлен
     (`v3LastGeminiMeta.source.audio` — с сегментами и метками).
  Сегодня караоке премиум-ветки работает в **той же сессии, что и импорт**. Для 117-минутной
  карточки это означает повторный импорт = повторную оплату ASR.
- **Предложение владельцу (отдельный слайс, НЕ сделан):** «оживление» сохранённых карточек без
  единого запроса. На открытии текста есть и сегменты (в паспорте), и строки таблицы; строки
  можно сопоставить сегментам тем же ДЕТЕРМИНИРОВАННЫМ правилом «строка обязана быть подстрокой
  своего сегмента» с монотонным продвижением указателя (то же доказательство, что в
  `premiumRowLineIdx`, — не эвристика). Не сошлось монотонно и однозначно → остаётся карантин
  K1. Это вернуло бы караоке на уже оплаченном ASR и заодно на всех старых карточках.
