# S12.7 — сжатые часы ASR-чанка: гейт, починка, честная слепота

**Дата:** 2026-07-30 · **Версия:** v3.11.270 · **Статус:** РЕАЛИЗОВАНО, гейты зелёные,
живая owner-приёмка НЕ проводилась.
**Источник:** owner-приёмка карточки «Заложница Миа. Интервью» — «строка 87 верна, со строки 88
всё уезжает». **Разбор с замерами:** `docs/research/studio-karaoke-clock-drift/2026-07-30/FINDINGS.md`.

## Что оказалось не так

Не маппинг строк (212 строк ↔ 212 сегментов, тексты совпадают 212 из 212 — K1/K2/K3 отработали
верно) и не шов чанк-таблицы (куски 120+92, ломается строка 89 — середина первого). Сломаны
**сами метки**: внутри ASR-чанка 870–1800 модель перестала читать позицию в звуке и начала
штамповать почти постоянный шаг ~4.7 с независимо от длины реплики. 930 с речи упакованы в 660 с
меток; ошибка растёт монотонно до **4 мин 17 с** на 57 % таблицы.

Замер против внешнего оракула (пословные субтитры того же ролика):

| окно | медиана \|ошибки\| | размах меток / длина окна | корреляция «длина текста ↔ шаг метки» |
|---|---|---|---|
| 0 (0–900) | 0.6 с | 0.99 | r = 0.81 |
| 1 (870–1800) | **59.7 с** (макс 257) | **0.71** | r = 0.05 |

Класс дефекта тот же, что корень S12.5: **самоотчёт модели о собственных координатах — не
оракул**. S12.5 закрыл подделку абсолютного времени (режем звук, офсет наш). Здесь подделывается
время ВНУТРИ честно нарезанного чанка, и структура этого не запрещает.

## Почему прежние гейты молчали

`classifyGap` (S12.6) судит **найденный разрыв** (hop > 90 с либо хвост ≥ 180 с). Он сработал —
но пометил `unreliableMarkRanges` только хвостовые 240 с из 836 испорченных и **ничего не
выключил**: `timingDropReason` остался пуст, караоке уверенно подсвечивало не ту строку. Хуже:
сжатие на 15 % в 15-минутном окне разрыва не даёт ВООБЩЕ — тайминг уехал бы на две минуты молча.

## Решение

### 1. Детектор `AsrTranscript.classifyClockCompression(density)`

Судит **размах меток чанка против объёма его текста**, разрыв для этого не нужен:

```
coverage = (markToSec − markFromSec) / windowSec
expected = min(densityRatio, 1)          // объём текста относительно базы прогона
сжато ⇔ expected − coverage ≥ CLOCK_SPAN_MARGIN (0.15)
```

Обрезка ожидания единицей обязательна с обеих сторон: окно имеет право честно молчать (тогда и
объём меньше — обвинения нет), а окно речистее базы при полном покрытии иначе было бы оболгано.
Судить можно, только если базу образует **кто-то кроме подсудимого** — иначе `densityRatio`
выходит 1.0 по построению и оракул судит сам себя. Порог по живому замеру: сломанные прогоны
0.69–0.71, здоровые 0.90–0.99.

**Отброшено замером:** корреляция «длина текста ↔ шаг метки». На полном прод-прогоне она
выглядела убедительно (0.81 против 0.05), но на отдельном прогоне это шум — 0.37 у сломанного
против 0.33 у здорового. В гейт не вошла.

**Осознанный остаток:** файл ≤ 15 мин = одно окно, базы нет, вердикт не выносится. Такое сжатие
ловит только прежний путь (разрыв ≥ `ASR_TAIL_GAP_SEC` → `marks-unreliable`).

### 2. Починка (`runWindowedAsr`, после основного цикла)

Дефект **стохастический**: тот же звук, тот же промт, повтор вызова — и медиана ошибки 55 с
превращается в 0.58 с (5 живых прогонов, FINDINGS.md §5). Поэтому лечение — переспрос:

1. **раунд 1** — повтор того же чанка (+1 вызов на сжатый чанк);
2. **раунд 2** — тот же чанк кусками по `CLOCK_SPLIT_SEC` (310 с, замер: 3 из 3 здоровы,
   медиана 0.46–0.71 с), склейка тем же швом по тексту; потолок `CLOCK_SPLIT_MAX_WINDOWS` = 4
   чанка за прогон, пропущенное помечается `clockSplitSkipped` (никаких молчаливых потолков);
3. не помогло → диапазон уходит в `clockCompressedRanges` + `ASR_CLOCK_COMPRESSED`.

Новый ответ принимается **только как доказанное улучшение** (R11): покрытие обязано вырасти,
объём текста — не упасть ниже `DENSITY_TEXT_PRESENT_RATIO` от прежнего (тайминг не покупается
ценой потерянной речи), и он обязан пройти анти-реплей гейт против **чужих** окон (повтор самого
себя уликой не является — для этого `shinglesExcept(idx)`). Каждая попытка видна в
`windows[k].clockRepair` (R9). Здоровый прогон не тратит ни одного лишнего вызова.

### 3. Честная слепота вместо вранья

`buildRowTiming(segments, rowSegIdx, blindRanges)` помечает записи сжатых диапазонов
`blind: true`. `StudioMediaKaraoke` на них **не подсвечивает ничего** и отказывает в повторе
строки. Записи не выбрасываются намеренно: тогда караоке молча держало бы последнюю честную
строку весь чанк — то же «уверенно показываем не ту строку», только тише. Честных записей
осталось < 2 ⇒ караоке нет вовсе. Сводка прогона получила **третий** факт (не потеря и не
«может уезжать», а «караоке выключено») со своей строкой в ru/en/he.

### 4. Один процесс на всех провайдеров

Было три способа связать строку с сегментом: `segment_index` (seg-режим Gemini),
`source_line_index` (премиум K2), выравнивание по тексту (K3, только сохранённые карточки).
Первые два требуют строгой идентичности «строка = сегмент» и зависят от поля конкретного
провайдера. Теперь `alignRowsToSegments` считается **на каждом ответе** и, когда сходится,
становится основным маппингом; индекс провайдера остаётся перекрёстной проверкой
(`timingMap.disagreed`, R9). Доказательство сильнее утверждения — тот же довод, по которому K3
замещает сохранённый тайминг.

Следствия: премиум-ответ из старого doc-кэша (без `source_line_index`) больше не лишает
владельца караоке на его дефолтном провайдере; переразбивка 1:N перестала быть тупиком. Инвариант
K1 не ослаблен, а усилен: чужой 1-based `segment_index` не является источником маппинга ни при
каких условиях — это пинится `timingMap.source === "aligned"` в сценарии 4a.

## Что осталось

- **Живая owner-приёмка** нового пути (импорт длинного медиа с починкой) не проводилась.
- Одиночное окно (файл ≤ 15 мин) детектором не судится — см. остаток выше.
- Восстановить тайминг без переспроса **нельзя** (замерено: пропорция по тексту 17.5 с, VAD по
  реальному звуку 51 с, честные якоря каждые 120 с + VAD 5.5 с). Если однажды понадобится
  строчная точность без ASR — нужен источник, ИЗМЕРЯЮЩИЙ звук (форсированное выравнивание либо
  ASR с пословными офсетами), а не вывод из текста.
