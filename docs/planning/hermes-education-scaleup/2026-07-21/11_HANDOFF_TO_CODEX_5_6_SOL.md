# 11 — Handoff: как исполнять пакет в Codex GPT-5.6 Sol-сессиях

## 1. Модель исполнения

- **Одна Codex-сессия = один слайс.** Промт слайса из `prompts/` вставляется в НОВУЮ чистую сессию
  целиком. Никакого «сделай весь H1 за раз»: H1_00_MASTER_ORCHESTRATION_PROMPT.md — карта и
  диспетчер, не рабочее задание.
- **Первая сессия**: `prompts/H1_01_TRAINER_POLICY_AND_GUARDRAILS.md` (соответствует слайсу H1.0).
  Затем H1_02→H1_04 (скиллы), затем H1_05→H1_08 (интеграции; параллелизуемы разными сессиями),
  затем H1_09 (owner-live + closure). Нумерация промтов сдвинута на +1 от номеров слайсов
  (H1_01 = слайс H1.0 и т.д.) — фиксированные имена файлов из промта владельца сохранены.
- **H2-промты BLOCKED UNTIL H1 CLOSURE** — исполнять только после G-H2-START (STATUS.md — истина).
- **H3** — только `H3_RND_EVALUATION_PROMPT.md` с подставленным чартером; **P11** — только
  `P11_PLATFORM_TRACK_DECISION_PROMPT.md`, вне цепи H1/H2.

## 2. Обязательные правила каждой сессии

1. **Живое состояние сначала.** План — не факт реализации: перед работой проверить HEAD, версию,
   фактическое состояние файлов/инструментов/STATUS.md. Расхождение с пакетом → зафиксировать в
   отчёте; существенное расхождение → остановиться и вернуть вопрос владельцу, не «чинить план на лету».
2. **Scope слайса не расширяется.** Соседние улучшения «заодно» — в отчёт как предложения, не в код.
3. **Не начинать следующий слайс** без CLOSED предыдущего блокирующего (STATUS.md).
4. **После кода**: тесты (с выводом), документация, commit+push; при деплое — прод-верификация
   (Coolify собирает по push в main; ждать образ на хосте, проверить healthz + инструмент вживую).
5. **Найденные unrelated production-баги** — отдельный отчёт/коммит с явным описанием; не чинить
   молча внутри слайса и не маскировать.
6. **Запрещено объявлять SHIPPED/CLOSED** без артефактов соответствующего гейта (10).
7. **STATUS.md обновляется в каждой сессии** — это единственный канонический леджер прогресса.
8. Инварианты W0/W1/провенанс/R16/R11 — в каждом промте; их нарушение не может быть «оптимизацией».

## 3. Проектные ловушки (Codex их не знает — перечислены и в промтах)

| Ловушка | Правило |
|---|---|
| MCP-клиенты кешируют схемы (additionalProperties:false) | НЕ мутировать существующие схемы; только новые инструменты; CAPABILITY_VERSION не бампить |
| Hermes listChanged:false | После добавления инструментов: `docker restart hermes-agent hermes-webui` + новая сессия агента |
| Compose требует HERMES_WEBUI_PASSWORD | Запуск стека — через start-hermex.ps1; голый `docker compose up` упадёт |
| Новые UI-строки LinguistPro | tt(key, fallback) + ключи во ВСЕ три локали ru/en/he + SW CACHE_VERSION bump |
| Миграции | `migrations/NNN_*.sql`, следующий номер = реальному следующему индексу; одна миграция = одна транзакция; без BEGIN/COMMIT в .sql; перед рискованным — db:backup |
| UPSERT | Только ON CONFLICT DO UPDATE SET <свои колонки>; INSERT OR REPLACE стирает чужие |
| Ослабление любого гейта/условия | gate-consumers sweep: grep всех потребителей по всем поверхностям |
| Смоук завис | Диагноз: сироты headless-chrome/node → убить и перезапустить; не «CPU виноват» |
| Прод-деплой | Может зависнуть на старом коммите → cancel в Coolify UI; transient 404 при rolling-update → подождать |
| G:\HERMES_AGENT | НЕ git: канон артефактов — в LinguistPro-репо, там только рабочие копии |
| Секреты | Ключи/координаты прода — в env/.claude/PROD_OPS_PRIVATE.md; в git и промты не попадают |

## 4. Формат итогового отчёта сессии (единый)

1. Слайс и промт-файл; 2. HEAD до/после; 3. созданные/изменённые файлы; 4. тесты и их вывод
(команды); 5. гейты пройденные, с артефактами; 6. owner-live статус (что осталось владельцу);
7. инциденты/unrelated-находки; 8. обновление STATUS.md (диф); 9. что блокирует следующий слайс.

## 5. Что делать при провале слайса

Провал (no-go/rollback-порог из 08) — валидный исход: откатить по rollback-инструкции слайса,
зафиксировать в STATUS (BLOCKED/NO-GO + причина), НЕ выключать соседние работающие слайсы, вернуть
решение владельцу. Не переизобретать дизайн слайса внутри сессии — предложения в отчёт.
