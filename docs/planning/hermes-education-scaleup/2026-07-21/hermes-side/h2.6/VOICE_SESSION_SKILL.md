# Асинхронная голосовая сессия LinguistPro

Это голосовая надстройка над `linguistpro-conversation-session`, а не замена текстового режима.
Перед первым ходом загрузи этот skill, `linguistpro-conversation-session` и обязательную
`linguistpro-trainer-policy`. Не оценивай произношение: ASR даёт только гипотезу текста.

## FAIL-CLOSED TOOL GATE — выполни раньше любого ответа о файле

1. Единственный источник transcript — успешный фактический tool result
   `mcp__ivrit_asr__transcribe_audio` в текущем ходе. Сначала вызови его; только потом разрешено
   писать, что файл прочитан, называть длительность, текст, сегменты или confidence.
2. Если полного callable-имени нет в доступных tools либо вызов не состоялся, ответь
   `ASR недоступен; transcript не получен` и сразу перейди в failure-порядок ниже. Не пытайся
   «найти способ» вызвать ASR.
3. Для получения transcript или проверки аудио **запрещены** `terminal`, `execute_code`, Python,
   ffmpeg, чтение файла, shell, внешний API, мок и «симуляция». Не выдумывай tool result по имени
   файла, prompt-тексту или общим знаниям.
4. Valid tool result обязан содержать `schema_version:"asr.transcribe.1.0.0"` и
   `confidence_note:"ASR_HYPOTHESIS_NOT_GROUND_TRUTH"`. Иначе считай вызов неуспешным и не показывай
   transcript. Разрешённые значения segment confidence — только `NORMAL` и `LOW`; `HIGH` не существует.

Для каждого голосового сообщения проходи только вперёд:

`VOICE_INTAKE → LOCAL_ASR → TRANSCRIPT_PREVIEW → WAIT_CONFIRMATION → CONFIRMED_UTTERANCE → H1.1_STATE`

Следующий голосовой файл всегда снова начинает `VOICE_INTAKE`. Ни смысловой ответ, ни recast, ни
разбор нельзя строить до `CONFIRMED_UTTERANCE` текущего файла.

## VOICE_INTAKE

1. Принимай ровно один явно названный файл на сообщение. Путь должен быть внутри
   `/workspace/voice-inbox`; не ищи файлы по всему workspace и не обрабатывай inbox пакетом.
2. Предпочтительный и проверенный owner-формат — `.wav`. Допустимы поддерживаемые локальным
   decoder форматы `.m4a`, `.mp3`, `.ogg`, `.flac`, `.webm`, но не утверждай, что конкретный формат
   проверен на устройстве владельца, если это не было показано живым вызовом.
3. Рекомендуй имя без речевого содержимого: `voice-YYYYMMDD-HHMMSS.wav`. Не помещай transcript,
   тему или личные данные в имя.
4. Пройди FAIL-CLOSED TOOL GATE: вызови только `mcp__ivrit_asr__transcribe_audio` с точным путём и
   `language:"he"`. Не вызывай cloud STT, shell-транскрипцию или другой ASR.

## TRANSCRIPT_PREVIEW и WAIT_CONFIRMATION

1. Покажи полный `text` как гипотезу. Затем отдельно перечисли сегменты с `confidence:"LOW"`
   вместе с их временными границами и пометкой «неуверенно»; `avg_logprob` можно показать как факт,
   но не превращать в оценку речи.
2. Заверши preview одним вопросом: `Я расслышал «<полный текст>» — верно? Если нет, напиши
   исправленный вариант.` Не добавляй перевод, recast, объяснение ошибки или ответ по теме.
3. Оставайся в `WAIT_CONFIRMATION`, пока пользователь явно не подтвердит или не даст исправление.
   Содержательное продолжение без подтверждения сначала возвращай к этому вопросу.
4. Подтверждённый текст или полный исправленный вариант становится единственным
   `confirmed_utterance` текущего хода. Исправление пользователя полностью побеждает ASR; различия
   между ASR и исправлением — ошибки распознавания, никогда не ошибки ученика.
5. В контексте текущего чата веди для каждого voice-хода явный ephemeral ledger:
   `raw_asr_text`, `LOW_spans`, `confirmation: unchanged|corrected`, `confirmed_utterance`.
   Не достраивай этот ledger по смыслу поздних реплик. Любая реплика, которую пользователь сам
   напечатал уже в `CONVERSATION`, имеет источник `TYPED` и **никогда** не становится ASR-текстом,
   даже если она неясна, содержит ошибку или потребовала `CLARIFY`.

## Переход в разговорную машину H1.1

1. Сразу после первого `confirmed_utterance` и **до любого profile/due вызова или содержательного
   ответа** фактически вызови `skill_view({"name":"linguistpro-conversation-session"})`. Успешный
   tool result — обязательный H1.1 LOAD GATE; упоминание skill по памяти его не заменяет. Если
   skill недоступен, скажи `Разговорный протокол H1.1 недоступен` и остановись, не импровизируй
   state machine.
2. Только после успешного LOAD GATE выполни SETUP H1.1: `get_learner_profile`, затем
   `get_due_review_items`; due-список остаётся скрытым. Само подтверждённое голосовое высказывание
   считается явным выбором темы. Personal-first grounding нужен только если пользователь просит
   строить разговор по личной песне/тексту.
3. Продолжай по H1.1: `CONVERSATION ⇄ CLARIFY/RECAST → POST_ANALYSIS → RETRY → CLOSURE`. Каждый
   ответ после подтверждения — максимум два предложения. Следующий voice-файл снова проходит
   preview/confirmation до содержательного ответа.
4. В `POST_ANALYSIS` используй только `confirmed_utterance` каждого хода. Отдельно назови
   `Где ASR мог расслышать неверно` и заполняй этот раздел **только** из `LOW_spans` либо различий
   `raw_asr_text` с пользовательской правкой в voice-ledger. Неясные/ошибочные `TYPED`-реплики
   сюда не попадают. Если voice-preview был подтверждён без правки и не имел `LOW`, напиши:
   `Подозрительных мест ASR в подтверждённом voice-ходе не обнаружено.` Не смешивай этот раздел
   с форматом `сказал → корректно → почему` и не приписывай ASR-различия пользователю.
5. Если пользователь исправил transcript, первоначальную ASR-форму не анализируй, не recast'и и
   не цитируй как его речь. Если подтверждения нет, этот ход вообще не входит в разбор.

## ASR failure → текстовая деградация

1. При typed-ошибке или отсутствии ASR назови код/недоступность один раз, не ретрай и не переключайся
   на облачный сервис. Скажи, что разговор может продолжиться текстом.
2. H2.5 удаляет raw только после успеха. Поэтому при неуспехе явно скажи:
   `Файл не был удалён автоматически — удали его из voice-inbox, затем напиши ту же фразу текстом.`
   Не продолжай учебный разбор, пока пользователь не подтвердит удаление или сам не удалит файл.
3. Напечатанная пользователем замена становится `confirmed_utterance`; дальше работает обычный
   H1.1 text-mode без снижения качества или обвинения пользователя в сбое ASR.

## W0/W1, retention и TTS

1. Transcript и исправления живут только в текущем чате. Не записывай их в memory, notes, файлы,
   профиль или LinguistPro; не включай полный transcript в итоговый `propose_action`.
2. `propose_track_word` допустим только после отдельного согласия владельца. Для голосовой речи:
   `evidence:"USER_PRODUCED_SPEECH"`; если surface пришёл из первоначально LOW-сегмента и владелец
   не перепечатал его явно, добавь `caveat:"POSSIBLE_ASR_ERROR"`. Не передавай `context_snippet`.
3. Не создавай запись автоматически и не объявляй exposure mastery. Все W1-предложения ждут
   подтверждения владельца в LinguistPro.
4. Ответ по умолчанию текстовый. Существующий product-TTS handoff можно предложить только по
   явному запросу и только для уже доступного reading-content; не создавай новый TTS-канал и не
   озвучивай произвольный chat-ответ обходным способом.

## Метрики без скрытого хранения

В конце owner-live можно сообщить только счёт текущего чата: число завершённых preview, число
preview с пользовательской правкой и сумму минут по максимальному `end_s` ASR-сегментов.
`ASR correction rate = исправленные preview / все подтверждённые preview`. Эти числа владелец
вручную переносит в H2.6 EVIDENCE; сам skill ничего долговременно не пишет.
