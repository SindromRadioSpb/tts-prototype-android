## BLOCKER

### B1 [R14] §6 (+§3.1, §9 CLG-P2) — Content-only event id + сохранённый PRIMARY KEY id → детерминированная кросс-тенантная коллизия и молчаливая потеря чужой памяти

**Опровержение:** Живой код: lemma-canon.js:125-131 строит id как sha1(item_key|reviewed_at|grade|source|channel) БЕЗ user_id; seed-события имеют id 'seed:<item_key>' (чистая лемма, без времени и пользователя). §6 говорит «серверный review_log — та же схема, что клиентский (id/item_key/...) плюс серверные колонки», а §3.1 строит серверный дедуп на 'INSERT OR IGNORE, дедуп между устройствами бесплатно' → id остаётся единственным PRIMARY KEY на общей таблице всех тенантов. Сценарий: пользователь A и пользователь B оба сидируют лемму להתקדם → оба генерируют id 'seed:להתקדם' → второй INSERT OR IGNORE молча отбрасывается, выжившая строка несёт user_id ПЕРВОГО. Ровно то же для любого совпадения (одна due-лемма, одна секунда reviewed_at, тот же grade — а бинарный цикл Зала пишет всего grade 1|3, крошечное пространство значений). Гейт CLG-P2 «повторный ingest той же пачки = 0 новых строк» ПРОЙДЁТ, пока идёт кросс-тенантная потеря: он не проверяет двух разных пользователей с одинаковым контентом. Результат: память слова пользователя B исчезает, replay FSRS у A/B считается по чужим строкам — порча канона.

**Предложенный fix:** Явно зафиксировать в §6: серверный PRIMARY KEY = составной (user_id, id) ЛИБО user_id вплетается в хэш id перед серверным ingest (не как клиентский id). Добавить в гейт CLG-P2 обязательный тест кросс-тенантной изоляции: два user_id с идентичным контентом события → ДВЕ строки, ни одна не подавлена INSERT OR IGNORE. Seed-события ('seed:<item_key>') обязаны неймспейситься по user_id на сервере.

### B2 [R14] §7 (+§13.4, §9 CLG-P2) — Ingest доверяет user_id из тела/аргумента клиента и агента → запись событий в чужой тенант

**Опровержение:** §7 задаёт инструменты с user_id КАК ПАРАМЕТРОМ: get_due_words(user_id, limit), create_review_task(user_id, word_ids), record_review_answer(...). §13.4 маршрутизирует записи stateless agent-воркера «через Cloud API» с передачей user_id аргументом. Нигде в доке не сказано, что Cloud API ВЫВОДИТ user_id из аутентифицированного принципала и ИГНОРИРУЕТ/ОТКЛОНЯЕТ user_id из конверта события. Сценарий: скомпрометированный или враждебный клиент (или сам agent-сервис, у которого нет пользовательской сессии — он stateless worker) шлёт ingest-пачку с event.user_id = чужой → сервер, доверяя полю, пишет review-события и отдаёт due/known/личные тексты (класс C) за любого пользователя. Гейт CLG-P2 проверяет только идемпотентность, не авторизацию — дыра пройдёт гейт. Это прямое нарушение инварианта tenant isolation (R14: «А не пишет за Б»).

**Предложенный fix:** В §6/§7/§13.4 прописать инвариант: сервер выводит user_id ТОЛЬКО из аутентифицированной сессии/принципала; конвертное поле user_id, не совпадающее с принципалом, → 403 (reject, НЕ молчаливый remap). Для agent-сервиса — Cloud API принимает не «user_id-аргумент», а делегированный токен пользователя с ограниченным scope. Добавить в гейт CLG-P2 тест: запрос с сессией A и телом user_id=B → 0 строк записано, 403.

### B3 [R14] §8 (+§9 rate limits, §1.4) — Pairing-code: одноразовость+TTL не защищают от брутфорса/перехвата → захват канала владельца

**Опровержение:** §8 задаёт код «одноразовый, TTL» без указания энтропии, без лимита попыток на код, без привязки к сессии, которая код сгенерировала; §9/§11 откладывают ВСЕ rate limits до G-EXT (а Telegram P7 — задолго до G-EXT). Бот публичный (любой Telegram-аккаунт достигает его). Сценарий брутфорса: атакующий шлёт боту '/pair <guess>' в цикле в пределах TTL; в owner-only фазе единственный user_id — владельца, поэтому первое попадание привязывает telegram_user_id АТАКУЮЩЕГО ↔ user_id владельца → атакующий получает due-слова, историю чтения, личные тексты (класс C) владельца и инжектит review-события в канон. Одноразовость НЕ спасает от перехвата (задача: «достаточны ли против перехвата»): код показывается в веб-вкладке и не привязан к инициатору, так что перехвативший/подсмотревший submit'ит ПЕРВЫМ и выигрывает гонку у легитимного пользователя. 6-значный код при отсутствии лимита попыток вскрывается за минуты.

**Предложенный fix:** §8: код высокой энтропии (≥128 бит, не 6 цифр); жёсткий лимит попыток на код + глобальный лимит /pair на бота С МОМЕНТА P7 (не G-EXT); привязка pairing к аутентифицированной веб-сессии, сгенерировавшей код, и двусторонний confirm (подтверждение в веб-UI, что привязался ожидаемый chat_id); немедленная инвалидция кода при первом неверном формате. Переклассифицировать «rate limits до G-EXT отсутствуют» → «rate limits обязательны с введения каждого публичного эндпоинта».

### B4 [R15] §1.3-1 vs §5/§9 CLG-P1 — Прямое противоречие: «review_log append-only — событие никогда не удаляется» vs «удаление аккаунта с первого дня»

**Опровержение:** §1.3-1 объявляет неприкосновенным каноном: «Событие никогда не редактируется и не удаляется». §5 и гейт CLG-P1 требуют работающее удаление аккаунта «с первого дня». Сценарий провала: пользователь запрашивает удаление аккаунта → реализатор, следуя канону §1.3 буквально, делает soft-delete/деактивацию, оставляя строки review_log (с meta_json, содержащим surface-формы и text_key личных текстов — подтверждено живым кодом library-ui.js gradeReadingTap) на сервере навсегда → GDPR Art.17 нарушен, R15-красный флаг «удаление, которое что-то оставляет» сработал на собственном каноне программы. Обратная реализация (физическое удаление строк) нарушает канон §1.3. Любая реализация ломает одно из двух обязательных требований — дизайн не даёт правила выбора.

**Предложенный fix:** Внести в §1.3-1 явный carve-out: append-only действует В ПРЕДЕЛАХ живого аккаунта (запрет редактирования/выборочного удаления событий); удаление аккаунта = физическое удаление ВСЕГО стрима user_id (event-sourcing 'forget-the-stream'), включая review_log, learner_events, srs_projections, seed-строки. Добавить в гейт CLG-P1 проверку: после delete replay по user_id пуст и никакая таблица не содержит строк с этим user_id.

### B5 [R15] §5 / §4.4 / §6 — review_log.meta_json — контентный канал класса C внутри «всегда хранимого» класса A, минующий consent

**Опровержение:** §5 относит review_log целиком к классу A («хранится на сервере всегда»), а полные личные тексты — к классу C («ТОЛЬКО явный opt-in»). Но собственный пример дока §4.4 кладёт в meta_json ответ пользователя и ожидаемый текст ({"answer":"מתקדם","expected":"להתקדם","sentence_id":"s_456"}), а живой код уже сегодня пишет туда контент: library-ui.js gradeReadingTap → meta.surface (словоформа из читаемого текста) + meta.text_key; room-recall → meta.surface. Сценарий провала: пользователь загрузил личное медицинское письмо в «Мои тексты», НЕ дал ни одной галочки класса C, тренирует слова из него через reading-tap/диктант → события review (класс A) автоматически синхронизируются и несут на сервер словоформы, expected-фразы и идентификаторы личного текста. Consent-модель §5 обойдена самим дизайном; попутно item_key (леммы редкой чувствительной лексики — диагнозы, юр. термины) раскрывают содержание непосинхронизированных текстов.

**Предложенный fix:** Определить в §6 sync-политику meta_json: серверный ingest принимает только allowlist ключей (grade-метаданные, keyer_version, scheduler, ts_clamped, идентификаторы); контентные поля (answer/expected/surface/фразы) для событий, чей источник — не-consented класс C, при синке вырезаются или хэшируются (локальная копия остаётся полной). Прецедент уже в кодовой базе: research-mode server-side recursive forbidden-field check. Добавить гейт CLG-P2: ingest-валидация отклоняет неразрешённые meta-ключи. В consent-copy класса A раскрыть, что синк переносит леммы/item_key тренируемых слов.

### B6 [R2] §2.2/§4.4/§7/§9 (гейт CLG-P7) — Фаллибельный машинный грейдер получает право необратимой записи в append-only канон — без гейта точности и без компенсационной семантики

**Опровержение:** Диктант/cloze в чате: «честная проверка» = машинная оценка ответа, результат — событие grade в review_log (§4.4 пример: grade 1). Инвариант §1.3-1: событие никогда не редактируется и не удаляется. Сценарий: ожидается אישה (ktiv male), юзер пишет אשה (ktiv haser, корректно без никуда) — наивный компаратор или LLM метит «неверно» → grade 1 = lapse навсегда в каноне; при систематическом дефекте компаратора (ktiv-варианты, matres lectionis, конечные буквы) — сотни ложных lapse-событий на живом профиле владельца, стабильности известных слов рушатся, due-лист заполняется словами, которые юзер знает («он даёт случайные упражнения» — прямое убийство премиум-критерия §2.4). Гейт CLG-P7 проверяет только сантехнику («/review → ответ → review_log → Зал видит»), точность грейдинга не гейтится нигде; механизма аннулирования ошибочного события в доке нет. Anki-прецедент не спасает: там грейды — самооценка юзера, здесь — машинное суждение об эквивалентности ивритских строк, новый класс писателя с новым режимом ошибки, а док подаёт его как «ещё один такой канал» (§3.1).

**Предложенный fix:** До CLG-P6 вписать в §7: (1) детерминированная нормализация ответа ПЕРВОЙ — skeleton-сравнение без никуда + эквивалентность ktiv male/haser через резолвер (норма проекта уже существует: cloze keyed by skeleton); LLM никогда единолично не решает верность, только формулирует фидбек; (2) grader-accuracy gate в CLG-P7: gold-набор ответов (включая ktiv-пары, огласовочные варианты, near-miss формы) с порогом точности до права записи grade; (3) решить компенсационную семантику канона (amend/void-событие, учитываемое редьюсером, или meta-flag) — ДО первого агентского write, не после первого инцидента.

### B7 [R12] §6 (+§4.4) — review_answered/dictation_answered имеют ДВА дома: learner_events и review_log; владелец review-фактов не определён, диаграмма §4.4 рисует learner_events → review_log

**Опровержение:** §6 включает review_answered и dictation_answered в примерный поток learner_events, при этом review_log объявлен отдельной таблицей-зеркалом мигр. 41, а диаграмма §4.4 рисует learner_events как ПРИТОК review_log (чего в клиентской архитектуре нет — клиенты пишут review_log напрямую). Сценарий: Mini App на один ответ диктанта пишет learner_event 'dictation_answered' И review_log-строку → один ответ учитывается дважды в weak_patterns/аналитике; либо две записи расходятся по grade (баг в одном из путей), и не определено, которой верит FSRS-replay. Это «два дома одного факта» — прямое нарушение собственного §4.7 и урока мигр. 040 («no dual home for the same fact»).

**Предложенный fix:** Объявить review_log ЕДИНСТВЕННЫМ домом review-семантики; вычеркнуть review_answered/dictation_answered из списка learner_events (или явно определить их как уведомительные события, которые replay/метрики/проекции памяти НИКОГДА не читают); исправить диаграмму §4.4: learner_events и review_log — два параллельных append-only потока, стрелки learner_events→review_log нет.

### B8 [R12] §3.1 (+§4.3) — «Дедуп между устройствами бесплатно» ложен для kind='seed': id 'seed:<item_key>' identity-детерминированный, не content-детерминированный — merge молча выбрасывает проигравший снапшот

**Опровержение:** Живой код: seed id = 'seed:'+item_key (public/js/library-ui.js:1753, public/db/local-db.js:4094; «a word can only ever seed once» по PK), а replay стартует с seed-watermark (fsrs-core.js). Сценарий: ПК лениво сидирует слово X из богатого SM2-снапшота (seed:X, высокая S); телефон офлайн ДО первого down-sync помечает X как l1 → пишет СВОЙ seed:X (seed-manual, низкий) + две оценки; при merge INSERT OR IGNORE молча выбрасывает второй снапшот (истина = кто первый пришёл) → серверный replay телефонных оценок стартует с чужого снапшота → server replay ≠ browser replay: гейт CLG-P4 падает или, при проверке только на одном профиле владельца, молча расходится. Претензия §3.1 «content-детерминированный id → INSERT OR IGNORE, zero loss» кодом опровергается для seed-строк.

**Предложенный fix:** До CLG-P2 специфицировать merge-семантику seed: либо content-hash в id (seed:<item_key>:<sha1(snapshot)>) + детерминированное правило выбора watermark в replay при НЕСКОЛЬКИХ seed одного item; либо объявить seed device-local (не синкается) + правило, из чего сервер сидирует item при первом ingest. Добавить кейс «два разных seed одного item_key с разных устройств» в lossless-гейт CLG-P3.

### B9 [R12] §4.7 (+§4.3, §5) — Трихотомия event/projection/cache не вмещает существующее asserted-состояние (ручные статусы T-a, ручные переводы, text_user_meta); §5 мислейблит known/learning как «derived»

**Опровержение:** Ручные статусы Track-any-word (l1–l4 на любом слове, shipped v3.11.14) НЕ выводимы из лога: seed-once по PK означает, что смена l2→l4 или снятие пометки ПОСЛЕ первого seed не оставляет следа в review_log. §4.7 говорит «третьего не дано», §5 называет known/learning «derived» — по букве дока имплементатор обязан счесть статус проекцией (тогда ручные пометки владельца невосстановимы из лога) или завести четвёртую категорию, которую док запрещает. Сценарий: владелец за месяцы вручную пометил сотни слов; migration dry-run CLG-P3 валидирует ТОЛЬКО review_log (count/checksum/replay) → при canon-флипе ручные статусы теряются/клобберятся молча, гейт зелёный. Заодно опровергается §4.3 «конфликт-модель тривиальна по построению» — она тривиальна только для append-only потоков, а mutable asserted-состояние (статусы, заметки, text_user_meta, studio drafts, которые агент правит с сервера, а пользователь — в браузере) конфликт-модели не имеет вообще.

**Предложенный fix:** Добавить в §4.7 четвёртую легальную категорию «asserted user state» с явной sync-моделью (например, status_set-события + LWW-редьюсер по created_at_client — состояние снова становится проекцией лога); исправить §5 (known/learning = смесь asserted+derived); включить word_status (ручные пометки), text_user_meta, заметки и переводы в чек-лист migration dry-run CLG-P3; для class-B mutable артефактов явно зафиксировать конфликт-модель или вывести их из scope sync v1.

### B10 [R11] §3.1 / §4.3 / §6 — «Глобально-уникальные» event-id детерминированно коллидируют между пользователями — INSERT OR IGNORE на multi-tenant сервере молча съедает чужие события

**Опровержение:** Док утверждает: id «глобально-уникальный… серверный ingest = INSERT OR IGNORE, дедуп между устройствами бесплатно» и переносит клиентскую схему на сервер, добавляя user_id лишь колонкой (§6), не переопределяя ключ уникальности. Но `seed:<item_key>` (local-db.js:4094) — это буквально `seed:` + каноническая лемма: пользователь А сидирует שלום → строка `seed:שלום` записана; пользователь Б сидирует то же слово → его seed с ДРУГИМ SM2-снапшотом в meta_json тихо игнорируется по PK → replay Б для שלום стартует без seed-watermark → неверные S/D/due у Б из его же корректных данных. `anki:<epoch-ms>` коллидирует между пользователями вероятностно (Anki reviewId — миллисекундный таймстамп ревью, уникальный только внутри одной коллекции), а `app:<sha1>` (lemma-canon.js:125-131) хэширует item_key|reviewed_at|grade|source|channel — без user-scope. Гарантированная тихая потеря событий при втором же пользователе; она же ломает будущий серверный Anki-ingest (двойной путь client+server дедупится корректно ТОЛЬКО при user-scoped ключе).

**Предложенный fix:** В §6 явно зафиксировать: уникальность серверного review_log и learner_events = UNIQUE(user_id, event_id), НЕ глобальный PK по id; вся idempotency ingest-пачек и пре-чек «exists» — user-scoped. В §3.1 исправить формулировку: id уникальны В ПРЕДЕЛАХ пользователя. Добавить в гейт CLG-P2 тест: две учётки ингестят одинаковый `seed:<item_key>` → обе строки сохранены. Для будущего серверного Anki-канала — норма: id выводится тем же правилом `anki:<reviewId>`, чтобы клиентский и серверный ingest одного ревью дедупились, а не двоились.

### B11 [R11] §4.4 / §6 (два времени) vs живой replay — Пример события в §4.4 вводит non-UTC offset в reviewed_at, а канон-replay упорядочивает события лексикографически — смешение форматов фолдит корректные события в неверном хронологическом порядке

**Опровержение:** Весь живой канон пишет reviewed_at через toISOString() — UTC Z с миллисекундами (local-db.js:2614, 4094, 4099), а replay полагается на SQL `ORDER BY reviewed_at ASC, id ASC` — лексикографический сорт TEXT (getReviewLog, local-db.js:2502; fsrs-core.replay ожидает уже упорядоченные строки). Нормативный пример агентского события в §4.4 задаёт `"reviewed_at": "2026-07-04T20:10:00+03:00"`. Сценарий: Telegram-событие «2026-07-04T20:10:00+03:00» (=17:10 UTC) и браузерное «2026-07-04T18:00:00.000Z» (=18:00 UTC, ПОЗЖЕ). Лексикографически «18:00:00Z» < «20:10:00+03:00» → replay фолдит позднее событие первым → неверные elapsed/S/D/due из двух ВЕРНЫХ событий. Оракул «server replay == browser replay» это не ловит — обе стороны сортируют одинаково неверно.

**Предложенный fix:** В §6 зафиксировать канонический формат: reviewed_at/created_at_client — ТОЛЬКО UTC ISO-8601 с суффиксом Z и мс (формат toISOString()), для всех каналов включая agent/Telegram; ingest-валидация отклоняет/нормализует иные offset-формы. Исправить пример §4.4. Альтернатива/дополнение: серверный replay упорядочивает по распарсенному epoch + tie-break по id, а не по строке; в CLG-P4-гейт добавить фикстуру со смешанными offset-формами.

### B12 [R13] §3.1 + §4.3 (и гейты §9 CLG-P3/P4) — PK 'seed:<item_key>' коллидирует между устройствами, а seed-watermark replay делает слияние логов НЕкоммутативным — канон молча теряет выученное

**Опровержение:** Док утверждает: «id content-детерминированный → серверный ingest = INSERT OR IGNORE, дедуп между устройствами бесплатно» (§3.1) и «конфликт-модель тривиальна по построению» (§4.3). Живой код опровергает: seed-строки минтятся с id 'seed:'+itemKey БЕЗ девайс-компонента и без хэша содержимого в трёх путях (local-db.js:4094 studio-trainer, library-ui.js:2693 manual-mark, library-ui.js:2750 reading-tap), а replay (fsrs-core.js:209–214) игнорирует ВСЕ строки до последней seed-строки. Сценарий: ПК-профиль владельца — слово X, seed:X@2026-06-20 (SM2-снапшот interval=12) + 10 FSRS-ревью до 07-04; телефон-профиль — то же слово конвертировано позже, свой seed:X@2026-07-03 с другим снапшотом. Оба синкают в один user_id. INSERT OR IGNORE оставляет seed:X того устройства, чей ingest пришёл ПЕРВЫМ: (а) если выжил телефонный seed@07-03 — watermark отбрасывает все 10 ПК-ревью из state, канонический srs_projection сбрасывает слово на слабый снапшот, и после §4.6-флипа этот НЕВЕРНЫЙ state — канон, перетирающий верный ПК-кэш при projection refresh; (б) если выжил ПК-seed — SM2-история телефона молча выброшена. В обоих случаях replay(union) ≠ stored любого устройства — оракул CLG-P4 в принципе непроходим при двух девайсах. Даже уникализация id не чинит: два seed-lineage в одном логе → watermark всё равно отбрасывает более раннюю ветку. Попутно: инвентарь id в §3.1 неполон — Studio-тренер минтит 'sre:'+crypto.randomUUID() (local-db.js:4099), не content-детерминированный.

**Предложенный fix:** До CLG-P2 задизайнить мульти-девайс-семантику seed-строк: (1) id seed-строки — девайс-скоупный или content-hashed ('seed:<item_key>#<device_id>' или sha1 от meta), чтобы обе строки выживали в union; (2) правило replay для нескольких seed одного item_key (напр. «действует самый РАННИЙ seed; более поздний seed игнорируется, если между ними уже есть review-строки» — earliest-wins сохраняет всю историю); (3) расширить гейт CLG-P3: обязательный merge-тест ДВУХ реальных профилей владельца (ПК+телефон) с пересекающимися item_key и разными seed-моментами, оракул replay(union) без потери review-строк из state; (4) исправить формулировки §3.1 (id-инвентарь + убрать «дедуп бесплатно» для seed) и §4.3 («тривиально по построению» — только для review/skip-строк).

### B13 [R13] §5 (класс A) + §6 + §4.7 + гейт CLG-P3 — Ручная ось word_status (l1–l4/known/ignore) — asserted-состояние ВНЕ трихотомии §4.7: у неё нет ни канала миграции в облако, ни merge-правила, ни места в серверной модели §6

**Опровержение:** Док в классе A называет known/learning «derived», а §4.7 постулирует «любое состояние = event | derived projection | local cache». Живой код опровергает: ручной статус — АВТОРИТЕТНОЕ asserted-состояние (manual-wins overlay поверх SRS, local-db.js getKnownWordStates ~2258–2266), пишется чистым UPSERT без события (setWordStatus, local-db.js:2276+), причём known/ignore осознанно НЕ сидируются в review_log (reader-morph.js:2135 «known/ignore/new → null … per owner: NOT seeded») — из лога эта ось невосстановима. В §6 нет таблицы для неё, в примерах learner_events нет word_marked, dry-run CLG-P3 покрывает только review_log (count/checksum/replay). Сценарий: владелец пометил ~500 слов known/ignore на ПК и ~200 (частично конфликтующих) на телефоне. После CLG-P3+P4 сервер объявлен каноном, но ручной оси в нём нет → CLG-P5 getKnownWords/getDue и агент (P6/P7) работают по неполному state: Telegram-наставник гоняет слова, которые владелец явно пометил ignore, и считает «известные» слова неизвестными (i+1-подбор текстов ломается). Либо реализация добавит наивный whole-table-синк word_status по updated_at → LWW при clock skew: телефонные 200 строк перетирают ПК-шные 500 → массовая потеря ручной разметки, а это годы кликов владельца.

**Предложенный fix:** Правка дока ДО кода: (1) честно переклассифицировать ручную ось в §5 как asserted user state (не derived); (2) ввести событие пометки (word_marked в learner_events или kind='mark' в review_log-подобном логе) с created_at_client, и определить серверную проекцию status = LWW по created_at_client поверх слитого потока пометок; существующие word_status-строки бэкфиллятся синтетическими mark-событиями при миграции; (3) включить word_status в dry-run гейт CLG-P3 (count + checksum + parity ручного overlay до/после); (4) добавить merge-правило конфликтующих пометок двух устройств в спецификацию sync bridge.

### M4 [R14] §13.1 — Session cookie возвращает CSRF, который кодовая база сознательно не делала; в доке ноль cookie/CSRF-требований

**Опровержение:** server.js:369-370 фиксирует текущую модель: «We deliberately don't add a CSRF token — there are no per-user sessions to scope it to». §13.1 вводит session cookie → эта предпосылка аннулируется, но док не переоткрывает её. На одном домене окажутся ДВЕ модели: header-token (X-Audio-Upload-Token) — CSRF-иммунна (кастомный заголовок нельзя послать кросс-ориджин без preflight+CORS), и cookie для learner-state — CSRF-подвержена. Док не задаёт ни SameSite, ни Secure/HttpOnly, ни CSRF-токен, ни TTL/ротацию сессии, ни аудит существующих state-changing эндпоинтов (напр. /api/srs/sessions/*), которые начнут honor'ить cookie. Сценарий: владелец залогинен (cookie без SameSite), заходит на сайт атакующего, тот делает fetch('/api/ingest',{credentials:'include', ...}) — если эндпоинт добавлен без requireSameOriginJson (guard проектировался под мир без сессий) или принимает simple content-type, запрос форжится от имени владельца в канон.

**Предложенный fix:** §13.1: session cookie обязательно SameSite=Lax (Strict для мутаций) + Secure + HttpOnly; TTL + ротация; сохранить Origin/Referer-guard И добавить CSRF-токен для cookie-аутентифицированных мутаций; провести sweep ВСЕХ эндпоинтов, которые будут видеть аутентифицированную cookie, и явно отметить, что старый инвариант server.js:369 более не действует.

### M5 [R14] §13.1 (+§9) — Bootstrap secret: нет порога энтропии, нет анти-брутфорса на фронт-двери, риск утечки в логи

**Опровержение:** В отличие от AUDIO_UPLOAD_TOKEN (док/код требуют ≥32 случайных байта + IP-fail-limiter _audioUploadAuthFails + timingSafeStrEqual, server.js:1276-1327), для bootstrap secret / invite-code §13.1 НЕ задаёт ни энтропийного порога, ни timing-safe сравнения, а §9 откладывает rate limits до G-EXT. ### M6 [R14] §8 — Telegram webhook: «secret-token» ≠ подпись; нет дедупа update_id и ротации webhook-секрета → форжинг/replay апдейтов

**Опровержение:** §8 пишет «webhook с secret-token», трактуя это как подлинность. Но Telegram НЕ подписывает payload — есть лишь статичный bearer-заголовок X-Telegram-Bot-Api-Secret-Token. Привязка channel_links (проверка на каждом входящем) обеспечивает авторизацию, но НЕ подлинность транспорта.

**Предложенный fix:** §8: явно указать, что secret_token — bearer-only (высокая энтропия, только env, ротируется НЕЗАВИСИМО от bot-токена, с процедурой); HTTPS-only webhook; дедуп на update_id для ограничения replay; сохранить серверную проверку channel_links как авторизацию, но не выдавать secret-token за подпись payload.

### M7 [R14] §8 (P8 Mini App) — Mini App initData: нет проверки свежести auth_date → бессрочный replay чужой аутентификации

**Опровержение:** §8 требует «валидацию initData (подпись Telegram)», но не задаёт TTL на auth_date. HMAC initData считается по ключу, производному от НЕротирующегося bot-токена, поэтому перехваченная строка initData валидируется БЕССРОЧНО. Сценарий: атакующий однократно получает initData жертвы (расшаренная ссылка, утечка Referer, логирующий прокси) и переигрывает её на Cloud API как аутентификацию жертвы неограниченно долго. ### M31 [R11] §1.3-2 / §3.1 / CLG-P4 гейт (§9) — Replay-оракул CLG-P4 не независим: сервер и браузер исполняют ОДИН fsrs-core.js + lemma-canon.js — гейт «server == browser» соглашается сам с собой

### M32 [R11] §7 (грейдер) / §6 (схема события) — Грейдер-независимость покрывает только метрики, но не сам grade: LLM-тьютор, оценивающий ответ, пишет grade 1–4 в канонический append-only лог — «учитель судит сам себя», и отрава необратима

Схема события §6 не имеет поля провенанса оценки — постфактум LLM-graded строки даже не отличить от детерминированных.

В §7 добавить норму: для всех проверяемых форматов (диктант, cloze, reverse) грейд присваивает ДЕТЕРМИНИРОВАННЫЙ грейдер (нормализованное сравнение с никуд-каноном, наш пайплайн), LLM может только комментировать; LLM-грайдинг допустим лишь для свободных форматов и обязан быть помечен и фильтруем в FSRS-оптимизаторе/метриках. R17 утвердить до P6 — уже записано; сама схема провенанса grade должна попасть в §6 сейчас.

### M33 [R11] §4.6 / §4.7 / §4.2 — Пост-P4 окно двойного писателя локального srs_*-кэша: локальный replay (офлайн) и sync-pull серверных проекций пишут одни колонки с разных баз — стейл-pull воскрешает уже отвеченные слова

**Опровержение:** §4.2 определяет OPFS-проекции как «last known projections» (реплика канона), но офлайн-режим (заявленный там же) требует, чтобы клиент САМ пересчитывал проекции локальным replay после каждого офлайн-review — иначе due-кольцо мертво без сети. Итого после CLG-P4 у локального srs_* два писателя с разными входами: локальный replay (лог + pending outbox) и pull серверных проекций (лог БЕЗ ещё-не-доставленных событий). Сценарий: пользователь отвечает 5 слов офлайн → локальный replay ставит due=+3д; связь возвращается, sync-цикл делает pull раньше/параллельно ack push'а → серверная проекция (due=сегодня, посчитана до прибытия пачки) затирает свежий локальный расчёт → слова снова в due-кольце → пользователь их пере-отвечает → лишние события с elapsed≈0 в вечном логе. Это дословно воспроизводит уже прожитый урок «два писателя word_status.srs_*» (§4.7 сам на него ссылается), но в неописанном доком месте; §4.6 определяет, кто КАНОН, но не кто пишет локальный кэш.

**Предложенный fix:** Дополнить §4.6/§4.7 правилом владения локальным кэшем: локальный srs_* ВСЕГДА derived только от локальной реплики лога (server projections на клиент не спускаются вовсе — серверные проекции потребляют только agent/push/Mini App); либо, если pull проекций нужен, разрешить его строго при пустом outbox и cursor==head. Добавить в гейт CLG-P3/P4 тест race-сценария: офлайн-пачка + ранний pull → due-кольцо не показывает уже отвеченные слова.

### M34 [R11] §6 (два времени) / §1.3-1 — Дыра clock-skew: событие с будущим created_at_client навсегда отравляет replay, запрет «серверного времени в учебной математике» блокирует единственную возможную серверную защиту, а канон append-only не даёт механизма ремедиации

**Опровержение:** fsrs-core клампит только ОТРИЦАТЕЛЬНЫЙ elapsed (utcDayDiff → max 0), но не защищает от самого future-dated события: устройство с уехавшими на год часами пишет reviewed_at=2027 → в replay-порядке (reviewed_at ASC) это событие сортируется ПОСЛЕДНИМ при каждом пересчёте; elapsed от последнего реального ревью ≈ 365 дней → FSRS трактует как успешный recall после года → stability раздута, due уезжает в 2027+ → слово исчезает из повторений на год+. По §1.3-1 событие нельзя отредактировать или удалить — отрава перманентна, механизм исправления доком не определён. Клиентский Anki-ingest УЖЕ клампит будущие ts по nowMs (local-db.js:2604-2605) — прецедент необходимости признан кодом, но серверный конверт §6 не задаёт никакой валидации, а буквальное чтение запрета «использование серверного времени в учебной математике запрещено» запрещает и sanity-clamp по ingested_at_server.

**Предложенный fix:** В §6 внести carve-out: ingested_at_server разрешён как SANITY-BOUND на ingest (валидация created_at_client ≤ ingested_at_server + допуск; нарушители — clamp или карантин с пометкой, единый режим для всех каналов), запрещён только как вход расписания. Определить канонический механизм ремедиации отравленных строк, не ломающий append-only: компенсирующее событие (kind='annul'/'correction' со ссылкой на event_id), которое replay обязан учитывать; добавить его в схему до CLG-P2, пока версия схемы события фиксируется.

### M35 [R13] §4.6 + §9 (CLG-P3 rollback, G-5) — Rollback специфицирован и гейтится только в CLG-P3 — в мире, где server-originated событий ещё НЕ существует; откат после P6/P7 не определён и стравливает Telegram-события в никуда

**Опровержение:** Единственный rollback-гейт программы — пункт dry-run CLG-P3 «rollback возвращает прежнюю local-only работу». На этапе P3 все события рождаются в OPFS, и откат тривиален по построению — гейт даёт ложную уверенность. Сценарий: после CLG-P7 владелец месяц отвечает на диктанты в Telegram — события source='agent:telegram' рождаются НА СЕРВЕРЕ и существуют только там (downstream-доставка в OPFS в §4.3 описана лишь как «projection refresh»; server→OPFS ingest СОБЫТИЙ не специфицирован, слово «inbox» в §4.6 упомянуто один раз без механизма и без гейта). Обнаружен серверный дефект/инцидент (прецедент: диск CX23 100% 2026-07-04) → решение откатиться в local-only. Процедуры нет: локальный лог не содержит месяц Telegram-ревью → локальный replay даёт state «слова месяц не повторялись», due-расписание регрессирует, replay==stored ломается — и это тихо, без единого красного гейта, потому что rollback-гейт был пройден на P3 и больше не перепроверяется.

**Предложенный fix:** (1) Специфицировать в §4.3 downstream event sync как симметричный первокласcный механизм: server→OPFS INSERT OR IGNORE тех же строк review_log, cursor в обе стороны; гейт «Telegram-событие появляется в ЛОКАЛЬНОМ OPFS-логе» — часть CLG-P7 (уточнить формулировку «Зал видит»: видит через локальный лог, не только через API); (2) определить rollback-процедуру пост-канон-флипа: финальный server→client экспорт всех server-originated событий + lossless-checksum ДО переключения канона назад; (3) rollback-drill повторяется на каждом гейте, вводящем нового серверного писателя (P6, P7, P8), а не единожды в P3.

### M36 [R13] §6 (конверт события) + §1.3 — KEYER_VERSION отсутствует в конверте события, а серверный re-key при бампе кейера противоречит append-only канону §1.3-1 — item_key-истории расщепляются на диалекты

**Опровержение:** lemma-canon.js:18–19 фиксирует инвариант: «bumping KEYER_VERSION WITHOUT a re-key migration of review_log/word_status fails the gate» — локально re-key = переписывание таблицы. На сервере §1.3-1 запрещает редактирование событий → серверная re-key-миграция невозможна без нарушения канона, и док это противоречие не разрешает. Одновременно конверт §6 (event_id/idempotency_key/schema_version/source_client_version/device_id/…) НЕ содержит keyer_version — он лежит только внутри meta_json, и никакая ingest-политика на несовпадение не задана. Сценарий: KEYER_VERSION→2 (напр., расширен functionPid-класс: слово было 'גם#adverb', стало 'pid:3304'); ПК-клиент обновился и re-key'нул локально, телефон со stale SW-кэшем (задокументированная реальность проекта) или с офлайн-outbox ещё неделю шлёт события с v1-ключами. Серверный лог получает ДВЕ item_key-линии одного слова: replay считает due по хвосту одной, слово одновременно «новое» и «в повторении», due-кольцо и агент видят разное. Это ровно тот «раскол истории по ключевым диалектам», от которого lemma-canon и создавался (P0 BLOCKER B1/B2), — воспроизведённый на сервере.

**Предложенный fix:** (1) Поднять keyer_version в первокласcное поле конверта §6; (2) задать ingest-политику: пачка со смешанными/устаревшими keyer_version — reject или карантин с translate-стадией, не молчаливый приём; (3) ДО CLG-P2 задизайнить серверный re-key, совместимый с append-only: таблица key_alias (old_key→new_key, keyer_version), канонизация применяется на ЧТЕНИИ/replay, строки лога не трогаются; (4) гейт: replay с alias-слоем == replay пере-ключёванного клиентского лога на реальном профиле.

### M37 [R13] §9 CLG-P3 + §4.3 — Lossless-гейт одноразовый: события между снапшотом бэкфилла и включением моста могут навсегда выпасть из канона, механизма постоянной reconciliation нет

**Опровержение:** Гейт CLG-P3 фиксирует равенство логов в МОМЕНТ dry-run и никогда не перепроверяется. Док не приколачивает реализацию outbox к самому логу: если outbox — отдельная очередь, наполняемая писателями с момента включения моста (а все 5+ существующих путей записи зовут appendReviewLog в таблицу напрямую и об outbox не знают), возникает дыра: бэкфилл-ingest снял снапшот OPFS-лога в 12:00, гейты гонялись до вечера, мост включён в 18:00; в 14:00 владелец позанимался в Зале — 30 событий легли в review_log, но не в снапшот и не в outbox. Локально они есть, на сервере — никогда не появятся: cursor-синк движется только вперёд. После §4.6-флипа канон = сервер: серверный replay для этих слов беднее реальности, и при доставке проекций вниз верный локальный кэш перетирается неверным каноном. Гейт «клиент-лог == сервер-лог» был честно зелёным в 12:05 — и это его последняя проверка в жизни программы.

**Предложенный fix:** (1) Зафиксировать в §4.3 конструктив: outbox = НЕ отдельная очередь, а cursor (rowid-watermark) по самому append-only review_log — тогда дыра невозможна по построению, и ни один существующий писатель не меняется; (2) cutover-процедура: full-scan ingest повторяется в момент включения моста, cursor инициализируется только после «full-scan = 0 новых строк»; (3) постоянная фоновая reconciliation (count + checksum по item_key-окнам, идемпотентный ре-ingest расхождений) как штатный механизм, а не одноразовый гейт; добавить её в критерии G-5.

### M38 [R13] §9 CLG-P3/P4 (формулировки гейтов) + roadmap — Гейты P3/P4 определены для ОДНОГО профиля владельца; онбординг второго устройства с непустым дивергентным OPFS после canon-флипа — отсутствующая фаза без гейта

**Опровержение:** Dry-run CLG-P3 — «на РЕАЛЬНОМ OPFS-профиле владельца» (единственное число), lossless-гейт — «клиент-лог == сервер-лог», оракул CLG-P4 — «server replay == browser replay». У владельца доказуемо ≥2 живых профиля (ПК + телефон: P4.5 сам обещает push на телефон владельца с deep-link в due-кольцо, а телефонный PWA-профиль копил СВОЮ историю месяцами local-first-эпохи). С двумя устройствами гейты в написанном виде неопределимы: после слияния каждый клиентский лог — строгое ПОДМНОЖЕСТВО серверного, равенство «клиент==сервер» не выполняется никогда, а browser replay (подмножество) ≠ server replay (union) по построению. Сценарий: P3+P4 пройдены на ПК, сервер = канон; на P4.5 владелец открывает PWA на телефоне — телефонный профиль вливает свой дивергентный лог в канон (здесь же детонирует seed-коллизия из находки №1) БЕЗ какого-либо гейта, и первый push приходит с due-числами, посчитанными по состоянию, которое только что молча перемешалось. Второй девайс — не «ещё один клиент», а полноценная вторая миграция, и в roadmap для неё нет ни фазы, ни гейта.

**Предложенный fix:** (1) Переформулировать гейты: lossless = «после полного двустороннего синка КАЖДЫЙ клиентский лог == серверный == union всех», оракул P4 = «server replay(union) == browser replay(union) после downstream-синка»; checksum — по детерминированному порядку (reviewed_at, id); (2) добавить в roadmap явную фазу/гейт «second-device onboarding»: подключение существующего непустого OPFS-профиля к уже-каноническому серверу = управляемый merge с dry-run (count/checksum/replay-диффом и отчётом ДО применения), прогнанный на реальном телефонном профиле владельца до CLG-P4.5.

### M3 [R16] §13.4 / §3.1 / §11 — «CLG-P1–P5 влезает в основной контейнер» — топологическое решение подписано без измеренного baseline текущего потребления RAM/CPU (нарушение собственной нормы R10 measure-before-code в ресурсной плоскости)

**Опровержение:** Док трижды называет бюджет 1536 MB (§3.1, §11, §13.4), но нигде нет замера, сколько из него УЖЕ занимает сервер+TTS-прокси+Dicta-проксирование под реальной нагрузкой (p95). Сценарий провала: фактический headroom оказывается, скажем, ~200 MB под пиковой TTS/bake-нагрузкой → добавленные в P2–P4 ingest-батчи + серверный FSRS-replay + Web Push-планировщик выталкивают контейнер за hard limit → OOM-kill main-контейнера обнаруживается не гейтом, а падением прода посреди CLG-P3/P4 — ровно тогда, когда идёт миграция канона и стабильность сервера критична для lossless-гейта.

**Предложенный fix:** В CLG-P1 добавить дешёвый measure-гейт: снять и вписать в док baseline RAM/CPU main-контейнера (idle + под TTS-нагрузкой, p95 за сутки), зафиксировать headroom-порог (например, «P2–P5 суммарно ≤ 30% свободного запаса, иначе досрочный вынос планировщика в отдельный сервис»). Одна строка docker stats — но решение §13.4 станет измеренным, а не предположенным.

### M4 [R15] §7 / §9 G-EXT — Retention/обучение на данных у LLM-провайдера (Gemini) для классов C/D не адресованы

**Опровержение:** Класс C-контент («разрешить агенту видеть полный текст») по §7 уходит в Gemini. Политика §5 (TTL класса D) покрывает только собственное хранение; провайдерская сторона — retention для abuse-мониторинга, а на free-tier ещё и использование промптов для обучения моделей — не упомянута ни в классах данных, ни в G-EXT privacy-ревизии, ни в consent-copy. Сценарий провала: внешний пилот на server-key free-tier → личные письма пользователей легально утилизируются Google для тренировки моделей, о чём согласие класса C не предупреждало.

**Предложенный fix:** Добавить в G-EXT пункт: server-key только paid-tier/условия без обучения на данных + фиксация DPA/data-processing terms провайдера; в consent-copy класса C явно назвать третью сторону-процессор (Gemini/Google) и срок её retention.

### M5 [R15] §9 G-EXT / §13.1 — G-EXT не содержит минимального возраста / модели согласия для несовершеннолетних и организационного (ульпан) сценария

**Опровержение:** Внешний пилот проекта исторически нацелен на ульпан-когорты, §2.2 включает пакеты «школа/сад», а сервер — в ЕС (GDPR Art.8: для info-society services согласие несовершеннолетнего до 16 требует носителя родительской ответственности). consent_records моделирует только собственное согласие пользователя; G-EXT-чеклист (privacy-ревизия, tenant isolation, rate limits...) не содержит ни минимального возраста в terms, ни модели родительского/организационного согласия. Сценарий провала: ульпан-преподаватель приводит группу, среди которой 16–17-летние репатрианты → аккаунты с классом A-данных (а при галочках — и C) создаются на несовершеннолетних без валидного правового основания.

**Предложенный fix:** Добавить в G-EXT пункт: либо минимальный возраст в terms (16+/18+) с age-gate при регистрации, либо расширение consent_records полем consent_by (self | parent | organization) с процедурой для образовательного сценария; решение зафиксировать до первого внешнего пользователя.

### M6 [R2] §2.2 (миссии) — Миссия «закрыть 4 почти-закреплённых слова за 7 минут» противоречит семантике движка: массированный same-day дрилл не даёт «закрытия» при enable_short_term=false

**Опровержение:** fsrs-core.js работает с enable_short_term=false и learning_steps=[] (шапка файла): повторы того же дня и ранние (не-due) повторы при retrievability≈1 дают мизерный прирост стабильности — «закрыть за 7 минут» слово, которое не due, физически невозможно в терминах движка. Сценарий: юзер выполняет миссию, UI рапортует «4 слова закрыты», через 3 дня те же слова снова due → «миссии врут» → доверие к агентской геймификации падает; альтернативная реализация (форсировать grade 4 ранними повторами) пишет в канон события-накрутку. Классическая spacing-литература: retrieval ниже порога усилия не консолидирует.

**Предложенный fix:** В §2.2 добавить политику отбора миссий: пул только due/overdue/lapsed (то, что движок сегодня реально может «продвинуть»); язык «закрыть» заменить честным предикатом («пройти сегодняшний повтор», «вернуть 4 упавших слова»); принудительные ранние повторы не-due слов запрещены как источник событий review.

### M7 [R5] §2.2 (Израиль-пакеты) — «Иврит для жизни» — витринный сценарий без единого кирпича в программе

**Опровержение:** Сценарий требует: загрузку реального письма (файл/фото → OCR), хранение класса C, тренировку ответа, шаблоны. В §6 нет таблиц для загруженных документов, в P1–P10 нет ни file-upload, ни OCR, ни C-инфраструктуры. Сценарий провала: концепт-док создаёт ожидание killer-фичи «пользователь загружает письмо из битуах леуми», которую программа по построению не может отдать даже к P10 — на любом демо/питче это первое, что спросят, и первое, что не работает.

**Предложенный fix:** Пометить в §2.2 как «vision, вне программы CLG-P1..P10» или убрать; если оставлять в горизонте — требует своей фазы с классом C и file-ingest, которую надо честно вписать и оценить.

### M8 [R5] §9 (CLG-P8) — Mini App при нуле внешних пользователей — заведомо худший дубликат собственного тренажёра

**Опровержение:** P8 строит тренировки due/listening/dictation/cloze внутри Telegram-webview — то, что PWA владельца уже делает богаче (due-кольцо в живом чтении, reveal-then-grade, огласовки, аудио-канон). Сценарий провала: владелец тратит недели на Mini App v1, пользуется им дважды и возвращается в PWA, потому что она лучше; тем временем P9 (agent-кнопки в Зале/Студии — поверхность ЕЖЕДНЕВНОГО использования владельца) ждёт своей очереди позади. Красный флаг R5: функция хуже собственного бесплатного аналога.

**Предложенный fix:** Понизить P8: перенести после P9 либо гейтить триггером «есть внешние пользователи/дата пилота». Бот-команды P7 уже закрывают messenger-кейс для owner-as-user.

### M9 [R5] §11 — Пивот принимает постоянные per-user издержки без единого слова о том, кто платит

**Опровержение:** Программа осознанно берёт на себя серверные LLM-затраты (server-key для внешних, §11 BYOK-напряжение), хранение learner-данных, GDPR-обязательства и liability — навсегда и на пользователя. Cost Governor (R16) задаёт лимиты, но у лимитов нет бюджетной цели, потому что revenue-модель не существует даже как вопрос: слово «премиальность» в §2.4 — про ощущение, не про tier. **Предложенный fix:** Добавить в §11 явный пункт: модель покрытия затрат внешних пользователей (paid tier / BYOK-agent-key / спонсируемый ульпан-контракт) — решение требуется до G-EXT, вместе с privacy-уровнем-2.

### M10 [R12] §4.7 (+§4.6) — Граница «mirror vs dual-write» не проговорена словами — педантичное чтение §4.7 объявляет собственный CLG-P2 нарушением

**Опровержение:** Буквально §4.7: «запрещено иметь двух независимых писателей одного и того же state». На P2 браузер пишет review_log в OPFS И шлёт копию на сервер — два писателя одного логического лога. Неявное различие (реплика ИММУТАБЕЛЬНОГО события одним producer'ом с content-id ≠ второй независимый мутатор state) в доке отсутствует — первый же ревьюер кода P2 упрётся в этот вопрос, как и поставлен он в задании этой критики.

**Предложенный fix:** Добавить в §4.7 явный критерий легальной репликации: один producer события, content-детерминированный id, идемпотентный транспорт (INSERT OR IGNORE), получатель не мутирует, — это копия канона; dual-write = два НЕЗАВИСИМЫХ производителя/мутатора одного факта.

### M12 [R12] §7 (+§5) — Нет матрицы «tool × класс данных / consent-режим»: флагманские сценарии §2.2 требуют класс B, поведение агента при выключенном B-синке не определено

### M13 [R11] §3.1 — Инвентарная неточность: существует четвёртый id-namespace `sre:<uuid>` (Studio-trainer), случайный, не content-детерминированный — дедуп для него держится только на verbatim-переносе id

**Опровержение:** §3.1 перечисляет ровно три формата id (app:|anki:|seed:) и обобщает «id — content-детерминированный». Живой Studio-путь пишет `id: 'sre:' + crypto.randomUUID()` (local-db.js:4064, 4099) — id не выводим из содержимого; идемпотентность держится исключительно на сохранении минтованного id при любом переносе (bundle Pass 8/14). Если sync-bridge CLG-P3 где-либо ПЕРЕ-derive строку вместо verbatim-передачи (например, при конфликте форматов или нормализации), sre-события задвоятся — а док, декларируя content-детерминизм для всех id, не даёт ему повода этого не делать.

**Предложенный fix:** Поправить §3.1: четыре namespace, `sre:` = random uuid, минтуется один раз. В контракт CLG-P3 (outbox/ingest) внести явное требование: строки review_log шипятся verbatim с исходным id; пере-derivation id на любой стороне запрещена.
