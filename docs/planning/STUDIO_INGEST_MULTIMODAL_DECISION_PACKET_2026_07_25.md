### Детали и линзы по сценариям

- **S1 (статьи).** Браузер не может fetch чужой URL (CORS) → тонкий серверный эндпоинт
  fetch+extract (Readability-класс). R14: анти-SSRF обязателен (только http/https, запрет
  приватных/link-local IP и редиректов в них, лимит размера/времени). R4: провенанс — source-URL
  сохраняется в артефакте, виден пользователю.
- **S2 (PDF/Word).** Gemini читает PDF нативно → BYOK-путь уже есть; DOCX — mammoth.js в браузере
  либо тоже Gemini. R11: извлечение ивритского текста из PDF печально известно (порядок RTL,
  никуд, лигатуры) — до масштабирования мини-gold-набор 10–20 реальных PDF, честная деградация
  («не удалось надёжно извлечь — вставьте текст»), никакого молчаливого мусора.
- **S3 (RU/любой → иврит-таблица).** Расширение существующего промпта + переключатель направления
  в UI. R1/R9: сгенерированный иврит = **derived, не asserted** — помечается в провенансе; никуд
  и морфология идут существующим пайплайном (②-заметки, офлайн-словарь) с их гейтами. R2:
  закрывает петлю production («как сказать эту мысль»), сильнейший сценарий для пилотных новичков.
- **S4 (аудио).** ASR через Gemini (BYOK, аудио-модальность). Word-level тайминги ASR ненадёжны →
  **честная посегментная подсветка**: формат timing-сайдкара `[{o,t}]` уже терпит частичный
  тайминг (studio-karaoke гласит «no fake highlight»). R11-инвариант: НЕ выдавать по-словную
  точность, которой нет; апгрейд до word-level — отдельным решением, только с независимой
  верификацией. Лимит длительности per-request + смета стоимости в UI до запуска (R16).
- **S5a (видео с субтитрами).** Если у видео есть субтитры (ручные или авто) — VTT даёт готовый
  сегмент-тайминг: караоке почти бесплатно, ASR не нужен. Серверный caption-fetch (тот же
  fetch-прокси). Качество авто-субтитров иврита переменное → бейдж провенанса «авто-субтитры».
- **S5b (видео без субтитров).** Требует yt-dlp/ffmpeg → по решению I-ARCH НЕ на сервере.
  Путь W3: companion-скрипт у владельца (локально извлекает аудио → загружает файлом → S4).
- **S6 (аудио-перевод).** Цепочка из готовых кирпичей: ASR (S4) → таблица (ядро) → per-row TTS
  (существует). Выход — билингвальная таблица с оригинальными сегментами И иврит-TTS. «Дубляж»
  как один склеенный файл — только как экспорт-опция (S7-класс), не отдельный движок.
- **S8 (фото/OCR).** Gemini vision хорошо читает печатный иврит; тот же файловый путь, что S2.
  Владелец не перечислял — добавлен брейнштормом, одобрен в составе каркаса.
- **S10 (share_target).** PWA-манифест + SW route: телефонное «Поделиться» (URL, файл, текст) →
  единый диалог «Импорт». Превращает каждый сценарий в two-tap мобильный флоу (R4).
- **S11 (graded-пересказ).** Опция выхода «упростить до моего уровня» при любом инжесте:
  R8 graded-reading + R2 comprehensible input; уровень берётся из профиля ученика (CLG).

## 3. Архитектура (I-ARCH: решено)

### 3.1 Развилка и решение

- **A. Browser-first BYOK — ✅ ВЫБРАНО.** Файлы (PDF/DOCX/аудио/фото) идут из браузера в Gemini
  по существующему BYOK-прокси; для URL — только тонкий серверный fetch-extract + caption-fetch.
  Никакого yt-dlp/ffmpeg на проде. Платит владелец ключа (R16), сервер тонкий (R12; hard-limit
  RAM 1536MB на CX23), данные в OPFS пользователя (R15), работает для пилотников со своими ключами.
- **C. Эволюция в гибрид — ✅ ПРИНЯТА как путь.** Для тяжёлых кейсов (S5b) — локальный
  companion-скрипт у владельца: извлечь аудио → загрузить файлом. Дёшево закрывает хвост без
  серверного риска.
- **B. Полный серверный медиа-пайплайн — ⏸ ОТЛОЖЕН** до доказанного спроса. Минусы: вечная гонка
  yt-dlp с блокировками платформ, CPU/RAM-бюджет CX23, расширение R14-поверхности.

### 3.2 Ограничения выбранной архитектуры (честно зафиксировать)

- Inline-загрузка в Gemini ограничена (~20MB запрос); длинные медиа → Gemini Files API тем же
  BYOK-ключом (загрузка из браузера пользователя, хранится у Google до 48ч) — это часть дизайна
  Wave 2, не сервера.
- «Вставил ссылку на любое видео без субтитров — получил всё» в этой архитектуре НЕ обещается —
  честный UX-тупик с подсказкой companion-пути (R4: тупик оформлен, не молчалив).

### 3.3 Граница с Hermes-полосой (ЗАФИКСИРОВАНА)

Эта программа = **in-app** инжест: артефакты ложатся в OPFS/Библиотеку пользователя через его
BYOK-ключ, исполнитель Claude. Hermes-scaleup (исполнитель Codex) решает свои Д2 (Spotify) и
Д7 (raw-audio, default не хранить) в своём леджере `hermes-education-scaleup/2026-07-21/STATUS.md`.
**Правило границы:** любое будущее решение о серверном медиа-пайплайне (вариант B) принимается
одним пакетом с Д2/Д7, не порознь — чтобы не выросло два параллельных медиа-инжеста.

## 5. Данные для ментора/CLG (I-CLG: утверждено)

Инжест-артефакты — источник данных ИИ-ассистента/ментора и базы учебного процесса. Доктрина:

1. **Ни одного нового параллельного хранилища.** Каждый артефакт приземляется в УЖЕ канонический
   формат: текст → личный текст Зала; таблица → Студия; лексика → ②-заметки; аудио-тайминг →
   существующий timing-сайдкар. Событие изучения → только `review_log` (истина памяти не меняется).
2. **Провенанс-паспорт обязателен** на каждом артефакте: источник (URL/имя файла), метод
   (extract/OCR/ASR/перевод), модель+версия, дата, флаг **derived≠asserted** (R9). ASR-транскрипт
   и сгенерированный иврит никогда не выдаются за проверенный текст (R11: не перезаписывать
   выверенное менее надёжным).
3. **Ментор/Hermes читают существующими MCP-инструментами** (list_personal_texts и родня) —
   новые типы артефактов появляются в тех же реестрах, отдельного API-канала не строим.
   Единственное расширение: медиа-ассет (загруженное аудио) + привязка транскрипта.
4. **R12:** log/projections/artifacts разделены, без dual-write. **R15:** медиа-файлы = класс
   данных пользователя, OPFS-first; серверные temp (fetch-кэш) — с TTL. **R17:** квизы по
   ingested-контенту грейдит детерминированное ядро с grader-провенансом, не тот же LLM,
   который контент породил (анти-циркулярность).

## 6. Ключевые риски и контрмеры

| Риск | Линза | Контрмера |
|---|---|---|
