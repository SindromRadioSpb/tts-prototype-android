## §0. TL;DR

- **Кросс-корпус для оси «знаю/учу» УЖЕ решён** архитектурно: одна per-lemma карта `getKnownWordStates()`
  (ключ канонический `pid:N`/`lemma#pos`, корпус-агностичный) → покрытие/i+1/цвет каждого текста
  считаются против неё. Слово, пройденное в корпусе A, авто-известно в B. **Это не надо строить —
  надо ПОКАЗАТЬ** (и проверить на per-corpus утечки).
- **Реверс-синк Anki частичный и LOCAL-ONLY:** кнопка «Синхронизировать из Anki» работает только при
  локальном Anki+AnkiConnect. **Remote-владелец (kolosei.com) ей пользоваться НЕ может.**
- **P4 связал Anki→расписание Зала**, но внёс **латентную регрессию демоции 'new'** (§2.2, подтверждена
  по коду) — чинить в P4.1.
- **Премиум-цель:** ОДНА память слова, корпус-агностичная, питаемая всеми каналами (recall Зала,
  тренажёр Студии, Anki), сводимая через `replay(review_log)`; честный отчёт «что изменилось» + живое
  отражение в Зале; рабочий remote round-trip (минимум — .apkg-реимпорт).
- **Замер (владелец, прод, read-only):** Anki-данных **0** (anki_managed=0, anki-события=0,
  anki_word_exports=0, srs_cards=0); review_log=54, все Room. → felt-value чистого Anki для владельца
  низкая; наибольшая ценность = подсветка кросс-корпуса + фикс демоции + премиум-оповещение.

## §1. Как это устроено сейчас (факты + код-якоря)

**Реверс-синк есть, но частичный и LOCAL-ONLY.** Кнопка «Синхронизировать из Anki» (Студия,
`index.html:11519` → `v3AnkiSyncNow` `index.html:~36784`) работает только в `LOCAL_MODE`
(AnkiConnect = `localhost:8765`, нужен десктопный Anki + аддон на той же машине). Remote →
отдаёт «Синхронизация доступна только в локальном режиме». **Ключевое ограничение.**

**Что синк делает** (`v3AnkiSyncFromAnki` `index.html:~15466`): тянет состояния из Anki →
- `applyAnkiReviewStates` (`local-db.js:2542`) — зеркалит состояние в `srs_cards` + метит
  `meta.anki_managed=true` (исключает из in-app due-очереди Студии); есть **local-newer guard**
  (`keepLocal`) — recon велит его снять (§2.8);
- `recordAnkiReviews` (`local-db.js:2619`) — пишет в `events` (research-аналитика), id `anki:<reviewId>`;
- **[P4]** `ingestAnkiReviewsToLog` (`local-db.js`, P4-блок) — канон `review_log` + пересчёт `word_status`.

**Один источник истины — в основном ДА, через per-lemma слияние.** Карта «что я знаю»
`getKnownWordStates()` (`local-db.js:2236`) — единая, ключ канонический per-lemma, корпус-агностичный.
Сливает **в два слоя**:
1. **overlay** (`getLearningStateOverlay` `local-db.js:2048`): `srs_cards` → per-note состояние
   (weak/stale/learning/new/known; RANK-max на лемму). Anki-состояние приходит СЮДА (через
   applyAnkiReviewStates → srs_cards.state → overlay).
2. **manual-wins** (`local-db.js:2265`): `for (lk in getAllWordStatuses()) out[lk]=manual[lk]` —
   любой непустой `word_status` ПЕРЕБИВАЕТ overlay для этой леммы.

**→ Кросс-корпус УЖЕ решён для оси «знаю/учу».** Покрытие и i+1-frontier каждого текста считаются
клиент-сайд против ЭТОЙ ОДНОЙ per-lemma карты (`corpus-vocab.js:15-16,51,64`; `KNOWN_STATES` на
`corpus-vocab.js:37`). Слово, пройденное/изучаемое в корпусе A, авто-засчитывается в покрытии B,
красится во всех текстах, уходит из «нового» везде. **Это уже архитектура, а не то, что надо строить.**
Anki-выученные слова уже становятся «known»/«learning» в этой карте (через srs_cards→overlay) —
тултип кнопки (`index.html:11519`) не врёт.

**Чего до P4 не было:** Anki-ревью кормили граф Студии + покрытие/frontier, но НЕ доходили до
**расписания Зала** (кольца/recall = `word_status.srs_*`). P4 это связал:
Anki → `review_log` → `updateSrsState` → `word_status.srs_*` → кольца Зала.

**Оповещение — минимальное** (`index.html:~36816`): строка статуса + тост («Синхронизировано: N слов —
обновлено X, новых выучено Y, удержание Z%»). Ни превью, ни «что изменилось в Зале», ни живого
обновления открытой вкладки Зала.

## §2. Разрывы и риски (в т.ч. не обговорённые владельцем)

1. **Remote-раунд-трип сломан (главное).** AnkiConnect локальный → владелец и любой remote-пользователь
   не может синкать назад кнопкой. Премиальный remote round-trip требует другого пути (развилка **A**).

2. **Регрессия P4 «демоция 'new'» — ПОДТВЕРЖДЕНА ПО КОДУ (чинить в P4.1).** `updateSrsState` при INSERT
   ставит `status='new'` для слова без строки `word_status`. Далее `getKnownWordStates` (стр. 2265)
   делает manual-wins: `out[lk]='new'` **перебивает** overlay-«known» (пришедшее из Anki через
   srs_cards). А `'new'` **НЕ входит** в `KNOWN_STATES` покрытия (`corpus-vocab.js:37`). → **Anki-известное
   слово, не тронутое в Зале вручную/recall'ом, демотируется до «new»** в покраске/покрытии/frontier.
   Тебя сегодня не касается (0 Anki-данных), но это латентный баг и ровно та кросс-поверхностная
   рассинхронизация, которой нельзя допускать (R11). *Фикс-направления:* updateSrsState не создаёт
   демотирующий статус (schedule-only без вставки статуса), ИЛИ merge учитывает overlay-known, ИЛИ
   'new'-из-updateSrsState трактуется отдельно от ручного 'new'.

3. **Расписание vs ручной уровень: «пройдено в Anki» → «пройдено (known)» на сайте?** Оценка в Anki —
   НАСТОЯЩИЙ машинно-верифицированный тест (в отличие от reading-tap самоотчёта, где D8(a) запретил
   промоушен уровня). Сейчас P4 двигает только расписание; «known»-цвет приходит из overlay. Надо
   решить (развилка **B**): зрелое Anki-ревью повышает ручной уровень к «known» или остаётся schedule-only.

4. **Две пересекающиеся системы состояния не сведены в одну.** Система A (`srs_cards`/overlay — граф +
   покрытие/frontier) и Система B (`word_status.srs_*` + manual — кольца/recall/цвет) перекрываются в
   `getKnownWordStates` через хрупкое двухслойное слияние. Премиум = ОДНА per-lemma память, а не две с
   merge (развилка **C**).

5. **Нет живого/кросс-таб отражения.** Синк идёт в Студии (`index.html`); открытая вкладка Зала
   (`library.html`) не обновит кольца/покрытие до переоткрытия. Есть мульти-таб BroadcastChannel-прокси
   (P0-1 v2) — синк должен слать «профиль изменился», чтобы Зал перерисовался.

6. **Sentence-карты не переносятся кросс-корпусно (верно, но UX прояснить).** Карта предложения =
   `sent:<text_key>#<oix>#<tpl>` — по природе привязана к тексту, не к слову; `recomputeSrsFromLog`
   их СПЕЦИАЛЬНО пропускает (их state в `srs_cards.meta_json.fsrs`, не в word_status). Практика
   предложений текст-специфична, память слова — универсальна; это стоит честно показать в UX.

7. **Провенанс (R9).** Состояние из Anki vs in-app vs ручное должно быть честно различимо (в карточке
   уже есть lifecycle «📤 в Anki»); реверс-состояние — помечать как машинно-Anki-производное.

8. **Семантика конфликта не единая.** Принцип recon — «сливаем истории, не перезаписываем состояния»
   (P4 делает replay-merge для расписания через review_log). Но `applyAnkiReviewStates` всё ещё
   ПЕРЕЗАПИСЫВАЕТ `srs_cards`-состояние с local-newer-гардом (`keepLocal`), который recon велит снять.
   Нужна ОДНА политика слияния (replay-merge везде).

## §3. Премиальный конечный вид

ОДНА память слова, корпус-агностичная, питаемая всеми каналами (recall Зала, тренажёр Студии, Anki),
сводимая через `replay(review_log)`. «Знаю/учу» и расписание согласованы везде: отметил/выучил/прошёл
слово где угодно (любой корпус, Anki) → это его состояние во всех текстах и корпусах. Реверс-синк из
Anki даёт честный отчёт «что изменилось» (+ Δпокрытия) и живьём обновляет Зал. Remote-пользователь
имеет рабочий раунд-трип (минимум — реимпорт .apkg). Провенанс каждого состояния честен (R9).

## §4. Развилки (владелец решает)

**A. Remote round-trip:**
- (a) **реимпорт .apkg** *(рекоменд.)* — работает remote, периодически вручную; идентичность карт по
  тегам `lp_note_<id>` уже есть (Anki A+B shipped);
- (b) серверный мост AnkiWeb — мощно, но сложно + ToS + секреты;
- (c) честно «для remote только экспорт», AnkiConnect — для локальных power-user.

**B. Anki-ревью → ручной уровень:**
- (a) только расписание (консервативно, текущий P4);
- (b) зрелое Anki-ревью повышает к «known» с капом (Anki-оценка верифицирована — в отличие от reading-tap);
- (c) зрелая Anki-карта прямо ставит «known».

**C. Модель сведе́ния:**
- (a) оставить две системы + починить merge *(дёшево, лечит демоцию 'new' §2.2)*;
- (b) свести к ОДНОЙ per-lemma памяти (`word_status.srs_*` — единый кэш расписания; `srs_cards` →
  только linkage/экспорт) — больше работы, но принципиально.

**D. Глубина оповещения:** минимальный тост vs премиум «что изменилось + Δпокрытия + живое отражение в Зале».

## §5. Рекомендуемый план (без кода, поэтапно)

- **P4.1 — корректность+честность:** починить демоцию «new» (§2.2 — updateSrsState не должен перебивать
  known-карту), решить развилку **B**, свести merge-политику (**C(a)** как минимум: снять local-newer
  guard §2.8, replay-merge везде). Делает P4 верным. *(Гейт: расширить `smoke:memory-canon` — Anki-known
  слово НЕ демотируется в getKnownWordStates после ingest.)*
- **P4.2 — remote round-trip:** путь реимпорта .apkg (**A(a)** — то, чем владелец реально сможет
  пользоваться remote).
- **P4.3 — премиум-оповещение + кросс-таб:** отчёт «что изменилось» + Δпокрытия + BroadcastChannel →
  Зал перерисовывается (§2.5, **D**).
- **Кросс-корпус:** уже работает — **выгодно ПОКАЗАТЬ** («это слово ты знаешь во всех своих
  текстах/корпусах» + проверить, что нет per-corpus утечек в getKnownWordStates/покрытии). Малый труд,
  высокая воспринимаемая ценность.

**Норма перед кодом:** адверсариальная роль-критика (R2/R9/R11) ДО реализации (как для retention-recon);
live-verify Anki-путей — синтетикой на ОДНОРАЗОВОМ профиле (у владельца 0 Anki-данных, AnkiConnect
remote недоступен); commit+push+prod-verify; i18n×3 для новых строк.

## §7. Честная приоритизация

Владелец **не использует Anki** (0 данных) и **remote** (кнопка не работает). Чистый Anki-раунд-трип
сейчас имеет низкую felt-value лично для него. Наибольшая ощутимая ценность в этом направлении:
1. **подсветить уже существующую кросс-корпусную унификацию** (владелец её реально ощущает ежедневно);
2. **починить демоцию 'new' (§2.2)** — корректность/честность (R11);
3. **премиум-оповещение/консистентность (§2.5, D)**.
Сам Anki-мост честнее сделать через **.apkg-реимпорт (A(a))**, чтобы он вообще работал у remote.
