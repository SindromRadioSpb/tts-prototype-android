# План: однозначная морфологическая карта и объект знания

Дата: 2026-10-20. Статус: подготовлен по запросу владельца; реализация не начата.
База анализа: код `32204e7c` (3.11.800), диагностический отчёт `fe0d5e08`.
Основание: [יוֹפִי follow-up](../../research/hamam-context/2026-10-20/YOFI_FOLLOWUP.md), O-111–O-114.
Это следующий этап после [CP-1–CP-6](CONTEXT_PROVENANCE_REQUIREMENTS_2026_10_20.md), не замена отчёта об архивной сохранности.

## Цель и границы

Карточка должна ясно отвечать: что слово значит в этой строке, какие анализы доступны,
какой анализ выбран и для какого слова сохраняется знание. Все утверждения имеют свой источник и область.
Исправляется общий путь распознавания и выбора, включая статьи без таблиц форм и орфографические варианты.

В этот выпуск входят локальные кандидаты, выбор вхождения, UI и согласование идентичности на затронутых поверхностях.
Генерация нового ИИ-морфологического слоя, массовая повторная обработка провайдерами и новая система sense-ID не требуются.
Статус относится к лексической записи; два значения внутри одной статьи Pealim этот этап автоматически не разделяет.
Исходники, архивная огласовка/переводы, оплаченный кэш и история обучения сохраняются.

## Принятый для плана пользовательский сценарий

Для `בְּסֵדֶר, יוֹפִי.` при открытии:

1. Заголовок: `יוֹפִי`. Ни один провайдер не помечает всю карточку целиком.
2. «В этой строке: отлично» — контекстный перевод с собственной меткой ИИ/ручной правки. Источник огласовки — отдельно у огласовки.
3. «Варианты значения»: «отлично! замечательно! · наречие · Pealim» и «красота · существительное · Pealim». Ссылки ведут на соответствующие статьи. Спорный локальный анализ Dicta подписан как отдельное свидетельство; совпадающие свидетельства одного кандидата объединены без потери источников.
4. Для неразрешённой неоднозначности: «Выберите значение для этой строки». Нажатие варианта даёт предварительный просмотр; «Использовать здесь» сохраняет выбор. «Имя собственное» находится среди действий уточнения, а не рекомендуется каждому слову.
5. После выбора наречия: «Мой статус: יוֹפִי — отлично! замечательно! · наречие». Отметка относится к этой записи; существительное сохраняет самостоятельный статус.
6. «Изменить выбор» и «Сбросить мой выбор» доступны; сброс возвращает машинные данные, сохраняя журнал решений и обучения.

Отдельное подтверждение не требуется для каждого однозначного слова. Выбор нужен при нескольких правдоподобных лексических записях, конфликте источников или отсутствии согласованного объекта знания.
Совпадение одной словарной формы не означает доказанную однозначность контекста. Русский gloss ИИ сам по себе не подтверждает POS или словарный ID.

## Шаг 1. Зафиксировать воспроизведение и контрольную выборку

**Результат:** до изменения кода имеются воспроизводимые проверки O-111–O-114 и базовый замер.

- Малые fixtures: יוֹפִי/יֹפִי, noun/adverb одной формы, статья без cells, одно слово с несколькими статьями, שאול как имя/прилагательное, неизвестное слово, слово с приставкой, разные огласовки омографов.
- Разделить проверки наличия кандидатов, правильности выбранного чтения и согласованности объекта знания. Принадлежность перевода архиву не считается языковой проверкой.
- По исходному материалу собрать агрегаты: потерянные локальные кандидаты, несовместимые ID/POS, неизвестная/спорная идентичность. Полный материал — только локально/read-only, в git агрегаты и небольшие fixtures.
- Измерить холодное/повторное открытие карты и стоимость индекса кандидатов для сопоставления после правки.

**Выход:** дефекты воспроизводятся; уже корректные пути имеют контрольные примеры, не зависящие от того же ответа Dicta как единственного эталона.

## Шаг 2. Общий набор кандидатов и согласованный анализ — O-112/O-113

**Основные точки:** `reader-morph.js`, `notes-autogen.js`/общий resolver, `pealim-function-links.js`; использовать существующие индексы и модульные границы.

- Собрать кандидатов из словарных форм, заголовков, самостоятельных статей без cells и доступных морфологических свидетельств. Дедупликация по стабильному ID анализа, не по одному написанию.
- Разделить кандидата и свидетельства: ID, лемма, POS, значение, корень, таблица и прямая ссылка принадлежат одному анализу; сведения о совпадении формы и контекстном выборе хранятся отдельно.
- Поддержать יוֹפִי/יֹפִי как доказанный вариант словарного поиска. Не вводить глобальное удаление ו/י/огласовок; нормализация создаёт кандидатов, не сливает их идентичности и не переписывает исходную строку.
- Dicta fallback дополняет сведения и не уничтожает известные варианты. Лексикон написания устройства отличается от разбора текущего предложения.
- Устранить POS-mismatched присваивание Pealim ID. Совпадение написания само по себе даёт кандидат/поиск, а не право подменить ID существительного ID наречия.
- У статьи без таблицы показывается честное отсутствие таблицы, а не отсутствие слова/перевода.
- Кандидатный индекс строится однократно и переиспользуется; чтение карты не сканирует весь материал и не требует сети.

**Выход:** оба варианта יוֹפִי видны для обеих форм написания; нет комбинации noun + 5857. Для омографа сохраняется неоднозначность даже при совпадении формы.

## Шаг 3. Выбор чтения конкретного вхождения

**Основные точки:** `lexical-resolution-core/service/repository`, `morph-host.js`, места загрузки effective analysis в `reader-morph.js`.

- Использовать существующие `confirm_candidate`, `manual_correction`, `clear` и append-only lexical_resolution_events. Новое параллельное хранилище не создавать.
- Общий callback «подтвердить анализ» заменяет узкий callback только для имени; имя сохраняет существующее безопасное поведение.
- Сохранять source anchor точной строки/слова и fingerprint реально показанных кандидатов. Перед записью повторно проверить источник и выбранный ID/POS; смена строки/карты отменяет зависимое действие.
- Сейчас `projectExactOccurrence` читает только manual_correction. Для confirm_candidate добавить восстановление с проверкой текущего fingerprint; не обходить проверку, записывая любое подтверждение как manual_correction.
- При изменении исходного текста или набора кандидатов решение получает stale по существующему контракту и требует повторной проверки; старое событие не удаляется.
- Owner/teacher decision имеет приоритет над машинным анализом. Поздний Dicta не заменяет выбор, статус, введённую правку или состояние открытой карты.
- Просмотр/выделение варианта не пишет решение, знание, оценку ответа или расписание.

**Выход:** выбранный анализ восстанавливается после закрытия/перезагрузки и переносится существующим ZIP/backup путём; clear/реальное изменение источника обрабатываются корректно.

## Шаг 4. Структура карточки и действия — O-111

**Основные точки:** общий рендерер `reader-morph.js`, `reader-morph.css`, RU/EN/HE локали; существующий дизайн Studio/Room.

- Реализовать сценарий выше. Поля источника огласовки, контекстного перевода и морфологического анализа визуально привязать к своим данным.
- Вместо общего верхнего badge Dicta — источник у конкретного анализа; легенда различает «нет в локальной выборке», «не найдено распознавателем» и «нет данных», не утверждая отсутствия слова на Pealim.
- Варианты доступны непосредственно в карте; внешний поиск остаётся дополнительным действием.
- Общая команда «Уточнить значение здесь» доступна также без ИИ-gloss; имя — один из вариантов коррекции.
- Фокус, клавиатура, свёртывание, закрытие и длинные переводы проверяются на 380 px, desktop, LTR/RTL. Источник/статус проверки не кодируется одним цветом.

**Выход:** без открытия легенды и внешнего сайта понятно, где перевод в строке, где возможный анализ, что выбрано и кто это подтвердил.

## Шаг 5. Объект статуса и единая идентичность — O-114

**Основные точки:** `statusKeyForCard`/`lemma-canon.js`, `morph-host.js`, раскраска/сбор слов/повторов, «Мой словарь», сохранение word_study.

- Получать карточку, подпись объекта статуса, ключ сохранения и ключ раскраски из одного effective analysis. Подтверждённый ID/POS нельзя оставить только на экране, продолжая запись по старому pre-context ключу.
- Для выбранных статей: 5857 → `pid:5857`, 5856 → `pid:5856`; обычные неизменённые записи сохраняют действующие ключи. Версию/алгоритм канонических ключей без миграционного основания не менять.
- При неразрешённом конфликте вместо активных кнопок для скрытого другого чтения — выбор значения на месте. Существующая отметка не исчезает: показывается с точным объектом, к которому она относится.
- «Добавить в мои слова», личный перевод и заметка относятся к явно показанной записи. Правка контекстного gloss остаётся правкой одного вхождения.
- Отметки — через существующий `setWordStatus`/mark event, повторения — через канонический review_log/FSRS. Выбор анализа сам по себе не ставит уровень и не создаёт seed.
- Старые `dl:…`, pid и прочие mark/review/FSRS сохраняются. Массовое связывание, перенос истории или пересчёт знания по совпадению написания не выполняются. Исторические подозрительные связи отражаются в read-only отчёте для отдельного решения.

**Выход:** выбор наречия, отметка и раскраска согласованы во всех затронутых местах. Знание существительного не переносится на наречие и наоборот.

## Шаг 7. Выпуск и production-проверка

- Перед кодовой реализацией взять свежий origin/main в чистом worktree, сохранить чужие изменения. Последующие шаги небольшие и проверяемые; первая контрольная точка — исправленные кандидаты и идентичность без UI.
- Выпускать связанный пользовательский сценарий после всех обязательных gates; промежуточный UI с чужим объектом статуса на production не публиковать.
- Выполнить capacity/health preflight, согласовать shell/SW/locales/integrity и проверить no-cache version, served hashes, DB/migrations после деплоя. Новая очистка диска требует своего разрешения.
- На production проверить исходные יוֹפִי и שאול в профиле владельца без записи отметок/подтверждений; мутации статусов проверить на изолированном тестовом материале.
- Сопоставить review_log/word_status/FSRS до/после read-only owner acceptance; штатное изменение updated_at/позиции при навигации учитывать отдельно, позицию восстановить.
- Закрыть O-111–O-114 только с коммитом и фактическими результатами. Сохранить ограничения языковой проверки и различие local/production/owner evidence.
- При откате вернуть предыдущий код/образ; append-only решения и история сохраняются, проверяется совместимое чтение. Сбой нового выбора блокирует его применение, а не чтение исходного материала.
