# YouTube: проверка временных шкал и восстановление синхронизации

Основание: утверждённая владельцем 2026-09-15 схема проверки обеих временных шкал,
сохранения evidence, проверки начала/середины/конца, частичного восстановления и
отдельного исправления синхронизации без повторного перевода. Исходный commit: `765b8f77`.

## Живой диагноз

В карточке «Выборы-4» (`cPooKT5rFxc`) сохранены 156 реплик, все без времени.
Журнал ASR: `suspect`, 20 проверенных / 17 совпавших якорей, медианная разница 299 с.
Прежний алгоритм удалял отвергнутые метки, оставляя текст. По одному агрегату
нельзя установить, ошибся полный ответ или контрольный фрагмент. Прибавление или
вычитание 299 с не является доказанным исправлением. Подозрение на относительную
шкалу контрольного фрагмента остаётся гипотезой, а не установленной причиной.

Обнаружены дополнительные дефекты: compatibility projection теряла код причины;
`Number(null)` в сохранении происхождения строки превращал отсутствующий индекс
в первый сегмент; точная привязка считала наличие caption ID достаточным для
кнопки даже при отсутствии времени. Последний дефект воспроизведён полным UI smoke.

## Реализованный контракт

1. Новая задача включает в показанную смету три контрольных участка видео.
   Старые задачи без такой котировки не получают дополнительные платные запросы.
2. Сохраняются исходные разобранные метки полного ответа, raw ответы провайдера,
   границы проб, raw ответы проб, статус каждой попытки и диагностический результат.
   Evidence не является источником играбельных меток само по себе.
3. Перед платной пробой сохраняется `pending-charge-unknown`; после ответа —
   результат. После сбоя/перезагрузки завершённые и неопределённые попытки не
   повторяются. У каждого оплаченного контрольного окна одна попытка; ошибка
   прекращает текущую последовательность. Перевод не вызывается при восстановлении.
4. Временная шкала пробы определяется независимо от полного ответа: абсолютное
   время внутри заданного окна либо относительное время внутри его длительности.
   Неоднозначные, немонотонные и выходящие за окно метки не сертифицируются.
5. Якорь — уникальная последовательность четырёх слов. Для общего исправления
   используются только целиком совпавшие реплики: не менее трёх в каждом из трёх
   участков, разброс внутри участка и между медианами не более 5 с. Это выборочная
   проверка провайдерских меток, не утверждение физической проверки каждой секунды.
6. Постоянный сдвиг применяется только при согласовании трёх участков и пригодности
   всех полученных интервалов: порядок, положительная длительность, границы видео.
   Относительная шкала пробы не сдвигает правильный полный транскрипт.
   Неравномерный уход или отдельные ошибки не исправляются общей медианой.
7. При недостатке доказательств доступны только целиком совпавшие реплики с
   наблюдаемой следующей границей. Нет интерполяции пропусков и выдуманного хвоста.
   Кнопки, переходы и подсветка ограничиваются теми же строками; `end_o` обозначает
   границу строк, а не новое время. Старые timing basis hashes сохраняют совместимость.
8. «Восстановить синхронизацию» доступно из источника видео, панели без таймкодов
   и результата задачи. Варианты: проверенные SRT/VTT; ручная разметка реплики;
   три платные пробы после показа их отдельной цены. Частичность результата показана.
   Текст субтитров не заменяет текст карточки; несовпавшие реплики остаются без времени.
9. Перед сохранением пользователь проверяет видео и интервалы. Запись создаёт
   неизменяемую версию транскрипта, обновляет привязку карточки и создаёт версию
   таблицы с новой ссылкой на транскрипт. Старые версии сохраняются. Поля предложений,
   их идентификаторы, перевод, огласовка, транслитерация и learner state не записываются.
   Некорректная старая привязка пересчитывается только по проверяемому тексту.
10. Вся запись выполняется в одной транзакции. CAS проверяет прежнюю привязку,
    источник, предложения, текущую версию и отсутствие чужого draft. Конфликт или
    ошибка откатывает запись целиком. Новый архив содержит новое состояние;
    уже скачанный архив не меняется. Исходные оплаченные данные остаются в истории.

## Упрощение восстановления — 3.11.555

Владелец запустил три проверки и получил четыре пригодных интервала, но попал в
ручную форму. Пустые поля дали SEGMENT_TIMING_INVALID; сохранение результата
провайдера требовало ручного подтверждения прослушивания. Это был барьер UI,
а не необходимость размечать все 156 реплик.

- R4: основной экран показывает количество кнопок и одно действие. Сохранённые
  результаты применяются без новых запросов; новый запуск сначала показывает цену,
  после явного подтверждения сам сохраняет найденные интервалы. Ручной ввод,
  субтитры и диагностический список находятся в дополнительных способах.
- R10: provider evidence не требует ложного утверждения «я прослушал». Его
  authority остаётся provider. Для вручную заданных/загруженных интервалов
  подтверждение остаётся; пороги соответствия текста/времени не ослаблены.
- Автоматическое восстановление сохраняет существующие пригодные интервалы,
  добавляет только неперекрывающиеся новые. Пропуски не интерполируются.
- Владелец разрешил сохранение «Выборы-4»: применены уже оплаченные интервалы
  для реплик 7, 13, 146, 151. В настоящей таблице появились четыре кнопки.
  Все 156 строк, source video и review_log (7758 записей, прежний SHA) сохранены.
  Предыдущая caption revision остаётся в истории. Новых paid calls не было.
- Проверки: 88 targeted unit tests; OPFS smoke в режимах manual, --auto и --paid.
  Последний использует имитацию провайдера: цена до вызова, автоматическое сохранение,
  одна кнопка для одной размеченной строки, неизменный текст, новый архив,
  сохранённая предыдущая версия. RU/HE 380px, EN desktop проверены визуально.

Живые результаты проверки провайдера подтверждают только частичную доступность
времени, не прослушивание владельцем каждой реплики. Остальные 152 строки можно
оставить без кнопок. Физическая/AT проверка этим desktop smoke не заменяется.
